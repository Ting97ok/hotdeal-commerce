# RFC — 재고 동시성 벤치마크 (설계·실측·해석)

> **RFC** = 결정에 이르기까지의 근거·측정·토론을 보존하는 문서. 결정 **결과**의 정본은 `docs/adr/concurrency.md` 3줄 요약이고, 본 문서는 "왜 그 결정인가"를 실측으로 뒷받침한다. (순환을 막기 위해 링크는 ADR → RFC 한 방향만 건다.)
> 대상: 핫딜 재고 차감(`HotDealStock` 한 행)을 3방식으로 **동일 조건 측정**해 운영 1개를 고른 과정 전체 — 예상(가설) → 측정 설계 → 결과 → 결론을 바꾼 사건 → 한계.

## 0. 범위

- **측정 대상**: 구매 경로의 `HotDealStock` 한 행 차감 경합(`POST /api/orders`). 수천 요청이 같은 잔여 수량을 동시에 줄이는 지점.
- **측정 방식**: 낙관락(@Version) · 원자적 조건부 UPDATE · Redis 원자(+Lua) 3방식. 비관락·Redisson 은 이론 예상으로 배제(§1).
- **부하 밖**: 토스 결제 승인 구간은 부하 대상이 아니다 — 외부 샌드박스는 호출량 제한·차단 위험. 부하는 주문 생성 경로에 한정, 결제는 테스트 대역.

## 1. 벤치마크 전에 세운 가설 — 5방식 예상 분석

벤치마크는 "쏘고 보자"가 아니라 **예상을 검증**하는 것이다.

| 방식 | 동작 | 한 행 폭주(핫딜)에서의 예상 |
|---|---|---|
| 낙관락(@Version) | 안 잠그고 진행 → 저장 때 버전 충돌이면 실패 | 충돌률이 매우 높아 대부분 실패·재시도 → **성공 처리량 최저** |
| 비관락(FOR UPDATE) | 행을 잠그고 줄 세움 | 정확하지만 대기 내내 **DB 커넥션 점유** → 처리량이 락 보유시간에 묶임. 커넥션 풀(HikariCP 기본 10)이 먼저 마르는 연쇄 장애 위험 |
| Redis 원자(+Lua) | 인메모리·단일 스레드라 원자 차감 | **처리량 최고** 예상. 단 재고 정답이 Redis 로 옮겨가 DB 정합 보정 필요 |
| 분산락(Redisson) | Redis 락을 서버들이 공유해 직렬화 | 락 획득·해제 왕복 비용 → Redis 직접 차감보다 느림. DB 는 정답 유지 |
| 원자적 조건부 UPDATE | `WHERE remaining >= :qty` 조건부 차감 한 문장, 영향 행 수로 판단 | 재시도 폭증도 긴 커넥션 점유도 없음 — **단일 행 한계까지 단순·정확** 예상 |

- **실측은 3방식**: 낙관락(나쁜 기준선) · 조건부 UPDATE(단순 RDB) · Redis(+Lua, 고성능 대안) — "정확성만은 쉽다 vs 정확성+성능이 어렵다"를 수치로 보이는 최소 집합. 비관락·Redisson 은 위 예상으로 배제(측정 한계효용 낮음).
- **JVM 잠금(`synchronized` 등)은 후보가 아니다** — 자기 프로세스 안에서만 직렬화하므로 서버 여러 대(LB 뒤) 전제에서 서버 사이 동시 차감을 못 막아 오버셀이 난다. 자명해서 실측 시연 없이 문서로 확정.
- 예상이 있는데도 측정하는 이유: ① 차이의 **크기**는 이론으로 안 나온다 ② 예상이 틀릴 실제 가능성(Redis 단일 스레드 CPU 한계 등) ③ "X를 예상했고, 측정값은 Y였고, 이유는 Z"라는 서사 자체가 목적.
- 실무 선례 — 같은 트레이드오프 탐색: 올리브영은 선착순 쿠폰 차감을 Lua 전면 원자화로 정확성 0건을 얻었으나 ~21% 느려져, 이중 카운터(요청 카운터 선차단 + 실제 카운터)로 ~8% 비용에 정합 100%로 전환했다 — [올리브영 테크블로그](https://oliveyoung.tech/2025-12-15/fcfs-coupon/).

## 2. 전략 교체 구조

경합 지점이 항상 한 행이라, **잠금 방식만 바꿔 끼우고 똑같은 테스트를 다시 돌린다**. 차감 연산을 인터페이스로 추상화하고 3구현을 갈아 끼운다.

```
interface HotDealStockDeductor {
  void deduct(Long hotDealId, int quantity);    // 실패 시 DomainException(SOLD_OUT / CONCURRENT_UPDATE_CONFLICT)
  void restore(Long hotDealId, int quantity);   // 만료 복원 — 같은 행 연산이라 전략에 묶음(부하 대상은 아님)
}
```

| 전략 | 차감 동작 | 실패 신호 | 차감 위치 |
|---|---|---|---|
| 낙관락(@Version) | `findByHotDealId` → 엔티티 `deduct()` → 커밋 시 버전 비교 | 버전 충돌 → `CONCURRENT_UPDATE_CONFLICT`(재시도) / 잔여 부족 → `SOLD_OUT` | DB (읽고 씀) |
| 원자적 조건부 UPDATE | `UPDATE … SET remaining = remaining − :qty WHERE hot_deal_id = :id AND remaining >= :qty` 한 문장 | 영향 행 수 0 → `SOLD_OUT`(충돌·재시도 개념 없음) | DB (읽지 않고 씀) |
| Redis 원자(+Lua) | Redis 키(잔여)에 Lua 스크립트로 원자 차감 후 DB 정합 보정 | Lua 반환값 < 0 → `SOLD_OUT` | Redis(원본) → DB(보정) |

- **선택 방식**: `stock.deduct.strategy = optimistic | conditional | redis` + `@ConditionalOnProperty`로 빈 하나만 활성. 프로퍼티만 바꿔 재기동하고 **같은 k6 시나리오를 재실행** — 방식 차이만 순수 비교.
- **끼움 지점**: `HotDealStockService.deduct/restore`가 주입된 `HotDealStockDeductor`에 위임. 비경합 연산(create·조회)은 공통.
- **`@Version` 칼럼**: 측정 기간엔 전략 무관 공통 유지 → 운영 전략 확정 후 낙관락 전략·`version` 칼럼 제거(결과는 본 문서 표에 보존, 코드 재현은 git 히스토리).

## 3. k6 워크로드

- **시나리오**: 선착순 폭주 — 동시 다수 요청이 재고 적은 핫딜 하나에 `POST /api/orders {productId}`. 정확성(오버셀 0)과 성능(성공 처리량)을 함께 본다.
- **부하 모델**: k6 `shared-iterations` — 가상 사용자 N명이 총 N건을 나눠 처리한다(계정당 1주문이라 사용자 수 = 주문 수). 도착률을 입력으로 주는 방식이 아니라 **처리율이 결과로 나오는** 구성이라, 방식 간 비교는 "같은 인원이 같은 건수를 소화하는 데 걸린 시간"으로 읽는다.
- **부하 매트릭스**: 도착률 × 재고(저경합 100·재고10 / 고경합 1000·재고2000 / 품절 1000·재고10). 각 칸을 3방식 모두 측정.
- **데이터 셋업**: 가상 사용자(VU)마다 다른 계정 토큰(계정당 1활성주문 유니크를 충족해야 차감까지 도달). 핫딜·`ProductStock`·`HotDealStock`은 측정 전 시드.
- **단계**: warm-up(캐시·커넥션 풀 예열) → 측정 → 종료 후 **정합 검증**(DB에서 오버셀 0 단언).

## 5. 측정 스택 배선

```
k6(부하 생성) ──→ 앱(/actuator/prometheus 노출) ──→ Prometheus(스크랩) ──→ Grafana(통합 대시보드)
```

- 부하 곡선(k6)과 서버 지표(풀 포화·충돌)를 **같은 시간축**에 겹쳐 본다 — "RPS가 이만큼일 때 풀이 마르고 충돌이 튄다"가 한눈에.
- 재현: `bash k6/benchmark/run.sh`(단일) · `bash k6/benchmark/run-multi.sh`(1 vs 3 인스턴스) — 일회용 격리 스택으로 전략 순회 + 오버셀 검증 자동 ([k6/README.md](../../k6/README.md)).

## 6. 결과 ① — 측정 오염 발견이 결론을 바꿨다 (단일 인스턴스)

![측정 환경이 결론을 바꿨다 — 호스트 Redis 우위가 격리서 소멸](../design/images/benchmark-measurement-pollution.svg)

호스트 측정(SQL 로그 on·공유 DB)에선 조건부 2.25s vs redis 1.44s 로 **redis 가 앞서는 것처럼** 보였다. 원인은 조건부만 겪는 SQL DEBUG 로깅 오염 — 격리 스택(로그 off·tmpfs DB) 재측정에서 조건부가 **1.37s 로 급락**해 동률이 됐다. 조건부는 차감이 DB UPDATE 라 로깅·부하에 민감하고 redis 는 메모리라 둔감했던 것. **"측정 환경이 결론을 바꾼다"가 이 벤치마크의 핵심 교훈.**

| 구간 (격리 환경) | 조건부 | redis | 낙관락 |
|---|---|---|---|
| 저경합 100·재고10 (p95) | **266ms** | 344ms | 382ms |
| 고경합 1000·재고2000 (p95) | **1.37s** | 1.48s | 1.44s · **성공 163/1000 탈락** |
| 품절 1000·재고10 (정확성) | 정확히 10 | 정확히 10 | 정확히 10 |

전 구간 **오버셀 0 · 거짓 성공 0 · 5xx 0%**. 낙관락은 재시도 없는 버전 충돌로 성공 163/1000 — 정확하나 비실용(탈락).

## 7. 결과 ② — 스케일아웃은 재고 병목을 못 푼다 (다중 인스턴스 1 vs 3 · 2026-07-24)

앞 측정은 앱 1인스턴스다. 배포 전제가 서버 여러 대이므로, 다중 인스턴스에서만 드러나는 것을 따로 측정했다.

### 구성

```
k6 → nginx(LB, 18080) → 앱 컨테이너 ×1 또는 ×3 → MySQL 1 + Redis 1 (tmpfs)
```

- [docker-compose.multi.yml](../../k6/benchmark/docker-compose.multi.yml) — app1~3 + nginx 라운드로빈, 단일 스택과 격리. [run-multi.sh](../../k6/benchmark/run-multi.sh) — 전략 × 인스턴스 수 순회 + 오버셀 검증 + raw 로그 보존.
- **공정성**: 인스턴스 1도 nginx 를 경유시켜 **앱 대수만 변수**로 뒀다(LB 홉 유무가 섞이지 않도록). 앱 호스트 포트(18081~3)는 부하용이 아니라 인스턴스별 관측용.
- 측정 오염을 막으려 만료·해소 스케줄러는 끄고 돌린다(스케줄러 중복 실행 검증은 이 측정 범위 밖).

### 정확성 — 인스턴스 수와 무관 (깨끗한 실측)

![인스턴스 1→3: 조건부는 락 대기 8.8배, 락을 안 쓰는 Redis도 1.8배 악화](../design/images/benchmark-multi-instance.svg)

재고 10 < 인원 1,000 품절 경합에서 **앱 3대에서도 성공 정확히 10 · 초과 판매 0**(조건부·redis 둘 다). "차감의 최종 직렬화가 DB(또는 Redis)에 있으니 앱이 몇 대든 정확성은 같다"가 논리적 추론에서 **실측**으로 올라섰다. 이 관측은 자원 경합과 무관해 로컬에서도 신뢰할 수 있다.

### 처리량·지연 — 앱을 늘리면 둘 다 나빠진다

부하를 VU 1,000 · 1,000건으로 고정하고 앱 대수만 바꿨다(재고 = VU × 2로 전원 차감).

| 전략 | 앱 | 주문 API p95 (`http_req_duration`) | 처리율 | 행 락 대기 횟수 | 행 락 대기 누적 |
|---|:--:|---|---|---|---|
| 원자적 조건부 UPDATE | 1 | 1.44s | 7.14건/초 | 985회 | 5,220ms |
| 원자적 조건부 UPDATE | 3 | **2.52s** | 12.43건/초 | 999회 | **45,776ms** |
| Redis + Lua | 1 | 1.10s | 13.75건/초 | 0 | 0 |
| Redis + Lua | 3 | **1.99s** | 12.54건/초 | 0 | 0 |

- 앱 1대에서는 Redis가 처리율 1.9배(13.75 vs 7.14)로 앞선다. 앱 3대에서는 둘이 수렴한다(12.54 vs 12.43).
- 지연은 두 전략 모두 나빠졌다. 조건부 1.75배, Redis 1.8배.

### 원인을 둘로 분리했다

당초 가설은 "재고 한 행의 락 경합이 병목"이었다. **락 대기 누적을 기록하자 절반만 맞았다.**

**① 재고 행 락 경합 — 실재한다**

- 조건부 UPDATE의 락 대기 누적이 5.2초 → **45.8초로 8.8배** 늘었다
- 대기 횟수는 985 → 999회로 거의 같다. 요청 수가 동일하니 당연하고, **건당 대기 시간이 5.3ms → 45.8ms로 8.6배** 길어진 것이 악화의 실체다

**② 락과 무관한 요인 — 이것도 실재한다**

- Redis는 재고 행을 수정하지 않아 락 대기가 정확히 0인데도 1.10초 → 1.99초로 1.8배 느려졌다
- 한 머신에서 앱 셋 · DB · Redis · nginx · k6 가 자원을 나눠 쓴 몫이다

**③ Redis가 대조군이 되어 둘이 갈린다**

- 앱 3대에서 조건부 2.52초 − Redis 1.99초 = **0.53초가 락 경합이 추가로 만든 몫**
- 나머지 악화는 두 전략이 함께 겪었으므로 락 밖 요인이다

### 관측 지표를 잘못 고르면 병목을 놓친다

`conn-conditional-i3-vu1000.log` 34개 스냅샷(2초 간격):

| 지표 | 값 |
|---|---|
| `Innodb_row_lock_current_waits` (그 순간 대기 중인 수) | **0** (34/34) |
| DB `Threads_running` | 2 (32회) · 3 (2회) |
| 앱이 사용 중인 커넥션 합산 | 대부분 0~2, 최고 30이 1회 |

**순간을 찍는 지표로는 락 경합이 전혀 보이지 않았다.** 누적값(`Innodb_row_lock_time`)을 부하 전후 델타로 재고서야 45.8초가 드러났다. 대기가 짧고 잦으면 샘플링이 그 순간을 놓친다 — 이 프로젝트가 처음에 "DB는 한가했다"고 잘못 읽은 이유다.

인프라로 푸는 접근(RDS Proxy 커넥션 다중화 · 읽기 복제본)은 쓰기 경로라 무관하다. 락 경합이 확인된 이상 해법은 재고를 여러 행으로 분산하거나 Redis로 옮기는 것인데, 앱 3대에서 두 전략의 처리율이 수렴한 것을 보면 **Redis 전환만으로 얻는 이득도 환경에 따라 제한적**이다.

### redis 승격을 미룬 이유

- redis 이점은 속도만이 아니라 **격리**(재고 부하가 같은 DB 의 주문·정산으로 안 번짐 — [여기어때 사례](https://techblog.gccompany.co.kr/redis-kafka%EB%A5%BC-%ED%99%9C%EC%9A%A9%ED%95%9C-%EC%84%A0%EC%B0%A9%EC%88%9C-%EC%BF%A0%ED%8F%B0-%EC%9D%B4%EB%B2%A4%ED%8A%B8-%EA%B0%9C%EB%B0%9C%EA%B8%B0-feat-%EB%84%A4%EA%B3%A0%EC%99%95-ec6682e39731)). 대가는 정합·유실 관리.
- **"대형사가 쓰니까"는 근거가 아니다** — [Shopify(2026)](https://shopify.engineering/scaling-inventory-reservations)는 오히려 redis 를 걷어내고 MySQL `SKIP LOCKED` + 재고 1단위 1행으로 고처리량을 냈다. 본질은 'DB냐 redis냐'가 아니라 **'단일 행이냐 분산이냐'**.
- 현 redis 구현은 재고를 Redis 에만 두는 벤치마크용 반쪽이라, 채택하려면 정합(DB 싱크·유실 복구) 완성이 전제. i3 격차의 원인도 미분리(아래 한계)라 **"격차를 봤지만 이걸로 운영을 성급히 바꾸지 않는다"** 가 이 측정의 결론.

## 8. SLA 도출

주문 `POST /api/orders` — 실측 분포에 여유를 붙여 올림([Google SRE Workbook](https://sre.google/workbook/slo-document/) 절차):

| 구간 | 실측 p95 | SLA |
|---|---|---|
| 저경합 (동시 100·재고 10) | 266ms | **≤ 500ms** |
| 폭주 (동시 1,000) | 1.37s | **≤ 2s** |

- 부하 모델: 동시 1,000 VU = 오픈 순간 구매 버튼 동시 클릭 스파이크(실측 역산 ~700 RPS, 일반 동시접속자 환산 ≈ 2만~6만, Little's Law).
- 오버셀 0·거짓 성공 0 은 SLA 가 아니라 절대 불변식(협상 대상 아님). p50 은 측정 안 함(꼬리 지연이 선착순의 관심사).
- SLA 와 실사용자 경험의 상관은 미검증 — 운영 데이터로 조정 전제.

## 9. 한계 — 무엇을 못 밝혔나 (정직한 경계)

- **앱 3대에서 느려진 원인을 가리지 못했다.** 재고 한 행의 순차 처리인지, 한 머신에서 앱 셋과 DB·Redis·부하 도구가 자원을 다툰 것인지 판별할 데이터가 없다. 행 락 대기가 0으로만 관측돼 전자를 뒷받침할 근거가 오히려 부족하다.
- **락 대기 시간이 결과 파일에 남지 않았다.** `run-multi.sh`가 `Innodb_row_lock_time` 델타를 수집하지만 stdout 요약으로만 나가, 이전 문서가 인용하던 수치를 재현·검증할 수 없다. 이 값을 파일로 기록하는 것이 원인 규명의 첫 단계다.
- **tmpfs 환경**이라 실제 운영의 커밋 저장(디스크) 비용이 빠져 있다.
- **단일 측정**이라 절대 수치엔 노이즈가 있다. 신뢰하는 건 방향(앱을 늘렸을 때 응답이 나빠진다)이지 값이 아니다.
- 후속: ① 락 대기 시간 기록 후 재측정(원인 규명 — 남은 것 중 가장 큼) ② 부하 도구·앱·DB를 다른 기기에 두는 측정(장비 여건상 미실시) ③ SLA를 실제로 깨는 지점의 인원 곡선 스윕 ④ 셋째 전략 — MySQL `SKIP LOCKED` + 재고 단위별 행(Shopify 방식), 미측정.
