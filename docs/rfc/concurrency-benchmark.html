재고 동시성 벤치마크 — 측정과 해석

선착순 구매가 재고 한 행에 몰릴 때 어느 차감 방식을 쓸지, 세 가지를 같은 조건에서 재고 고른 과정이다. 결정 자체는 재고 동시성 ADR에 있고, 이 문서는 그 근거가 되는 측정 설계와 실측을 보존한다.

1. 무엇을 재고 무엇을 재지 않았나

측정 대상

  • 구매 경로에서 HotDealStock 한 행을 차감하는 경합 (POST /api/orders)
  • 수천 요청이 같은 잔여 수량을 동시에 줄이는 지점이다

측정한 세 가지

  • 낙관적 락(@Version) — 나쁜 기준선
  • 원자적 조건부 UPDATE — 가장 단순한 DB 방식
  • Redis + Lua — 고성능 대안

재지 않은 두 가지

  • 비관적 락과 분산 락(Redisson)은 결과가 이론으로 예측돼 측정 이득이 낮다고 보았다
  • synchronized 같은 JVM 락은 후보가 아니다. 자기 프로세스 안에서만 직렬화하므로 서버 여러 대에서는 초과 판매를 못 막는다

부하를 주지 않은 곳

  • 토스 결제 승인 구간은 외부 샌드박스라 호출량 제한과 차단 위험이 있다
  • 부하는 주문 생성 경로에만 주고, 결제는 테스트 대역으로 대체했다

측정 전에 세운 예상

벤치마크는 쏘고 보는 것이 아니라 예상을 검증하는 것이다.

방식 동작 한 행에 몰릴 때의 예상
낙관적 락(@Version) 락 없이 진행하고 저장 시점에 버전을 비교 충돌률이 높아 대부분 실패 → 성공 처리량 최저
비관적 락(FOR UPDATE) 행을 잠그고 줄을 세움 정확하지만 대기 내내 DB 커넥션을 쥔다 → 커넥션 풀이 먼저 마른다
Redis + Lua 인메모리·단일 스레드라 원자 차감 처리량 최고 예상. 단 재고를 Redis에서 관리하게 되어 DB 동기화가 따라온다
분산 락(Redisson) Redis 락을 서버들이 공유해 직렬화 락을 얻고 푸는 왕복 비용 → Redis 직접 차감보다 느림
원자적 조건부 UPDATE WHERE remaining >= :qty 한 문장, 영향 행 수로 판단 재시도도 긴 커넥션 점유도 없음 → 단순하고 정확할 것

예상이 있는데도 측정한 이유는 셋이다.

  • 차이의 크기는 이론으로 나오지 않는다. 숫자가 있어야 운영안을 고른다
  • 예상이 빗나갈 가능성이 실재한다. Redis는 단일 스레드라 고부하에서 예상만큼 안 빠를 수 있다
  • "무엇을 예상했고, 얼마가 나왔고, 왜 그런가"를 남기는 것 자체가 목적이다

실무에도 같은 트레이드오프 탐색이 있다. 올리브영은 선착순 쿠폰 차감을 Lua로 전면 원자화해 정확성을 얻었으나 약 21% 느려졌고, 이중 카운터로 전환해 약 8% 비용에 정합을 지켰다 — 올리브영 테크블로그.

2. 어떻게 재는가

무엇으로 재는가 — k6

도구를 고른 기준이 일반 부하 테스트와 다르다. 처리량 한계를 찾는 것이 아니라 세 방식을 같은 조건으로 반복 측정해 비교하는 것이라, 재현성과 서버 내부 지표가 먼저다.

  • 보려는 지표가 클라이언트가 아니라 앱 서버에 있다. 커넥션 풀 포화·락 대기·버전 충돌은 부하 도구가 모른다
  • 그래서 부하 곡선과 서버 지표를 같은 시간축에 겹쳐 봐야 "요청이 이만큼일 때 풀이 마른다"가 드러난다
도구 부하 제어 서버 지표 통합 시나리오 관리
k6 정확한 도착률 모델 Prometheus·Grafana 한 생태계 JS 파일
Gatling 동급 자체 리포트라 서버 지표와 분리 Scala
JMeter 스레드 모델이라 덜 정밀 플러그인 의존 XML

가운데 열이 갈랐다. Gatling 은 부하 제어가 동급이고 JVM 이라 익숙하지만, 리포트가 따로 놀아 두 곡선을 겹칠 수 없다. JMeter 는 도착률 정밀도와 버전 관리 둘 다에서 밀린다.

  • 측정 스택은 k6(부하) + Micrometer→Prometheus(앱 지표) + Grafana(대시보드)다. k6 결과도 Prometheus 로 내보내 한 대시보드에 겹친다
  • JS 를 쓰는 것이 유일한 이질점인데 측정 코드에만 갇혀 비용이 작다
  • 도구를 바꾸는 비용은 시나리오 재작성뿐이다

전략 교체 구조

경합 지점이 항상 한 행이므로, 차감 방식만 교체하고 같은 부하를 다시 준다.

public interface HotDealStockService {
  void createForHotDeal(Long hotDealId, int quantity);
  void deduct(Long hotDealId, int quantity);   // 실패 시 DomainException(SOLD_OUT)
  void restore(Long hotDealId, int quantity);  // 만료 복원 — 같은 행 연산이라 전략에 묶었다
}
전략 차감 동작 실패 신호 재고를 어디서 관리하나
낙관적 락(@Version) 조회 → 엔티티 차감 → 커밋 시 버전 비교 버전 충돌 또는 잔여 부족 DB (읽고 씀)
원자적 조건부 UPDATE UPDATE … SET remaining = remaining − :qty WHERE hot_deal_id = :id AND remaining >= :qty 영향 행 없음 → SOLD_OUT DB (읽지 않고 씀)
Redis + Lua Redis 키에 Lua 스크립트로 원자 차감 스크립트 반환값 Redis
  • stock.deduct.strategy 설정값과 @ConditionalOnProperty로 구현 하나만 활성화한다
  • 설정만 바꿔 재기동하고 같은 k6 시나리오를 재실행하므로 방식 차이만 남는다
  • 낙관적 락 구현과 version 컬럼은 운영 전략 확정 후 제거했다. 측정 결과는 이 문서에 남고, 코드는 git 히스토리에 있다

워크로드

  • 시나리오 : 재고가 적은 핫딜 하나에 다수가 동시에 POST /api/orders를 보낸다
  • 부하 모델 : k6 shared-iterations
    • 가상 사용자 N명이 총 N건을 나눠 처리한다. 계정당 1주문 제한이 있어 사용자 수가 곧 주문 수다
    • 도착률을 입력으로 주는 방식이 아니라 처리율이 결과로 나오는 구성이다
    • 그래서 방식 간 비교는 "같은 인원이 같은 건수를 소화하는 데 걸린 시간"으로 읽는다
  • 매트릭스 : 인원을 100·250·500·1,000·2,000·3,000으로 올리며 앱 1대와 3대를 각각 잰다(재고는 인원의 두 배로 두어 전원이 살 수 있게 한다). 품절 경합은 재고 10에 1,000명으로 따로 잰다
  • 데이터 : 가상 사용자마다 다른 계정 토큰을 쓴다. 계정당 1활성주문 유니크를 통과해야 차감까지 도달한다
  • 절차 : 예열 → 측정 → 종료 후 DB에서 초과 판매 0건을 단언
    • 계정 발급은 측정 밖에서 끝낸다. k6의 setup()에 두면 계정 생성 시간이 k6 총 실행 시간에 들어가고, iterations/s의 분모가 그 총 실행 시간이라 처리율이 주문이 아니라 계정 생성 속도를 재게 된다(3절)
    • 예열 회차는 값을 버린다. 앱을 재기동한 직후 첫 회차는 뒤 회차보다 몇 배 느려서, 그대로 두면 회차 편차가 경합이 아니라 JIT·버퍼풀 워밍업을 잰다
    • 같은 조건을 여러 번 친다. 한 번으로는 값을 믿을 수 없다는 것이 이번 측정의 결론 중 하나다(6절)

지표

출처 지표 무엇을 보나

재현

  • bash k6/benchmark/run-multi.sh — 다중 인스턴스. MODE로 세 가지를 돈다 (다중 인스턴스 실행 스크립트 · 다중 인스턴스 구성)
MODE 무엇을 재나

mix 주문 폭주와 무관한 조회를 같은 시간에 흘려 재고 부하가 번지는지 본다
  • 일회용 컨테이너로 전략을 순회하고 초과 판매 검증까지 자동으로 돈다 (k6 실행 안내)
  • 인스턴스 1도 nginx를 경유시켜 앱 대수만 변수로 두었다. 앱 포트를 따로 여는 것은 부하용이 아니라 관측용이다
  • 측정 오염을 막으려 만료·해소 스케줄러는 끄고 돌린다
  • 결과는 측정 로그에 그대로 남는다. 이 문서의 수치는 전부 거기서 옮긴 것이고, 재실행하면 덮인다 — 옛 회차는 git이 갖는다
    • 회차별 원값은 모드별 raw.tsv 한 줄씩, 그것을 접은 것이 summary-{모드}.md다. 회차별 k6 출력 원문은 수백 개가 되고 그 수치가 전부 raw.tsv에 있으므로 저장소에 두지 않는다

3. 결론을 바꾼 것은 두 번 다 측정 쪽이었다

한 번은 측정 환경이, 한 번은 지표 선택이 결론을 바꿨다. 전략을 바꿔서가 아니다.

환경 — 로깅과 저장장치

호스트에서 잰 첫 결과는 조건부 2.25초, Redis 1.44초로 Redis가 앞서는 것처럼 보였다.

  • 원인은 조건부만 겪던 SQL 디버그 로깅이었다
  • 격리 스택(로그 차단·tmpfs DB)에서 재측정하자 조건부가 1.37초로 떨어져 동률이 됐다
  • 조건부는 차감이 DB UPDATE라 로깅에 민감하고, Redis는 메모리라 둔감했다
구간 (격리 환경) 조건부 Redis 낙관적 락
저경합 100명·재고 10 (p95) 266ms 344ms 382ms
고경합 1,000명·재고 2,000 (p95) 1.37초 1.48초 1.44초 · 성공 163/1000
품절 경합 1,000명·재고 10 정확히 10 정확히 10 정확히 10

이 표는 앱 1대·단일 실행의 첫 측정이고, 세 전략을 한자리에서 비교한 유일한 기록이다. 낙관적 락 구현은 이 측정 뒤 코드에서 제거돼 다시 잴 수 없다(2절). 조건부와 Redis의 현행 값은 4절이고, 여러 회차로 다시 재서 값이 다르다.

  • 전 구간 초과 판매 0건 · 거짓 성공 0건 · 5xx 0%
  • 낙관적 락은 재시도 없이 버전 충돌로 끝나 1,000건 중 163건만 성공했다. 정확하지만 실용성이 없어 탈락

지연은 셋이 비슷한데 성공 건수에서 갈린다. 재고가 인원보다 많아 원래 전원이 살 수 있는 조건인데도 낙관적 락만 837명을 떨어뜨렸다.

지표 — 처리율이 재던 것은 주문이 아니었다

이 문서는 한동안 "앱 1대에서 Redis가 처리율 1.9배로 앞선다"고 적고 있었다. 그 1.9배는 계정을 만드는 시간이었다.

  • k6의 iterations/s는 분모가 총 실행 시간인데, 계정 1,000개를 만드는 setup()이 거기 들어가 있었다. 1,000명 회차가 140초 걸렸고 그중 실제 주문 부하는 2초였다
  • 게다가 계정이 DB에 남으므로, 뒤에 도는 전략은 회원가입이 중복 거절로 즉시 떨어졌다. 먼저 도는 쪽만 생성 비용을 뒤집어쓰는 실행 순서 효과였고, 순서는 항상 조건부가 먼저였다
  • 계정 발급을 측정 밖으로 빼자 같은 구간의 처리율이 세 자릿수로 올라왔다. 지연 p95는 주문 요청만 재는 별도 지표였으므로 영향이 없었다

측정 환경도 지표도 결론을 바꾼다. 전자는 조건부만 겪던 로깅이었고, 후자는 두 전략에 다르게 작용하는 사전 준비였다. 둘 다 전략의 성질이 아니었는데 전략의 차이로 읽혔다.

4. 인원을 늘렸을 때 — 무엇이 재현되고 무엇이 안 되나

배포 전제가 서버 여러 대이므로 앱 1대와 3대를 나란히 두고, 인원을 100에서 3,000까지 올리며 각 지점을 6회씩 쳤다. 주문 API 지연 p95의 중앙값이다.

인원 조건부 앱 1 조건부 앱 3 Redis 앱 1 Redis 앱 3
100 70ms 124ms 94ms 129ms
1,000 423ms 1.40초 494ms 808ms
2,000 1.00초 3.53초 1.05초 1.79초
3,000 2.11초 7.03초 2.07초 2.60초

전 구간과 회차별 편차·처리율·락 대기는 스윕 측정 요약에 있다.

앱을 늘리면 전 구간에서 느려진다. 한 머신에서 앱 셋과 DB·Redis·nginx·k6가 자원을 나눠 쓴 몫이다. 인원 100처럼 경합이 거의 없는 지점에서도 1.4~1.8배 벌어지므로 재고 경합 때문이 아니다.

인원 2,000부터는 요청이 서버에 닿지 못하기 시작한다

지연을 논하기 전에 걸리는 것이 있다. 인원 1,000까지는 전 조합에서 성공 건수가 인원과 같고 전송 실패가 0인데, 2,000부터 회차에 따라 요청이 유실된다.

인원 전송 실패 (회차 간 최소~최대)
~1,000 0 (Redis 앱 3만 0~11)
2,000 0~379
3,000 0~1,001

http_req_duration의 최솟값이 0초로 찍힌다 — 응답을 받은 것이 아니라 연결 자체가 성립하지 않았다는 뜻이다. 200도 409도 아니므로 경합에 밀린 것이 아니라 서버에 닿지 못한 것이다.

이것이 두 가지를 뜻한다.

  • 인원 2,000 이상의 p95는 완주한 요청만의 값이라 낙관적으로 편향돼 있다. 떨어져 나간 요청은 지연에 잡히지 않는다
  • 이 유실이 앱의 한계인지 측정 머신의 한계인지 가릴 수 없다. 부하 도구와 서버가 같은 기기에 있다(6절)

정확성은 인원에도 앱 대수에도 무관하다

정확성은 인원에도 앱 대수에도 무관하다.

재고 10에 1,000명이 몰리는 품절 경합에서 6회 모두 정확히 10건 성공, 초과 판매 0건이다. 두 전략이 같고, 인원을 3,000까지 올린 전 구간에서도 초과 판매는 0이다. 차감의 최종 직렬화가 DB나 Redis에 있으니 앱이 몇 대든 같다는 추론이 실측으로 올라섰고, 이 관측은 자원 경합과 무관해 로컬에서도 신뢰할 수 있다.

세 번의 실행에서 흔들리지 않은 것은 이것뿐이다.

재고 행 락 경합 — 실재하고, 앱을 늘리면 커진다

앱 1 앱 3
조건부, 인원 1,000 2.42초 32.60초
조건부, 인원 3,000 11.07초 204.35초
Redis, 전 구간 0 0
  • 대기 횟수는 요청 수와 거의 같다(인원 3,000에 2,978회). 요청마다 한 번씩 줄을 선다는 뜻이라 당연하다
  • 악화의 실체는 건당 대기 시간이다. 앱 1대에서 3대로 가면 같은 횟수에 누적이 13배 이상 늘어난다
  • Redis는 재고 행을 수정하지 않아 정확히 0이다. 이 대비는 세 실행에서 모두 같았다

커넥션 풀이 병목이다 — 그리고 순간값은 그것을 숨긴다

HikariCP는 기본 설정이라 앱당 10, 앱 3대면 상한 30이다. 부하 중 hikaricp_connections_active를 찍으면 조건부 30(상한), Redis 10(3분의 1)이 나온다.

이 순간값을 보고 "Redis는 풀에 여유가 있으니 풀이 병목이 아니다"라고 읽으면 틀린다. 획득 대기를 부하 전후 누적 델타로 재면 이렇다(인원 1,000·앱 3대, 6회 평균).

전략 커넥션 획득 대기 누적 사용 중 커넥션(순간값)
조건부 481초 30
Redis 258초 10

Redis도 258초를 기다린다. 자리가 남아 보이는 순간값과 정반대다. 이것은 이 문서가 락 경합에서 겪은 것과 같은 함정이다 — 대기가 짧고 잦으면 순간을 찍는 지표는 그것을 못 본다. 락 대기를 누적으로 재서 찾아냈으면서 커넥션은 순간값으로 판정할 뻔했다.

병목은 두 층으로 갈린다.

층 정체 Redis로 해소되나
위 락 대기가 커넥션 점유 시간을 늘린다 해소된다 — 481초에서 258초로, 46%
아래 풀 30개를 동시 요청 1,000건이 나눠 쓴다 안 된다 — 남은 258초가 이것이다

아래층은 락과 무관하다. 재고 차감을 Redis로 보내도 주문 하나가 사용자·상품·핫딜 조회와 주문 INSERT로 DB를 네 번 왕복하고, 그동안 커넥션을 쥔다.

풀 크기는 기본값 그대로 두고 쟀다. 아래층은 재고 전략이 아니라 풀 설정으로 건드리는 것이고, 이 벤치마크는 그것을 시도해 보지 않았다(6절).

관측 지표를 잘못 고르면 병목을 놓친다

같은 부하 구간에서 순간을 찍는 지표는 이렇게 나왔다.

지표 값
Innodb_row_lock_current_waits (그 순간 대기 중인 수) 0 (전 스냅샷)
DB Threads_running 2

순간을 찍는 지표로는 락 경합이 전혀 보이지 않는다. 같은 회차의 누적 델타는 204초였다. 대기가 짧고 잦으면 샘플링이 그 순간을 놓친다 — 이 프로젝트가 한때 "DB는 한가했다"고 잘못 읽은 이유다.

계정 발급을 측정 밖으로 뺀 뒤로 부하 구간이 몇 초로 짧아져서 스냅샷은 회차당 네 개뿐이다. 네 번 다 0이고 누적은 204초라는 대비는 그것으로도 성립한다.

두 전략의 우열은 이 환경에서 말할 수 없다

같은 격자를 세 번 돌렸는데 인원 2,000 이상에서 결과가 뒤집힌다. 인원 3,000·앱 3대의 p95 중앙값이다.

실행 조건부 Redis 어느 쪽이 빠른가
1회차 실행 3.75초 13.54초 조건부
2회차 실행 8.80초 9.76초 비슷
3회차 실행 (n=6) 7.03초 2.60초 Redis

한 실행 안의 회차 편차도 같은 크기다. 인원 2,000·앱 3대에서 Redis의 회차 범위가 773ms에서 59.95초까지 벌어진 회차 묶음이 있었다.

인원 1,000 이하에서는 값이 안정적이지만, 이번에는 두 전략의 범위가 서로 겹친다. 앱 3대·인원 1,000에서 조건부 692ms~2.11초, Redis 328ms~2.07초다.

그래서 이 문서는 두 전략의 지연 우열을 결론으로 쓰지 않는다. 락 대기와 커넥션 점유처럼 세 실행에서 일관된 관측만 근거로 쓴다.

저장장치를 디스크로 바꾸면 양쪽이 함께 나빠진다

tmpfs는 커밋 저장 비용을 통째로 빼먹는다. MySQL 데이터 디렉터리를 디스크에 두고 같은 부하(인원 1,000·앱 3대)를 6회 다시 쳤다.

전략 tmpfs 디스크 조건부 락 대기 누적
조건부 1.40초 3.56초 32.60초 → 96.90초
Redis 808ms 2.25초 0 → 0
  • 락 대기 누적이 3배로 는다. 커밋이 디스크에 닿는 동안 행 락을 더 오래 쥐기 때문이다. 예상한 방향이 그대로 나왔다
  • 다만 Redis도 2.8배 느려진다. 재고 차감은 DB 밖에서 끝나지만 주문 INSERT는 여전히 DB에 커밋된다. 디스크는 재고 경합만이 아니라 주문 경로 전체를 때린다
  • 순위는 바뀌지 않는다. 회차 범위가 조건부 2.90~4.98초, Redis 1.71~3.09초로 거의 겹치지 않아 디스크에서는 Redis가 빠르다고 말할 수 있다 — tmpfs에서는 겹쳐서 말할 수 없었던 것과 대비된다

격리는 이 구현에서 성립하지 않았다

"Redis의 이점은 속도만이 아니라 격리다 — 재고 부하가 같은 DB의 주문·정산으로 번지지 않는다"는 주장이 있다(여기어때 사례). 이 저장소에서 그것이 성립하는지 재봤다.

재고와 무관한 DB 읽기(GET /api/auth/me — users를 PK 단건 조회)를 같은 도착률로 흘리고, 주문 폭주를 겹칠 때와 안 겹칠 때를 6회씩 비교했다.

전략 조회만 주문 폭주와 동시 커넥션 획득 대기
조건부 16ms 1.76초 481초
Redis 13ms 964ms 258초

Redis가 조회를 45% 덜 밀리게 한다. 그리고 커넥션 획득 대기가 46% 줄었다. 두 감소율이 이렇게 맞아떨어지는 것이 인과를 가리킨다.

회차별로 보면 더 분명하다. 값이 회차마다 두 배 넘게 흔들리는데 두 지표가 함께 흔들린다.

조건부 Redis
가장 나쁜 회차 798초 → 조회 2,998ms 419초 → 조회 1,676ms
가장 좋은 회차 305초 → 조회 1,039ms 205초 → 조회 612ms

그래도 격리는 아니다. Redis에서도 조회가 무부하 13ms의 74배다. 남은 258초가 그 원인이고, 그것은 락과 무관하다 — 주문 하나가 사용자·상품·핫딜 조회와 주문 INSERT로 DB를 네 번 왕복하며 커넥션을 쥐기 때문이다.

자원 조건부 Redis
DB 왕복 5회 (조회 3 + 주문 INSERT + 재고 UPDATE) 4회
커넥션 점유 왕복 시간 + 락 대기 왕복 시간

Redis로 빠지는 것은 다섯 번 중 한 번이고, 그것이 조회 지연의 45%를 만들고 있었다. 나머지 55%는 남은 네 번이 만든다.

인용한 사례들은 재고 차감만 옮긴 것이 아니라 요청 경로 전체를 Redis에서 끝내고 DB 쓰기를 비동기로 미룬다. 그러면 주문 요청이 DB 커넥션을 아예 안 잡는다. 즉 격리의 조건은 이렇게 정리된다.

격리의 조건

Redis를 쓰면 격리되는 것이 아니라, 요청 경로에서 DB를 걷어내면 격리된다. Redis는 그 수단이지 조건이 아니다.

이 구현은 절반만 했고, 측정된 효과도 절반이다. 경합하는 한 행을 DB 밖으로 빼서 조회 영향을 45% 줄였지만, 주문 생성이 남아 74배는 그대로다.

Redis 쪽이 덜 무너지긴 하지만(958ms 대 1.37초) 회차 범위가 겹쳐(767ms~1.53초 대 952ms~2.55초) 우열로 쓰지 않는다.

  • 배경 부하의 지속 시간이 주문 구간보다 길어 조회 지연의 절대값은 희석돼 있다. 기준선 회차도 같은 지속 시간으로 돌렸으므로 두 회차의 차이는 유효하다
  • 배경 부하가 PK 단건 조회다. 실제 카탈로그 목록·검색과는 부하 성질이 다르다 — 조회 API가 생기면 그때 다시 잰다

그런데도 Redis로 옮기지 않은 이유

그런데도 Redis로 옮기지 않은 이유

  • 얻는 것은 분명하다 — 락 대기 0과 커넥션 여유. 조건부가 커넥션 풀을 상한까지 쓰는 부하에서 Redis는 3분의 1만 쓴다. 이것은 세 실행에서 일관된 실측이다
  • 그런데 그 여유가 지연으로 환산되지 않았다. 지연 우열은 실행마다 뒤집혀 결론이 안 서고, 격리는 이 구현에서 성립하지 않았다. 커넥션을 10만 쓰는 Redis에서도 무관한 조회가 똑같이 무너지므로 이 환경의 병목은 커넥션 풀이 아니다. 풀이 실제 병목인 환경(DB가 더 빠르거나 커넥션이 더 비싼 곳)에서는 이 이득이 살아날 수 있는데, 그것을 여기서 확인할 방법이 없다
  • 대가는 정합과 유실 관리다. 현재 구현은 재고를 Redis에만 두는 벤치마크용이라 채택하려면 DB 동기화부터 완성해야 한다
  • "대형사가 쓰니까"는 근거가 되지 않는다. Shopify(2026)는 오히려 Redis를 걷어내고 MySQL SKIP LOCKED와 재고 1단위 1행으로 고처리량을 냈다. 본질은 DB냐 Redis냐가 아니라 한 행이냐 분산이냐다
    • 락 대기가 앱 대수에 따라 13배로 커진다는 관측은 이 방향을 가리킨다. 경합하는 행을 쪼개면 그 대기가 어디로 가는지는 아직 재보지 않았다(6절)

5. SLA 도출

주문 생성 POST /api/orders — 격리 스택 실측 분포에 여유를 붙여 올렸다 (Google SRE Workbook 절차).

구간 실측 p95 중앙값 SLA
저경합 (동시 100명) 70~129ms ≤ 500ms
폭주 (동시 1,000명) 423ms~1.40초 ≤ 2초

목표선에는 전제가 붙는다 — 앱 3대까지, 저장장치는 tmpfs, 인원 1,000까지. 전제를 적지 않으면 어느 조건에서 유효한 약속인지 알 수 없고, 실제로 셋 중 둘을 벗어나면 깨진다.

어디서 깨지나

목표선 2초를 넘기기 시작하는 인원이다. 중앙값 기준이고, 전 구간은 스윕 측정 요약에 있다.

구성 통과하는 마지막 깨지는 첫
조건부 · 앱 1 2,000명 (1.00초) 3,000명 (2.11초)
조건부 · 앱 3 1,000명 (1.40초) 2,000명 (3.53초)
Redis · 앱 1 2,000명 (1.05초) 3,000명 (2.07초)
Redis · 앱 3 2,000명 (1.79초) 3,000명 (2.60초)
  • 앱을 늘리면 더 일찍 깨진다. 조건부는 앱 3대에서 한 단계 앞당겨진다
  • 다만 인원 2,000 이상의 값은 낙관 편향이다. 그 구간부터 요청이 유실되기 시작하는데 유실분은 지연에 안 잡힌다(4절). 깨지는 인원은 표보다 낮을 수 있다
  • 회차 편차가 커서 이 표의 경계는 한 칸 정도 흔들린다. 조건부 앱 3대·인원 1,000은 중앙값 1.40초인데 회차 상한이 2.11초로 목표선을 넘는다

운영 조건에서는 현재 목표선을 못 맞춘다

전제 중 tmpfs를 디스크로 바꾸면 인원 1,000·앱 3대에서 조건부가 3.56초다(4절). 목표선 2초의 1.8배다.

이것을 목표선을 늘려 해결하지 않는다. 실측이 나쁘면 목표선을 실측에 맞추는 것이 순환이 되기 때문이다. 지금 정직한 서술은 이것이다 — 목표선은 tmpfs 실측에서 도출됐고, 디스크가 끼는 실제 배포에서는 현재 구현이 그 선을 못 맞춘다. 재고 경합을 줄이는 작업(SKIP LOCKED 등, 6절)이 이 격차를 좁힐 후보다.

  • 동시 1,000명은 오픈 순간 구매 버튼을 함께 누르는 스파이크를 가정한다
  • 초과 판매 0건과 거짓 성공 0건은 SLA가 아니라 절대 불변식이다. 지연은 목표선이지만 정확성은 협상 대상이 아니다. 이 불변식은 세 번의 실행과 전 구간에서 한 번도 깨지지 않았다
  • p50은 재지 않았다. 선착순에서 관심사는 꼬리 지연이다
  • SLA와 실사용자 경험의 상관은 검증하지 않았다. 운영 데이터가 생기면 조정한다

6. 아직 못 밝힌 것

  • 같은 조건의 값이 재현되지 않는다. 이것이 이번 재측정의 가장 큰 소득이자 한계다. 회차를 6회로 늘리고 실행을 세 번 했는데, 인원 2,000 이상에서 두 전략의 우열이 실행마다 뒤집혔다(4절). 회차를 더 늘려도 좁혀지지 않는다 — 부하 도구와 서버가 한 기기에 있는 한 편차의 원인이 측정 대상 밖에 있기 때문이다
    • 처음에는 이것을 "단일 측정이라 노이즈가 있다"로 적고, 다회 측정으로 지울 수 있다고 봤다. 다회 측정이 실제로 한 일은 노이즈를 줄인 것이 아니라 그것이 결론을 못 낼 만큼 크다는 것을 보인 것이다
    • 인원 1,000 이하는 값이 안정적이다. 이 문서가 지연으로 무언가를 주장하는 곳은 그 구간뿐이다
  • 커넥션 풀 크기를 한 번도 건드리지 않았다. 전 측정이 HikariCP 기본값(앱당 10)에서 돌았다. 그런데 조회가 밀리는 원인의 상당 부분이 풀 획득 대기이고, 그중 락과 무관한 몫이 남아 있다(4절). 풀을 키우면 그 몫이 어떻게 되는지, 그때 병목이 DB로 옮겨가는지는 재지 않았다. 재고 전략을 바꾸는 것보다 훨씬 싼 수단이므로 먼저 재볼 후보다
  • 자원 경합의 몫을 정밀하게 나누지 못했다. 커넥션 획득 대기까지는 누적으로 갈라냈지만, 남은 지연이 앱 워커 스레드인지 CPU인지 네트워크인지는 모른다. Undertow는 Micrometer 스레드 풀 지표를 내지 않아(Tomcat의 tomcat.threads.*에 해당하는 것이 없다) 앱 안에서 볼 방법이 없고, 부하 도구·앱·DB를 각각 다른 기기에 두어야 나머지가 가려지는데 장비 여건상 확인하지 못했다
  • 요청 유실의 원인을 가리지 못했다. 인원 2,000부터 연결이 성립하지 않는 요청이 나오는데(4절), 이것이 앱의 한계인지 한 기기에 부하 도구까지 올린 측정 환경의 한계인지 구분할 방법이 지금 없다. 앞 항목과 같은 이유다
  • SKIP LOCKED + 재고 단위별 행(Shopify 방식)은 재보지 않았다. DB를 단일 진실로 유지하면서 한 행 경합만 없애는 접근이라 관심사고, 락 대기가 앱 대수에 따라 13배로 커진다는 관측이 이 방향을 가리킨다
  • 격리를 제대로 재려면 조회 API가 있어야 한다. 이번 배경 부하는 PK 단건 조회였다. 목록·검색처럼 DB를 실제로 무겁게 읽는 부하에서 재고 부하가 어떻게 번지는지는 그 API가 생긴 뒤에야 잰다
  • 가용성 목표선(SLO)을 세우지 않았고 알람도 붙이지 않았다. 월 몇 분 다운을 허용한다는 목표선은 다중 노드·실트래픽·에러 예산 소진 추적이 있어야 뜻이 생기고, 알람은 임계 초과를 받을 수신자가 있어야 산다. 단일 로컬 환경에서 숫자를 지어내면 그쪽이 더 거짓이다
    • 다중 노드에서 실트래픽을 받게 되면 그때 목표선을 정하고 알람 임계를 1:1 로 환산한다

7. 전략 구현 테스트 리스트

낙관적 락은 기존 동시성 통합 테스트가 차감 경합을 명세한다. 아래는 신규 전략 구현이 자라며 누적한 단건 행위 테스트다. 전략 간 성능 차이는 테스트가 아니라 벤치마크의 몫이다.

실물은 조건부 UPDATE 테스트 · Redis 전략 테스트 두 파일이고, 설정값이 실제로 구현을 가르는지는 전략 선택 테스트가 본다.

# 테스트 전략 시나리오 상태
1 conditionalDeductReducesRemaining 조건부 UPDATE 차감하면 잔여가 준다 통과
2 conditionalDeductRejectsWhenInsufficient 조건부 UPDATE 잔여가 부족하면 영향 행이 없어 SOLD_OUT, 잔여는 그대로 통과
3 conditionalRestoreIncreasesRemaining 조건부 UPDATE 복원하면 잔여가 는다 통과
4 conditionalDeductNoOversellUnderConcurrency 조건부 UPDATE 동시 100명·재고 10에서 정확히 10건 성공, 초과 판매 0건 통과
5 redisDeductReducesRemaining Redis + Lua 차감하면 Redis 잔여가 준다 통과
6 redisDeductRejectsWhenInsufficient Redis + Lua 잔여가 부족하면 스크립트 반환값으로 SOLD_OUT 통과
7 redisRestoreIncreasesRemaining Redis + Lua 복원하면 Redis 잔여가 는다 통과
8 redisDeductNoOversellUnderConcurrency Redis + Lua 동시 100명·재고 10에서 정확히 10건 성공, 초과 판매 0건 통과
