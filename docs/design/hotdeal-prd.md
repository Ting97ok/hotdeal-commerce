# 핫딜 선착순 이벤트 — 가설 PRD

> **가설 PRD** — 실측 데이터 없이 가정 위에 세운 PRD. 실무 PRD 형식을 따르되, 측정 불가한 사업 수치는 전부 **"가정"** 으로 라벨링한다.
> 기술 번역: [기술 가설](hotdeal-purchase-hypothesis.md) · 결정 근거: [ADR](../adr/README.md) · 데이터: [ERD](erd.md) · 실측 사례: [리서치](research-flash-sale.md)
> 20년차 PO 관점 리뷰(갭 10건) 반영: 2026-06-11 · 결제 실패·보정 정책 현행화(슬라이스4·Phase B1 반영): 2026-07-19

---

## 1. 배경 · 문제 정의

한정 수량을 파격가(100원딜·1,000원딜류)에 **선착순**으로 파는 특가 이벤트를 연다.

- **돈이 아니라 신뢰와 트래픽을 사는 장사다.** 미끼 상품이라 팔수록 손해일 수 있고, 그래서 "수량 한정"이 생명이다. 이벤트가 남기는 것은 매출이 아니라 "여기 핫딜은 진짜다"라는 신뢰와 정시 오픈에 모이는 트래픽.
- 운영 모델은 실측 사례를 따른다 — 정시 오픈(쿠팡 골드박스 매일 7시, 공식 채널 확인) · 한정 수량 선착순(카카오 선물하기) · 추가 물량은 진행 중 핫딜을 고치지 않고 **새 회차**로(카카오: 100개씩 3차례) — [리서치 9.5·10.1](research-flash-sale.md).
- 문제: 오픈 순간 트래픽이 한 점(핫딜 1개·재고 1줄)에 폭주한다 — 약속(선착순·한정수량·1인 구매 제한)을 폭주 속에서도 지키는 시스템이 이 이벤트의 성립 조건이다.

## 2. 목표 · 성공 지표

| 구분 | 지표 | 판정 방법 |
|---|---|---|
| 사업 (가정 — 측정 제외) | 정시 오픈 트래픽 형성 · "진짜 한정"이라는 신뢰 | 실사용자 부재로 **측정하지 않음을 명시** — 전환·재방문 같은 사업 KPI 는 본 프로젝트 범위 밖 |
| **시스템 검수 1** | 장부 일치 100% — `총수량 = 남은 재고 + 살아 있는 주문 수` · `결제 완료 주문 ↔ 승인 결제 1:1` | 검수 쿼리 (이벤트 종료 후·테스트 단언) |
| **시스템 검수 2** | 초과 판매(재고보다 많이 팔림) 0건 · 거짓 성공(성공 응답인데 주문 없음) 0건 | 동시성 테스트 + 검수 쿼리 |
| **시스템 검수 3** | 폭주 생존 — 피크 구간 구매 API 서버 오류(5xx) 0건 · 주문 생성 **폭주 p95 ≤ 2s / 평시 p95 ≤ 500ms**(실측 분포 기반 확정 — [동시성 벤치마크 8절](../rfc/concurrency-benchmark.md), 초안의 "p99 ≤ 500ms 가정"을 대체) · **동시에 호출되는 상품 조회 API p99 ≤ 200ms(가정) 유지**(핫딜 폭주가 다른 기능을 마비시키지 않음 — 고트래픽 조회 단계에서 측정) | k6 부하 테스트 — 구매 합격선은 벤치마크로 확정(2026-07-03), 조회 합격선은 기준선 측정 후 |

> **관측 최소판**: 검수 3의 SLO(p99 · 5xx 0건)는 알람 임계로 1:1 환산하고, 커넥션 풀 고갈 시 런북 한 장을 슬라이스 1~2 시점에 둔다 — 관측을 마지막(MoSCoW Should)으로만 미루지 않는다.

## 3. 전제 · 제약

| # | 전제 | 내용 |
|---|---|---|
| 1 | 구매 자격 | **구매·주문·결제 API 는 로그인 회원 전용**(JWT — 기구현 auth 사용). 핫딜·상품 **조회는 비로그인 허용** |
| 2 | 트래픽 가정 | 플래시세일은 서비스 규모와 무관하게 **오픈 순간에 수요가 집중**되는 행사다 — 가정은 이벤트 단위로 잡는다(거친 유도: 목표 MAU 10만 → 이벤트 참여 ~5% → 오픈 순간 집중 ≈ 동시 5,000명). **피크: 오픈 직후 60초간 동시 사용자 ~5,000명 · 초당 구매 시도 ~1,000건**. k6 시나리오와 비관적 락 대기 공식([재고 동시성 ADR](../adr/concurrency.md))의 공통 입력값, 3주차 첫 측정 후 갱신 |
| 3 | 운영 규모 가정 | **동시 진행 핫딜 1개 기준**(경합이 한 점에 집중되는 최악 케이스로 벤치마크), 운영 주기는 1일 1핫딜 가정 — 다중 핫딜은 행·키 추가로 일반화 |
| 4 | 결제 환경 | 토스페이먼츠 **테스트 모드** — 실거래 없음. **부하 테스트는 구매·만료 경로 한정, 결제 승인 구간은 테스트 대역(PaymentGatewayClient 가짜 구현)으로 대체** — 외부 샌드박스에 부하 전송 금지([결제 ADR 8절](../adr/payment.md)) |
| 5 | 운영 인력 | 관리자 1인 운영 — 등록·중단의 동시 조작 경합은 저빈도 수용 |
| 6 | 상품 재고 원본 | 상품은 실물·예약 재고를 `ProductStock`(상품 1:1, 가용=실물−예약)에 보관 — 핫딜 수량은 여기서 예약해 온다(허공 생성 아님). 초기 실물은 시드/픽스처, 운영 입고·다중 창고·재고 원장은 스코프 밖 ([재고 동시성 ADR](../adr/concurrency.md)) |

## 4. 사용자 시나리오

**구매자 — 해피패스**
7시 오픈 → 목록에서 핫딜 확인(특가·잔여 수량 보임) → "구매하기" → "주문이 접수됐습니다. 제한시간 내 결제해 주세요" → 토스 결제창 → 결제 → "구매가 확정되었습니다".

**구매자 — 실패 여정** (각 실패의 사용자 안내가 [기술 가설 7 거부 케이스](hotdeal-purchase-hypothesis.md)와 1:1 대응)

| 상황 | 사용자가 겪는 것 | 이후 |
|---|---|---|
| 매진 | "품절되었습니다" — 결제창까지 가지 않고 즉시 | 끝 (복원으로 재고가 살아나면 재시도 가능) |
| 폭주 경합에 밀림 | "주문이 몰려 처리하지 못했습니다 — 다시 시도해 주세요" | 재고가 남아 있으므로 재시도로 성공 가능 |
| 결제 제한시간 초과 | 주문 자동 취소 + 재고 복원 | 재구매 가능 (그 사이 매진될 수 있음 — 수용) |
| 결제수단 실패(한도 초과·카드 거절 등 확정 거절) | 결제 실패 안내 + **주문 즉시 취소·재고 방출** — 다시 사려면 새로 주문(그 사이 매진 가능 — 수용). 통신오류(요청이 토스에 닿지 못함)만 같은 주문 유지·재시도 가능 | 결과 미확정(타임아웃)은 "결제 확인 중" 표시 후 해소 스케줄러가 자동 확정 ([결제 ADR 5·6절](../adr/payment.md)) |
| 취소된 핫딜 | "판매가 중단된 핫딜입니다" — 구매·결제 승인 모두 거부 | 이미 결제 완료한 구매는 유효 |

**운영자 여정**
핫딜 등록(검증 통과: 기간 겹침·한계값) → 시작 시각 도달 = 자동 오픈(별도 조작 없음) → 진행 현황은 DB 쿼리·토스 대시보드 → 사고 시 긴급 중단(새 구매·결제 차단, **중단 시각 기록**, 이미 산 사람 유지) → 추가 물량은 새 회차 등록.

## 6. 범위

**안 하는 것 (사업 사유)** — 대기열(정문 통제는 별도 인프라 — 본편은 "계산대가 약속을 지키는가") · 봇/다계정 방어(별도 정책 영역) · 예고·알림(마케팅 영역) · 승인 후 환불 자동화(빈도 낮음 — 수동) · 주문 내역 화면(결제 결과는 직후 응답으로 확인) · 다중 PG(교체 지점만 격리) · 화면 설계(백엔드 범위 — 시나리오는 4장 텍스트로 대체) · 핫딜 중단 사유 기록(1인 운영 — 시각만 기록).

**받아들이는 불편 (왜 괜찮은가)** — 폭주 순간 "다시 시도" 실패(재고는 사라지지 않음) · 이탈 주문의 최대 10분 자리 점유(시한부) · 만료 후 재구매 시 매진 가능(선착순의 본질).

## 7. 오픈 이슈 — "모른다"가 아니라 "언제 정한다"

| 이슈 | 결정 시점 | 해소 (2026-07-19 현행화) |
|---|---|---|
| 조회 노출 상세 — 종료·매진 핫딜의 목록 유지, 취소 핫딜 상세 응답 형태 | 슬라이스 0 착수 시 | ❌ 공개 조회 API 를 만들지 않아 정하지 않았다 — [핫딜 ADR](../adr/hotdeal.md) 제외 |
