# 비기능 요구 — 숫자 한 곳 집약 (6슬롯)

> 기능 명세만 받고 만들면 새벽에 깬다 — 비기능 6개에 **숫자**를 박아 둔다. "빠르게"가 아니라 `p95 200ms`, "많이"가 아니라 `1,000 RPS`로.
> **정본은 각 ADR·PRD** — 본 문서는 여러 문서에 흩어진 비기능 수치를 **트래픽·응답·가용성·데이터·일관성·운영부담** 6슬롯으로 모아, 한 화면에서 보이게 한다.
> 표기: 기술 용어는 첫 등장에 한 줄 풀이. 근거는 파일 레벨 링크 + 텍스트에 절 번호.

## 빈 슬롯을 숨기지 않는다 (정직 라벨)

6슬롯 중 빈칸은 6개월 뒤 운영 사고로 채워진다 — 그래서 못 채운 슬롯도 드러낸다. 다만 이 프로젝트는 **실사용자 없는 포트폴리오**라, 일부 슬롯(가용성 SLO·데이터 증가율)은 의미 있는 수치를 **본질적으로 못 뽑는다**. 그 슬롯은 억지 숫자를 지어내지 않고 **"가정" / "미측정" / "미설정"** 으로 라벨하고, **언제 채우는지**를 함께 적는다("모른다"가 아니라 "언제 정한다" — [PRD 7장](hotdeal-prd.md) 기조).

| 라벨 | 뜻 |
|---|---|
| **실측** | k6 벤치마크로 측정한 값 ([RFC — 동시성 벤치마크](../rfc/concurrency-benchmark.md)) |
| **가정** | 실사용자 부재로 유도한 값(측정 아님) — 근거 유도식 명시 |
| **미측정** | 지금 측정하지 않음 + 언제 측정하나 |
| **미설정** | 이 규모에선 의미 있는 목표를 못 세움 + 어떤 조건에서 세우나 |

## 한눈에 — 6슬롯

| # | 슬롯 | 값 | 상태 | 근거 |
|---|---|---|:---:|---|
| 1 | **트래픽** (평소/피크/폭발) | 평소 1일 1핫딜 / 피크 오픈 60초 동시 ~5,000명·구매 ~1,000 TPS / 폭발(측정) 동시 1,000 VU ≈ 700 RPS | 가정+실측 | [PRD 전제2·3](hotdeal-prd.md) · [RFC 벤치마크 8절](../rfc/concurrency-benchmark.md) |

| 3 | **가용성** (SLO/다운타임) | 피크 5xx **0%**(실측). 가용성 SLO·허용 다운타임은 **미설정** | 오류율 실측·SLO 미설정 | [RFC 벤치마크 6절](../rfc/concurrency-benchmark.md) · [주문 ADR 6절](../adr/order.md) |
| 4 | **데이터** (크기/증가율/보존) | 소규모(핫딜 1일 1개·재고 상한 10만). 보존: **논리삭제 없음**, 결제 실패 시도도 행 보존 | 보존 명시·크기 미측정 | [ERD 6](erd.md) · [결제 ADR 2절](../adr/payment.md) |
| 5 | **일관성** (즉시/결과적/약함) | 구매 코어 = **즉시(강한)** / 주문↔결제 전파·후속 = **결과적(최종)** | 경계별 명시 | [ADR-0012](../adr/0012-context-map-module-boundaries.md) · [ADR-0002](../adr/0002-monolith-first-partial-msa.md) |
| 6 | **운영 부담** (알람/롤백/대시보드) | 대시보드 k6+Grafana(실측 시) · 롤백 전략 프로퍼티 교체(Type2) · 알람 **구상만** | 대시보드·롤백 있음·알람 미구현 | [ADR-0013](../adr/0013-load-test-tool-k6.md) · [재고 동시성 ADR 4절](../adr/concurrency.md) |

## 각 슬롯 상세

### 1. 트래픽 — 평소 / 피크 / 폭발

| 구간 | 값 | 라벨 | 유도·근거 |
|---|---|:---:|---|
| 평소 | 1일 1핫딜, 평시 부하 낮음 | 가정 | 운영 주기 1일 1핫딜([PRD 전제3](hotdeal-prd.md)). 평시 RPS는 미측정(실사용자 없음) |
| 피크 | 오픈 직후 60초 동시 사용자 ~5,000명 · 구매 시도 ~1,000 TPS | 가정 | MAU 10만 → 이벤트 참여 ~5% → 오픈 순간 집중 ≈ 5,000명 유도([PRD 전제2](hotdeal-prd.md)) |
| 폭발(측정) | k6 VU 1,000 동시 발사 = 오픈 순간 1,000명 스파이크, 실측 역산 **~700 RPS**(1,000건을 ~1.4초에 소화) | 실측 | [RFC 벤치마크 8절](../rfc/concurrency-benchmark.md). CCU 환산 ≈ 2만~6만(Little's Law) |

- **왜 "동시 1,000"인가**: 정상상태 부하가 아니라 **오픈 순간 도착 스파이크**를 가정한다. 측정은 가상 사용자 1,000명이 각 1건씩 총 1,000건을 소화하는 구성(k6 `shared-iterations`)이다.
- **미달 구간**: 앱 1인스턴스·동시 1,000에서는 SLA 안(p95 1.44초)이다. 앱 3인스턴스에서는 조건부가 2.52초로 SLA를 넘었고 Redis는 1.99초로 겨우 들어왔다 — 악화 요인은 재고 행 락 경합과 자원 경합 둘로 분리했다([RFC 벤치마크 7절](../rfc/concurrency-benchmark.md)).

### 2. 응답 시간 — p50 / p95 / p99

**SLA**(Service Level Agreement — 지키기로 정한 성능 목표선. 내부 목표라 엄밀히 SLO): 주문 생성 `POST /api/orders`

| 구간 | 목표 | 라벨 |
|---|---|:---:|
| 폭주(핫딜 오픈 스파이크) | **p95 ≤ 2s** | 실측 분포 기반 |
| 평시 | **p95 ≤ 500ms** | 실측 분포 기반 |

- **도출**: 실측에 여유를 붙여 올림 — 저경합 p95 266ms → 500ms, 고경합 p95 1.37s → 2s(Google SRE Workbook 절차 — [RFC 벤치마크 8절](../rfc/concurrency-benchmark.md)).
- **p50은 측정 안 함**(avg만 기록) — 정직 표기. 꼬리 지연(p95/p99)이 선착순의 관심사라 p50 우선순위 낮음.
- **상품 조회**: p99 ≤ 200ms — **가정**(핫딜 폭주가 조회를 마비시키지 않음을 [PRD 검수3](hotdeal-prd.md)이 요구). **미측정** — 고트래픽 조회 최적화 단계(Redis 캐싱·인덱싱)에서 측정.
- **단서**: SLA와 실사용자 경험의 상관은 미검증(구글 SLO 문서 예시도 동일 단서) — 운영 데이터로 조정 전제.

### 3. 가용성 — SLO / 허용 다운타임

| 항목 | 값 | 라벨 |
|---|---|:---:|
| 피크 오류율 | 구매 API 5xx **0%** | 실측 |
| 가용성 SLO (99.9% 등) | **미설정** | — |
| 허용 다운타임 | **미설정** | — |

- **초과 판매 0 · 거짓 성공 0 은 SLA가 아니라 절대 불변식**이다([주문 ADR 6절](../adr/order.md)) — 지연은 목표선(넘으면 조정)이지만, 정확성은 협상 대상이 아니다. 이 둘을 SLA 슬롯에 넣지 않는 게 정직하다.
- **왜 SLO 미설정인가**: 가용성 SLO(월 43분 다운 허용 = 99.9%)는 **다중 노드·실트래픽·에러 예산 소진 추적**이 있어야 의미가 있다. 단일 로컬 환경·실사용자 없음에선 숫자를 지어내는 게 오히려 거짓이다. **언제 채우나** — 다중 노드 운영·실트래픽 확보 시([PRD 검수3](hotdeal-prd.md) 관측 최소판이 진입점).

### 4. 데이터 — 크기 / 증가율 / 보존

| 항목 | 값 | 라벨 |
|---|---|:---:|
| 크기 | 소규모 — 핫딜 1일 1개, 재고 상한 10만([ERD 6](erd.md)) | 미측정 |
| 증가율 | 미관리 — 포트폴리오 소규모 | 미측정 |
| 보존 | **논리삭제 없음**(상태 enum으로 제어) · 결제 **실패 시도도 행 보존**(CS·정산 증빙) · 재고 변동 원장은 보류 | 명시 |

- **보존 정책은 명시적**이다 — 논리삭제 대신 상태 enum([entity.md](../../.claude/rules/entity.md)), Payment는 paymentKey 1건=1행이라 실패 시도도 남긴다([결제 ADR 2절](../adr/payment.md)). 재고 변동 원장(모든 변동을 한 줄씩 감사)은 보류 — 도입 시 [재고 동시성 ADR](../adr/concurrency.md) 갱신.
- **왜 크기·증가율 미측정인가**: 데이터 볼륨·월 증가율·아카이빙 주기는 실운영 데이터가 있어야 뽑힌다. **언제 채우나** — 합성 대량 데이터 확장 테스트 또는 실운영 진입 시. 그 전이라도 "빠지면 1년 뒤 마이그레이션이 RFC 한 장 나온다"는 신호라 슬롯 자체는 비워 두지 않고 드러낸다.

### 5. 일관성 — 즉시 / 결과적 / 약함

| 경계 | 일관성 | 수단 |
|---|---|---|
| **구매 코어** (주문·재고 차감·결제 승인) | **즉시(강한)** — 초과 판매 0은 한 트랜잭션 | 조건부 UPDATE·조건부 상태 전이([주문 ADR 7절](../adr/order.md)·[재고 동시성 ADR 4절](../adr/concurrency.md)) |
| **주문 ↔ 결제 상태 전파** | **결과적(최종)** — 확정 전 "결제 확인 중" 파생 상태로 노출 | IN_DOUBT 보존 + 해소 스케줄러([결제 ADR 5·6절](../adr/payment.md)) |
| **결제 후속** (알림·정산 등) | **결과적(최종)** — MSA 분리 대비 | 이벤트(Kafka + Saga) — [ADR-0002](../adr/0002-monolith-first-partial-msa.md)·[ADR-0012](../adr/0012-context-map-module-boundaries.md) |

- **경계를 일관성 요구로 가른 것**이 이 프로젝트의 뼈대다 — 돈·재고 정합은 동기(강한), 상태 전파·알림·통계는 이벤트(최종)([ADR-0002](../adr/0002-monolith-first-partial-msa.md) 근거 표).
- **약한 일관성은 두지 않는다** — 핫딜 잔여 표시조차 판단 원본이 항상 재고라([핫딜 ADR 1절](../adr/hotdeal.md)) "표시는 캐시, 판단은 원본"이지 약한 일관성이 아니다.

### 6. 운영 부담 — 알람 / 롤백 / 대시보드

| 항목 | 값 | 라벨 |
|---|---|:---:|
| **대시보드** | k6 + Micrometer→Prometheus→Grafana 통합(부하 곡선 + 서버 지표 한 화면) | 벤치마크 시 구성 |
| **롤백** | 재고 전략 `@ConditionalOnProperty(stock.deduct.strategy)` 교체(Type2) · FK 미사용이라 스키마 롤백 유연 | 있음 |
| **알람** | SLO→알람 임계 1:1 환산 + 커넥션 풀 고갈 런북 — **구상만, 실체 미구현** | 미구현 |

- **관측 지표(무엇을 보나)**: 스레드 수가 아니라 `hikaricp_connections_active`·`hikaricp_connections_pending`(커넥션 풀 포화)와 `jvm_threads_states{state="blocked"}`(락 대기)를 본다([RFC 벤치마크 4절](../rfc/concurrency-benchmark.md)).
- **롤백 절차**: 재고 차감 방식은 프로퍼티 한 줄로 조건부↔Redis 교체(Type2 — [재고 동시성 ADR 4절](../adr/concurrency.md)). Redis 승격 조건은 SLA 위반 시. 스키마는 FK 미사용이라 `ALTER`가 제약 순서에 안 묶임([ADR-0003](../adr/0003-no-db-fk-constraints.md)).
- **스케줄러 격리**: 만료·결제해소 스케줄러를 `ThreadPoolTaskScheduler`(pool 2)로 분리 — 해소가 토스 장애로 장기 점유해도 만료(재고 방출)가 안 멈춘다([결제 ADR 6절](../adr/payment.md)). 각 스케줄러는 회차 상한(LIMIT 500) + 인덱스로 한 회차 비용을 묶는다.
- **왜 알람 미구현인가**: 알람은 임계 초과를 받을 **실운영 트래픽**과 수신자가 있어야 산다. **언제 채우나** — [PRD 검수3 관측 최소판](hotdeal-prd.md)(SLO→알람 1:1, 런북 한 장)을 관측/마무리 단계에서 실체화. 지금은 대시보드(벤치마크용)까지만 실재.

## 다중 인스턴스 운영 전제 (스케일아웃)

배포 전제가 **서버 여러 대**(LB 뒤, MySQL·Redis 공유 — [기술 가설 3장](hotdeal-purchase-hypothesis.md))다. 1 vs 3 인스턴스 실측 상세는 [RFC — 동시성 벤치마크 7절](../rfc/concurrency-benchmark.md), 여기엔 운영 전제만 요약한다.

- **정확성은 인스턴스 수와 무관** — 재고 차감(조건부 UPDATE 한 문장)·계정당 1활성주문(DB 유니크)·상태 전이 1회(조건부 전이)·인증(무상태 JWT + 공유 Redis) 모두 최종 직렬화가 DB/Redis에 있고, 인스턴스 로컬 상태(로컬 캐시·정적 컬렉션)가 없다. 앱 3대 실측에서도 성공 정확히 10 · 초과 판매 0. 스케줄러 중복 처리만 미측정(조건부 전이 관문의 설계 논리).
- **스케일아웃은 선형이 아니다(실측)**: 부하를 고정하고 앱만 1→3대로 늘리자 조건부 UPDATE의 지연이 1.44초→2.52초로 나빠졌고, **행 락 대기 누적이 5.2초→45.8초로 8.8배** 늘었다. 재고 행을 건드리지 않아 락 대기가 0인 Redis도 1.10→1.99초로 1.8배 느려졌다. **두 전략의 차이(0.53초)가 락 경합 몫이고, 나머지는 한 머신에서 자원을 나눠 쓴 몫**이다([RFC 벤치마크 7절](../rfc/concurrency-benchmark.md)).
- **커넥션 총량 = 인스턴스 수 × 풀 크기** — 온프레미스 2~4 인스턴스 × HikariCP 기본 10 = 20~40 (MySQL `max_connections` 151 내 여유). 실측: 3인스턴스 합산 30 = DB `Threads_connected` 31. 오토스케일링은 스코프 밖 — 인스턴스를 크게 늘리면 앱보다 DB 커넥션이 먼저 마른다(15인스턴스 × 10 ≈ 한계). 그 구간에선 인스턴스당 풀 축소·커넥션 풀러(RDS Proxy 등)·DB 수직 확장으로 대응.
- **시각 — 호스트 NTP 동기화 전제**: 만료 판정(`expiresAt < now`)·핫딜 기간 판정이 각 인스턴스 시계를 쓴다. 동기화된 오차는 수 ms라 결제 제한시간 10분 판정에 무해 — DB `NOW()` 단일 기준으로 바꾸지 않는다(앱에서 `now` 주입이 테스트 고정 시각에 유리, 과설계 회피).
- **외부 호출 중복 — 대응하지 않았다**: 만료 스케줄러의 중복 실행은 DB 안에서 끝나는 헛 SELECT 비용이라 수용한다. 해소는 토스 API를 호출하므로 N개 인스턴스의 중복이 외부 호출 N배가 되지만, 상태 전이가 조건부고 결제 키에 유니크가 걸려 있어 반영은 한 번이다 — 남는 것은 낭비뿐이다. 처리권을 나누는 장치는 넣지 않았다([결제 ADR 6절](../adr/payment.md)).

## 이 표가 답하는 것

- **"빠르게" 대신 숫자**: 응답 슬롯이 p95 목표선을 가진다 → 리뷰에서 "느린가?"가 아니라 "SLA를 넘나?"로 대화가 된다.
- **빈 슬롯의 정직**: 가용성 SLO·데이터 증가율이 비었음을 숨기지 않는다 → "안 했다"가 아니라 "이 규모에선 못 뽑는다 + 언제 뽑는다"로 관리된다.
- **6개월 뒤**: 새 멤버가 "폭주는 얼마까지 견디나 / 재고 전략은 어떻게 되돌리나 / 무슨 지표를 보나"를 이 한 문서에서 찾는다.
