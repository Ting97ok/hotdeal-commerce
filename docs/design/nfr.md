# 비기능 요구 — 숫자 한 곳 집약 (6슬롯)

> 기능 명세만 받고 만들면 새벽에 깬다 — 비기능 6개에 **숫자**를 박아 둔다. "빠르게"가 아니라 `p95 200ms`, "많이"가 아니라 `1,000 RPS`로.
> **정본은 각 ADR·PRD** — 본 문서는 여러 문서에 흩어진 비기능 수치를 **트래픽·응답·가용성·데이터·일관성·운영부담** 6슬롯으로 모아, 한 화면에서 보이게 한다.
> 표기: 기술 용어는 첫 등장에 한 줄 풀이. 근거는 파일 레벨 링크 + 텍스트에 절 번호.

## 빈 슬롯을 숨기지 않는다 (정직 라벨)

6슬롯 중 빈칸은 6개월 뒤 운영 사고로 채워진다 — 그래서 못 채운 슬롯도 드러낸다. 다만 이 프로젝트는 **실사용자 없는 포트폴리오**라, 일부 슬롯(가용성 SLO·데이터 증가율)은 의미 있는 수치를 **본질적으로 못 뽑는다**. 그 슬롯은 억지 숫자를 지어내지 않고 **"가정" / "미측정" / "미설정"** 으로 라벨하고, **언제 채우는지**를 함께 적는다("모른다"가 아니라 "언제 정한다" — [PRD 7장](hotdeal-prd.md) 기조).

| 라벨 | 뜻 |
|---|---|
| **실측** | k6 벤치마크로 측정한 값 ([ADR-0010](../adr/0010-concurrency-strategy-selection.md)) |
| **가정** | 실사용자 부재로 유도한 값(측정 아님) — 근거 유도식 명시 |
| **미측정** | 지금 측정하지 않음 + 언제 측정하나 |
| **미설정** | 이 규모에선 의미 있는 목표를 못 세움 + 어떤 조건에서 세우나 |

## 한눈에 — 6슬롯

| # | 슬롯 | 값 | 상태 | 근거 |
|---|---|---|:---:|---|
| 1 | **트래픽** (평소/피크/폭발) | 평소 1일 1핫딜 / 피크 오픈 60초 동시 ~5,000명·구매 ~1,000 TPS / 폭발(측정) 동시 1,000 VU ≈ 700 RPS | 가정+실측 | [PRD 전제2·3](hotdeal-prd.md) · [ADR-0010 부하 모델](../adr/0010-concurrency-strategy-selection.md) |
| 2 | **응답 시간** (p50/p95/p99) | 주문 생성 **p95 ≤ 2s(폭주)·≤ 500ms(평시)** / 상품 조회 p99 ≤ 200ms | 주문 실측·조회 가정 | [ADR-0010 SLA](../adr/0010-concurrency-strategy-selection.md) · [PRD 2장](hotdeal-prd.md) |
| 3 | **가용성** (SLO/다운타임) | 피크 5xx **0%**(실측). 가용성 SLO·허용 다운타임은 **미설정** | 오류율 실측·SLO 미설정 | [ADR-0010](../adr/0010-concurrency-strategy-selection.md) · [ADR-0006](../adr/0006-correctness-invariants-defense-layers.md) |
| 4 | **데이터** (크기/증가율/보존) | 소규모(핫딜 1일 1개·재고 상한 10만). 보존: **논리삭제 없음**, 결제 실패 시도도 행 보존 | 보존 명시·크기 미측정 | [ERD 6](erd.md) · [ADR-0008](../adr/0008-payment-model-pg-boundary.md) |
| 5 | **일관성** (즉시/결과적/약함) | 구매 코어 = **즉시(강한)** / 주문↔결제 전파·후속 = **결과적(최종)** | 경계별 명시 | [ADR-0012](../adr/0012-context-map-module-boundaries.md) · [ADR-0002](../adr/0002-monolith-first-partial-msa.md) |
| 6 | **운영 부담** (알람/롤백/대시보드) | 대시보드 k6+Grafana(실측 시) · 롤백 전략 프로퍼티 교체(Type2) · 알람 **구상만** | 대시보드·롤백 있음·알람 미구현 | [ADR-0013](../adr/0013-load-test-tool-k6.md) · [ADR-0010](../adr/0010-concurrency-strategy-selection.md) |

## 각 슬롯 상세

### 1. 트래픽 — 평소 / 피크 / 폭발

| 구간 | 값 | 라벨 | 유도·근거 |
|---|---|:---:|---|
| 평소 | 1일 1핫딜, 평시 부하 낮음 | 가정 | 운영 주기 1일 1핫딜([PRD 전제3](hotdeal-prd.md)). 평시 RPS는 미측정(실사용자 없음) |
| 피크 | 오픈 직후 60초 동시 사용자 ~5,000명 · 구매 시도 ~1,000 TPS | 가정 | MAU 10만 → 이벤트 참여 ~5% → 오픈 순간 집중 ≈ 5,000명 유도([PRD 전제2](hotdeal-prd.md)) |
| 폭발(측정) | k6 VU 1,000 동시 발사 = 오픈 순간 1,000명 스파이크, 실측 역산 **~700 RPS**(1,000건을 ~1.4초에 소화) | 실측 | [ADR-0010 부하 모델](../adr/0010-concurrency-strategy-selection.md). CCU 환산 ≈ 2만~6만(Little's Law) |

- **왜 "동시 1,000"인가**: 정상상태 부하가 아니라 **오픈 순간 도착 스파이크**(k6 개방형 도착률 — 응답을 기다리지 않고 정해진 도착률로 쏨). "대기자 5천~1만 명 이벤트의 오픈 순간" 가정.
- **미달 구간**: 단일 행 UPDATE 천장(조건부 ≈ Redis 동률이 깨지는 지점)은 동시 1,000보다 높아 **미도달** — 인원 곡선(100~2,000 스윕)으로 천장 위치를 좁히는 건 후속([ADR-0010 정직한 한계](../adr/0010-concurrency-strategy-selection.md)).

### 2. 응답 시간 — p50 / p95 / p99

**SLA**(Service Level Agreement — 지키기로 정한 성능 목표선. 내부 목표라 엄밀히 SLO): 주문 생성 `POST /api/orders`

| 구간 | 목표 | 라벨 |
|---|---|:---:|
| 폭주(핫딜 오픈 스파이크) | **p95 ≤ 2s** | 실측 분포 기반 |
| 평시 | **p95 ≤ 500ms** | 실측 분포 기반 |

- **도출**: 실측에 여유를 붙여 올림 — 저경합 p95 266ms → 500ms, 고경합 p95 1.37s → 2s([Google SRE Workbook]·[무신사 SLO 사례]와 같은 절차, [ADR-0010 SLA 절](../adr/0010-concurrency-strategy-selection.md)).
- **실측 분포**(조건부 UPDATE·격리 환경, [ADR-0010 결과 표](../adr/0010-concurrency-strategy-selection.md)):

| 워크로드 | p95 | avg |
|---|---|---|
| 저경합 (동시 100 · 재고 10) | 266ms | 99ms |
| 고경합 (동시 1000 · 재고 2000) | 1.37s | 925ms |
| 품절 경합 (동시 1000 · 재고 10) | 1.7~1.9s | — |

- **p50은 측정 안 함**(avg만 기록) — 정직 표기. 꼬리 지연(p95/p99)이 선착순의 관심사라 p50 우선순위 낮음.
- **상품 조회**: p99 ≤ 200ms — **가정**(핫딜 폭주가 조회를 마비시키지 않음을 [PRD 검수3](hotdeal-prd.md)이 요구). **미측정** — 고트래픽 조회 최적화 단계(Redis 캐싱·인덱싱)에서 측정.
- **단서**: SLA와 실사용자 경험의 상관은 미검증(구글 SLO 문서 예시도 동일 단서) — 운영 데이터로 조정 전제.

### 3. 가용성 — SLO / 허용 다운타임

| 항목 | 값 | 라벨 |
|---|---|:---:|
| 피크 오류율 | 구매 API 5xx **0%** | 실측 |
| 가용성 SLO (99.9% 등) | **미설정** | — |
| 허용 다운타임 | **미설정** | — |

- **오버셀 0 · 거짓 성공 0 은 SLA가 아니라 절대 불변식**이다([ADR-0006](../adr/0006-correctness-invariants-defense-layers.md)) — 지연은 목표선(넘으면 조정)이지만, 정확성은 협상 대상이 아니다. 이 둘을 SLA 슬롯에 넣지 않는 게 정직하다.
- **왜 SLO 미설정인가**: 가용성 SLO(월 43분 다운 허용 = 99.9%)는 **다중 노드·실트래픽·에러 예산 소진 추적**이 있어야 의미가 있다. 단일 로컬 환경·실사용자 없음에선 숫자를 지어내는 게 오히려 거짓이다. **언제 채우나** — 다중 노드 운영·실트래픽 확보 시([PRD 검수3](hotdeal-prd.md) 관측 최소판이 진입점).

### 4. 데이터 — 크기 / 증가율 / 보존

| 항목 | 값 | 라벨 |
|---|---|:---:|
| 크기 | 소규모 — 핫딜 1일 1개, 재고 상한 10만([ERD 6](erd.md)) | 미측정 |
| 증가율 | 미관리 — 포트폴리오 소규모 | 미측정 |
| 보존 | **논리삭제 없음**(상태 enum으로 제어) · 결제 **실패 시도도 행 보존**(CS·정산 증빙) · 재고 변동 원장은 보류 | 명시 |

- **보존 정책은 명시적**이다 — 논리삭제 대신 상태 enum([entity.md](../../.claude/rules/entity.md)), Payment는 paymentKey 1건=1행이라 실패 시도도 남긴다([ADR-0008 결정1](../adr/0008-payment-model-pg-boundary.md)), 재고 변동 원장(모든 변동을 한 줄씩 감사)은 슬라이스 2에서 검토로 보류([ADR-0011 보류](../adr/0011-product-inventory-reservation.md)).
- **왜 크기·증가율 미측정인가**: 데이터 볼륨·월 증가율·아카이빙 주기는 실운영 데이터가 있어야 뽑힌다. **언제 채우나** — 합성 대량 데이터 확장 테스트([project-plan Could](../project-plan.md)) 또는 실운영 진입 시. 그 전이라도 "빠지면 1년 뒤 마이그레이션이 RFC 한 장 나온다"는 신호라 슬롯 자체는 비워 두지 않고 드러낸다.

### 5. 일관성 — 즉시 / 결과적 / 약함

| 경계 | 일관성 | 수단 |
|---|---|---|
| **구매 코어** (주문·재고 차감·결제 승인) | **즉시(강한)** — 오버셀 0은 한 트랜잭션 | 조건부 UPDATE·조건부 상태 전이([ADR-0006](../adr/0006-correctness-invariants-defense-layers.md)·[ADR-0010](../adr/0010-concurrency-strategy-selection.md)) |
| **주문 ↔ 결제 상태 전파** | **결과적(최종)** — 확정 전 "결제 확인 중" 파생 상태로 노출 | IN_DOUBT 보존 + 해소 스케줄러([ADR-0008 B1](../adr/0008-payment-model-pg-boundary.md)·[payment system 설계](../payment/api-design-system.md)) |
| **결제 후속** (알림·정산 등) | **결과적(최종)** — MSA 분리 대비 | 이벤트(Kafka + Saga) — [ADR-0002](../adr/0002-monolith-first-partial-msa.md)·[ADR-0012](../adr/0012-context-map-module-boundaries.md) |

- **경계를 일관성 요구로 가른 것**이 이 프로젝트의 뼈대다 — 돈·재고 정합은 동기(강한), 상태 전파·알림·통계는 이벤트(최종). PDF 트레이드오프 3축의 "결합도 ↔ 일관성"을 결정마다 적용한 결과([ADR-0002](../adr/0002-monolith-first-partial-msa.md) 근거 표).
- **약한 일관성은 두지 않는다** — 핫딜 잔여 표시조차 판단 원본이 항상 재고라([ADR-0007 결정1](../adr/0007-hotdeal-state-operations.md)) "표시는 캐시, 판단은 원본"이지 약한 일관성이 아니다.

### 6. 운영 부담 — 알람 / 롤백 / 대시보드

| 항목 | 값 | 라벨 |
|---|---|:---:|
| **대시보드** | k6 + Micrometer→Prometheus→Grafana 통합(부하 곡선 + 서버 지표 한 화면) | 벤치마크 시 구성 |
| **롤백** | 재고 전략 `@ConditionalOnProperty(stock.deduct.strategy)` 교체(Type2) · FK 미사용이라 스키마 롤백 유연 | 있음 |
| **알람** | SLO→알람 임계 1:1 환산 + 커넥션 풀 고갈 런북 — **구상만, 실체 미구현** | 미구현 |

- **관측 지표(무엇을 보나)**: 스레드 수가 아니라 `hikaricp_connections_active`·`hikaricp_connections_pending`(커넥션 풀 포화)와 `jvm_threads_states{state="blocked"}`(락 대기)를 본다([ADR-0009 결정3](../adr/0009-stock-concurrency-design.md)).
- **롤백 절차**: 재고 차감 방식은 프로퍼티 한 줄로 조건부↔Redis 교체(Type2 — [ADR-0010 가역성](../adr/0010-concurrency-strategy-selection.md)). Redis 승격 조건은 "조건부와 동률이 깨지는 SLA 위반 지점". 스키마는 FK 미사용이라 `ALTER`가 제약 순서에 안 묶임([ADR-0003](../adr/0003-no-db-fk-constraints.md)).
- **스케줄러 격리**: 만료·결제해소 스케줄러를 `ThreadPoolTaskScheduler`(pool 2)로 분리 — 해소가 토스 장애로 장기 점유해도 만료(재고 방출)가 안 멈춘다([payment system 설계](../payment/api-design-system.md)). 각 스케줄러는 회차 상한(LIMIT 500) + 인덱스로 한 회차 비용을 묶는다.
- **왜 알람 미구현인가**: 알람은 임계 초과를 받을 **실운영 트래픽**과 수신자가 있어야 산다. **언제 채우나** — [PRD 검수3 관측 최소판](hotdeal-prd.md)(SLO→알람 1:1, 런북 한 장)을 관측/마무리 단계([project-plan F](../project-plan.md))에서 실체화. 지금은 대시보드(벤치마크용)까지만 실재.

## 이 표가 답하는 것

- **"빠르게" 대신 숫자**: 응답 슬롯이 p95 목표선을 가진다 → 리뷰에서 "느린가?"가 아니라 "SLA를 넘나?"로 대화가 된다.
- **빈 슬롯의 정직**: 가용성 SLO·데이터 증가율이 비었음을 숨기지 않는다 → "안 했다"가 아니라 "이 규모에선 못 뽑는다 + 언제 뽑는다"로 관리된다.
- **6개월 뒤**: 새 멤버가 "폭주는 얼마까지 견디나 / 재고 전략은 어떻게 되돌리나 / 무슨 지표를 보나"를 이 한 문서에서 찾는다.
