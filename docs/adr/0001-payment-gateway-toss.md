# ADR-0001. 결제 PG — 토스페이먼츠 (테스트 모드)

- 상태: 확정 · 작성: 2026-06-10 (결정 자체는 프로젝트 계획 단계)

## 컨텍스트

핫딜 구매를 결제까지 완결하려면 PG(Payment Gateway — 카드사·은행과 가맹점 사이에서 결제를 대행하는 사업자) 연동이 필요하다. 제약: 개인 포트폴리오라 **사업자 등록 없이** 테스트할 수 있어야 하고, 4주 일정상 연동 문서 품질이 곧 개발 속도다.

## 후보 비교

토스페이먼츠 / 포트원 / 나이스페이 / 카카오페이 / 스트라이프.

기준 우선순위: ① 사업자 없이 테스트 무료(0순위 — 미충족 시 탈락) → ② 요금 → ③ API·예외처리 문서 품질.

## 결정

**토스페이먼츠 테스트 모드.**

- 요금은 PG 간 대동소이해서 변별 기준에서 제외.
- 남은 변별은 **예외처리·멱등성 문서 품질** — 토스가 에러 코드 체계, 멱등키 헤더, 결제 조회 API, 웹훅(결과 통보) 문서에서 가장 충실.

## 결과 (이 결정이 만든 설계)

- 주문이 가맹점 주문번호를 보유: `orders.order_no`(UUID) — 결제창 호출·승인·웹훅 매칭에 사용.
- Payment 행 단위 = **paymentKey 1개**(토스가 시도를 식별하는 키), 같은 멱등키 재시도는 기존 행 갱신.
- 멱등 2겹(내부 활성 유니크 + 토스 멱등키), 승인 응답 유실 보정(결제 조회 API), 웹훅 보정 — [가설](../design/hotdeal-purchase-hypothesis.md) 5·9.

## 테스트 모드의 운영 한계 (제약)

- 실거래 없음 — 청약철회 등 실서비스 법적 의무는 발생하지 않음(포트폴리오 전제).
- **부하 테스트에서 토스 테스트 API 에 부하를 전송하지 않는다** — 외부 샌드박스는 호출량 제한·차단 위험. 결제 승인 구간은 PaymentGatewayClient 테스트 대역으로 대체하고 부하는 구매·만료 경로에 한정([가설 PRD 전제 4](../design/hotdeal-prd.md), [ADR-0008](0008-payment-model-pg-boundary.md)).
- 1인 로컬 환경의 웹훅 수신 한계(공인 주소 필요)는 슬라이스 3 에서 해결 방안 확정(터널링 등).
