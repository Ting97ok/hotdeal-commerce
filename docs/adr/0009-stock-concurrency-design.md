# ADR-0009. 재고 동시성 설계 — HotDealStock 분리·5방식·잠금 규율

- 상태: 확정 (운영 전략 최종 선정은 ADR-0010 예정 — 3주차 벤치마크 후) · 작성: 2026-06-11 · 갱신: 2026-06-20 (원자적 조건부 UPDATE 를 5번째 벤치마크 방식으로 추가 — [ADR-0011](0011-product-inventory-reservation.md) 결정 4)
- 관련 규칙: [가설 3·8](../design/hotdeal-purchase-hypothesis.md) · [erd 5](../design/erd.md) · [ADR-0011](0011-product-inventory-reservation.md)(이 분리 원칙을 상품 재고로 일반화 + `Stock`→`HotDealStock` 리네임)

## 컨텍스트

수천 동시 구매가 한 핫딜의 재고 한 줄을 차감한다. 본질은 확인-결정-쓰기(TOCTOU — 두 요청이 같은 값을 읽고 둘 다 통과) 경합의 직렬화([리서치 2](../design/research-flash-sale.md))이고, 배포 전제는 서버 여러 대(JVM 잠금 무효)다.

## 결정 1 — HotDealStock 별도 테이블 (HotDeal 1:1)

재고를 HotDeal 칼럼이 아니라 좁은 전용 행으로 분리한다.

1. **낙관락 가짜 충돌 방지** — `@Version` 은 행 전체 단위로 충돌을 판정한다. 재고가 HotDeal 행에 있으면 관리자의 가격 수정(버전 +1)이 진행 중 구매 전부를 "충돌"로 실패시킨다 — 무관한 작업이 같은 행에 산다는 이유만으로.
2. **비관락 잠금 줄 분리** — 비관락도 행 전체를 잠그므로, 분리해야 구매 대기 줄이 HotDealStock 에만 생기고 HotDeal(메타)은 자유.
3. **벤치마크 집중** — 경합 지점이 항상 HotDealStock 한 행(또는 Redis 키 하나)이라, 그 지점에서 잠금 방식만 바꿔 끼우고 똑같은 테스트를 다시 돌리면 다른 조건은 그대로라 방식 차이만 순수하게 비교된다.
4. **실증 사례** — Oracle PeopleSoft(별도 잠금 테이블)·Shopify(상품과 분리된 단위당 1행)·우아한형제들(전체 재고 RDB ↔ 실시간 사용량 Redis 분리) — 경합을 의식하는 시스템은 전부 어떤 형태로든 재고를 분리한다.

## 결정 2 — 5방식 벤치마크: "운영 선택 1개 + 나머지는 그 선택의 근거"

낙관락(@Version) · 비관락(FOR UPDATE) · Redis 원자 연산 · 분산락(Redisson) · **원자적 조건부 UPDATE**(단일 행 — [ADR-0011](0011-product-inventory-reservation.md) 결정 4 에서 ProductStock 운영 채택) — 전부 서버 여러 대에서 유효. 5개를 다 돌리는 건 운영이 아니라 **학습·비교 장치**이며, README 에 "운영은 1개, 4개는 벤치마크 근거"로 표기해 실무 오해를 차단한다. 실선례: 올리브영 — Lua 전면 적용은 정확하지만 21% 느려짐 → 카운터 2개 조합으로 8%만 손해 보고 정확성 유지([리서치 3](../design/research-flash-sale.md)). "정확성만"은 쉽고 "정확성+성능"이 어렵다는 게 서사의 핵심.

### 5방식 예상 분석 — 벤치마크 전에 세운 가설

벤치마크는 "쏘고 보자"가 아니라 **예상을 검증**하는 것이다. 이론상 예상:

| 방식 | 동작 | 한 행 폭주(핫딜)에서의 예상 |
|---|---|---|
| 낙관락(@Version) | 안 잠그고 진행 → 저장 때 버전 충돌이면 실패 | 충돌률이 매우 높아 대부분 실패·재시도 → **성공 처리량 최저** |
| 비관락(FOR UPDATE) | 행을 잠그고 줄 세움 | 정확하지만 대기 중 **DB 커넥션 점유**(결정 3) → 처리량은 락 보유시간에 묶임 |
| Redis 원자(+Lua) | 인메모리·단일 스레드라 원자 차감 | **처리량 최고** 예상. 단 재고 정답이 Redis 로 옮겨가 DB 정합 보정 필요 |
| 분산락(Redisson) | Redis 락을 서버들이 공유해 직렬화 | 락 획득·해제 Redis 왕복 비용 → Redis 직접 차감보다 느릴 수 있음, DB 는 정답 유지 |
| 원자적 조건부 UPDATE | `UPDATE … SET remaining = remaining − :qty WHERE id = :id AND remaining >= :qty` 한 문장, 영향 행 수로 판단(버전·재시도 없음) | 행 잠금을 UPDATE 한 문장 동안만 잡고 원자 차감 — 낙관락 같은 재시도 폭증도, 비관락 같은 긴 트랜잭션 커넥션 점유도 없음. **단일 행 한계(~500 QPS)까지 단순·정확** 예상, 넘으면 Redis 필요 |

> **Lua** = 가벼운 스크립트 언어. Redis 가 Lua 스크립트를 서버에서 한 덩어리(원자적)로 실행해, "재고 확인 후 차감"을 명령 두 개로 쪼개지 않고 한 동작으로 만든다. 그래서 "Redis 원자 연산"은 실무에선 보통 Redis + Lua.

> **원자적 조건부 UPDATE 를 5번째로 넣는 이유**: 낙관락과 달리 행을 읽지 않고 `WHERE remaining >= :qty` 조건부 차감 한 문장으로 끝내 충돌·재시도 개념이 없다(영향 행 수 0 = 품절). [ADR-0011](0011-product-inventory-reservation.md) 결정 4 에서 저경합 ProductStock 의 운영 방식으로 이미 채택했으므로, 같은 방식이 **고경합 HotDealStock 한 행**에선 어떤 성능을 내는지 측정해 "ProductStock 엔 충분했지만 HotDealStock 엔 부족한 지점"을 수치로 드러낸다. 가장 단순한 RDB 차감의 성능 기준선이기도 하다.

**예상이 있는데도 벤치마크하는 이유**:
1. **차이의 크기는 이론으로 안 나온다** — 낙관락이 얼마나 나쁜지, Redis 가 몇 배 빠른지는 숫자가 있어야 운영안을 고른다.
2. **예상이 틀릴 실제 가능성** — 리서치에서 봤듯 Redis 는 단일 스레드 CPU 가 고RPS 에서 한계라 예상만큼 안 빠를 수 있고([리서치 4](../design/research-flash-sale.md)), 비관락 즉시 실패(NOWAIT)는 실패율이 너무 높아 "정확하지만 못 씀"이 될 수 있다.
3. **포트폴리오 가치가 바로 그 서사** — "X 를 예상했고, 측정값은 Y였고, 차이의 이유는 Z." 결과는 ADR-0010 에 남긴다.

### 왜 JVM 잠금(`synchronized` 등)은 후보가 아닌가 — 시연 없이 문서로 확정

- JVM 잠금은 **자기 프로세스(서버 인스턴스) 안에서만** 스레드를 직렬화한다. 배포 전제가 서버 여러 대(로드밸런서 뒤)이므로 각 서버가 따로 줄을 세울 뿐, **서버 사이의 동시 차감은 아무도 막지 않아 오버셀이 난다.** `ReentrantLock` 등 JVM 안 동기화 수단 전부가 같은 이유로 탈락.
- 덤으로 성능도 잃는다 — 서버 1대 안에서조차 차감 경로 전체를 한 줄로 세워 처리량을 깎는다. 다중 서버에서 정합은 못 지키면서 비용만 내는 선택.
- **실측 시연은 하지 않는다** — "인스턴스 경계를 못 넘는다"는 자명한 사실이라 문서 설명으로 충분하고, 벤치마크 런과 변형 코드를 아끼는 스코프 선택이다. (시연을 원하면 벤치마크의 전략 교체 구조에 변형 하나로 추가 가능 — 다른 전략과 중첩이 아니라 교체라 측정 오염은 없음)

## 결정 3 — 비관락 대기는 즉시 실패(NOWAIT)가 출발값

비관락에서 잠금을 기다리는 요청은 **그 대기 내내 DB 커넥션 1개와 열린 트랜잭션을 붙잡는다.** 진짜 한계는 스레드 수가 아니라 **DB 커넥션 풀**이다 — 풀 크기가 보통 작아서(HikariCP 기본 10), 수십 요청만 잠금 대기에 들어가도 풀이 마른다. 그러면 같은 풀을 쓰는 **핫딜과 무관한 API 들까지 커넥션을 못 받아 멈춘다**(연쇄 장애). `NOWAIT`(즉시 실패)는 기다리지 않고 커넥션을 곧바로 반납해 이 공유 풀을 보호한다.

- MySQL 잠금 대기 설정은 1초 단위(기본 50초!)라 선택지는 사실상 즉시 실패(NOWAIT) vs 1초 — 3주차 부하 테스트로 실측 확정.
- "기다리지 않고 정직하게 실패"는 덜 팔림 허용([ADR-0006](0006-correctness-invariants-defense-layers.md))과 일관.
- **관찰 지표**: 스레드 수가 아니라 `hikaricp_connections_active`·`hikaricp_connections_pending`(커넥션 풀 포화)와 `jvm_threads_states{state="blocked"}`(락 대기로 막힌 스레드)를 본다. ("스레드 200개" 같은 웹 워커 풀 한계는 이 경로의 병목이 아니다 — JVM 은 여러 독립 풀로 나뉘고, 막히는 건 공유 커넥션 풀이다.)

## 결정 4 — 잠금 순서·교착 수습

- **정본 순서: 주문 → 재고** (두 테이블을 건드리는 모든 경로 공통). JPA(Hibernate)가 같은 트랜잭션에서 INSERT(주문)를 UPDATE(재고)보다 먼저 내보내는 기본 동작과 일치 — 우회 조작 불필요.
- 만료 일괄 처리는 **주문 1건 = 트랜잭션 1개** — 잠금 짧게, "전이 1회" 단위와 일치, 문제 생겨도 1건만 영향.
- 교착(deadlock — 두 작업이 서로가 잡은 잠금을 기다리는 고리. 무한 대기가 아니라 DB 가 즉시 감지해 한쪽을 강제 취소) 발생 시: 구매 = `CONCURRENT_UPDATE_CONFLICT`("다시 시도") 응답 / 만료 = 다음 주기 자연 재시도.
- **비관락 변형의 예외**: 재고 선잠금이 그 방식의 정체성이라 순서가 뒤집힌다 → 취소 경로를 방식별로 바꾸면 "차감 전략만 교체해 비교"라는 벤치마크 순수성이 깨지므로, **교착 허용 + 발생 횟수를 측정 지표에 포함**(방식 비교 데이터가 됨).
