# ADR-0007. 핫딜 상태 모델과 운영 정책

- 상태: 확정 · 작성: 2026-06-11
- 관련 규칙: [가설 6](../design/hotdeal-purchase-hypothesis.md) · [erd 1·4](../design/erd.md)

## 컨텍스트

핫딜의 진행 단계(예정/진행/종료/매진)를 무엇으로 표현하나 + 관리자 운영(취소·수정·등록)의 정책.

## 결정 1 — 진행/매진은 "판매 기간 + 재고"로 그때그때 판단 (상태 머신 ❌)

`status` 는 ACTIVE / CANCELED(관리자 취소 전용) 둘뿐. SCHEDULED→OPEN→CLOSED 같은 전이 상태값과 스케줄러를 두지 않는다.

- 정확성은 재고 차감의 원자성이 보장한다 — 상태값은 현실과 어긋날 수 있는 **표시**일 뿐이고, 임계 경로가 표시를 믿는 순간 어긋남(갱신 지연)이 오버셀·오구매가 된다.
- 정시 오픈 = "시작 시각 도달" — 쿠팡 골드박스 매일 7시(쿠팡 공식 채널 확인)·카카오 정시 오픈이 같은 모델([리서치 9.5·10.1](../design/research-flash-sale.md)). 스케줄러 인프라가 통째로 불필요해짐.
- 상태를 단계별로 전이시키는 구조(상태 머신 — finite state machine)가 필요한 생명주기는 Order(PENDING→PAID/CANCELED)가 이미 담당하므로, HotDeal 까지 그 구조를 둘 필요가 없다.
- 매진 시 품절 표시는 조회 최적화용 **선택 사항** — 도입하더라도 표시는 캐시일 뿐 판단 원본은 항상 재고, 해제는 재고 복원과 같은 트랜잭션.

## 결정 2 — 관리자 취소 정책

취소(CANCELED) 시:
- **새 구매와 결제 승인을 모두 차단** — 승인 검사는 토스 호출 **전**(돈이 움직이기 전에 거부). 취소의 대표 목적이 가격 오류 긴급 차단인데, "새 구매만" 막으면 이미 결제창을 연 수십 명이 취소 후에도 계속 확정되는 구멍이 남는다.
- **이미 PAID 인 주문은 유효**(구매 인정·이행) — 환불 자동화는 범위 밖이므로, 범위 안 기능(취소)이 만든 결과물의 방침을 명시: 필요 시 토스 대시보드 수동 환불.
- 미결제(PENDING)는 만료로 자연 취소 — 일괄 강제 취소를 만들지 않음(복원 경로 단일화).

## 결정 3 — 운영 중 수정·수량 변경 API 없음 (스코프 선택)

변경은 **취소 후 재등록**, 추가 물량은 **새 딜(회차) 등록**. `totalQuantity` 는 등록 후 불변.

- "품절 후 다시 살 수 있게 되는" 현상은 본 설계에서도 두 경로로 재현된다 — ⓐ 취소·만료 **복원**(재고 부활, [ADR-0004](0004-stock-reservation-lifecycle.md)) · ⓒ **회차** 재오픈(상품:딜 1:N — 카카오 100개씩 3차례, [리서치 9.5](../design/research-flash-sale.md)).
- **정직한 인정**: 운영자가 물량을 다시 채우는 ⓑ **재입고(증량)도 실무에 실재**한다 — 올리브영 공식 "재입고 기획전"([리서치 10.5](../design/research-flash-sale.md)). 즉 금지의 근거는 "업계 표준이라서"가 **아니다**.
- 금지의 실제 이유 = **스코프 선택**: ⓐ·ⓒ만으로 품절 부활 요구가 충족되는데, 증량은 관리 API·검증·테스트가 한 벌 더 늘어 "적은 API + 깊이" 절제에 어긋난다. 가격 오류 대응도 수정이 아니라 긴급 차단이 통례.
- **전환 경로**: 증량이 필요해지면 `totalQuantity += N` 과 `remaining += N` 을 **한 트랜잭션**에서 갱신하는 API 하나로 추가 가능 — 같은 트랜잭션이면 장부 일치식([ADR-0006](0006-correctness-invariants-defense-layers.md))도 깨지지 않는다(격리로 중간 상태가 밖에서 안 보임). "등록 후 불변"은 그때 해제.

## 결정 4 — 같은 상품의 판매 기간 겹침 등록 금지

겹치면 같은 상품이 동시에 두 가격으로 팔린다. MySQL 은 기간 배타 제약이 없어 **관리자 등록 API 검증**으로 막는다(슬라이스 0). 동시 등록 두 건이 검증을 같이 통과하는 경합은 관리자 단독 운영 전제로 수용 — 필요해지면 등록 직렬화(상품 행 잠금)로 보강.

## 결정 5 — 운영 현황·집계

관리자 현황 API 를 만들지 않는다 — 진행 중 판매 현황·종료 후 집계는 **DB 쿼리(정합 검증식 재사용)와 토스 대시보드**로 갈음. 핫딜 단건 조회 응답에 잔여 수량을 포함하는 것으로 노출은 충분.
