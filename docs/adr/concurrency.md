# 재고 동시성 — 의사결정 기록

선착순 구매가 재고 한 행에 몰릴 때 **재고를 어디에 두고, 무엇으로 차감할지** 정한 기록.
측정 방법과 실측값은 [동시성 벤치마크](../rfc/concurrency-benchmark.md)에 있다.

**결론**

- 재고는 상품·핫딜 정보와 다른 테이블에 둔다 (`ProductStock` 원본 / `HotDealStock` 핫딜 몫)
- 차감은 원자적 조건부 UPDATE 한 문장. 낙관적 락, Redis + Lua 와 같은 조건에서 측정해 선정했다
- 남는 한계는 앱을 늘려도 처리량이 선형으로 늘지 않는다는 것이다

---

## 1. 재고는 상품·핫딜 정보와 다른 테이블에 둔다

- 상품 재고 `ProductStock`(실물 / 예약), 핫딜 재고 `HotDealStock`(잔여) 두 테이블 — 전체 관계는 [데이터 모델](../design/erd.md)
- 재고는 주문마다 수정되고 상품 정보는 등록 후 거의 바뀌지 않는다
  - 한 행에 두면 상품 정보를 고치는 작업이 구매 차감과 같은 행 락을 두고 서로 기다린다
  - 지금은 상품 수정 기능이 없지만, 생기면 그 경합이 구매 경로 안으로 들어온다
- 차감 지점이 한 곳이라, 차감 방식만 교체하여 같은 부하를 다시 측정할 수 있었다

트레이드오프

| 대가 | 대응 |
|---|---|
| 핫딜 등록이 3단계로 늘었다 (상품 재고 예약 → 핫딜 → 핫딜 재고) | 한 트랜잭션으로 묶어 중간에 실패하면 전부 되돌린다 |
| 재고를 따로 조회해야 한다 | 구매가 몰리는 경로는 핫딜 재고 한 행만 봐서, 늘어난 조회가 부하 경로 밖이다 |

## 2. 핫딜 수량은 상품 재고에서 떼어 온다

- `ProductStock`이 재고 원본이다
  - 창고에 실제 있는 수를 실물, 핫딜에 떼어 둔 수를 예약으로 나눠 갖는다
  - 판매 가능 수량은 컬럼으로 저장하지 않고 `실물 − 예약`으로 그때그때 계산한다
  - 저장하면 실물이나 예약이 바뀔 때마다 같이 고쳐야 하고, 어긋나면 그대로 버그가 된다
- **구매가 몰리는 경로는 핫딜 재고 한 행만 수정한다.** 상품 재고는 핫딜 등록과 결제 확정에서만 건드리므로 경합에서 비켜나 있다

트레이드오프

| 대가 | 대응 |
|---|---|
| 상품 재고의 예약은 상품당 합계 하나라, 그 값만으로는 핫딜별 몫을 알 수 없다 | 핫딜별 예약량은 `hot_deals.total_quantity`(등록 후 불변)이고, 판매·대기 수량은 주문이 핫딜을 참조하므로 분해된다. 합계와 개별값이 어긋나지 않는지는 재고 장부 검증식이 확인한다 |

## 3. 세 방식을 같은 조건에서 측정한다

- 낙관적 락(@Version), 원자적 조건부 UPDATE, Redis + Lua
- 비관적 락과 분산 락(Redisson)은 재지 않았다
  - 결과가 이론으로 예측돼 측정 이득이 낮다
  - 비관적 락은 락을 기다리는 동안 DB 커넥션을 쥔다. 처리량이 락 보유 시간에 묶인다
  - 분산 락은 락을 얻고 푸는 데 Redis를 두 번 더 왕복한다. Redis 직접 차감보다 느리다
- 무엇을 재고 무엇을 이론으로 접을지 고르는 것 자체가 판단이다

## 4. 차감은 원자적 조건부 UPDATE 한 문장

```sql
UPDATE hot_deal_stock SET remaining_quantity = remaining_quantity - :qty
 WHERE hot_deal_id = :id AND remaining_quantity >= :qty
```

- 확인(WHERE)과 차감(SET)이 한 문장이라 그 사이에 다른 요청이 끼어들 틈이 없다
  - 영향 받은 행이 없으면 품절이다
  - 충돌도 재시도도 없다
- 읽어서 판단하고 쓰는 방식은 위험하다
  - InnoDB의 일반 SELECT는 스냅샷을 읽어(MVCC) 남이 방금 차감하고 커밋한 결과를 못 본다
  - UPDATE의 WHERE는 스냅샷이 아니라 최신 커밋 값으로 평가된다
- 선정한 이유
  - 쿼리 한 문장이라 단순하다
  - 재고를 DB 한 곳에서만 관리한다
- 낙관적 락은 고경합에서 1,000건 중 163건만 성공해 탈락
- Redis + Lua는 미채택
  - 재고를 Redis에서 관리하게 된다
  - DB 동기화와 유실 복구가 따라온다

## 5. 앱을 늘리면 왜 느려지는가 — 원인을 둘로 분리했다

부하를 동시 1,000명 · 1,000건으로 고정하고 앱 대수만 1과 3으로 바꿔 측정했다.
전략별 실측값은 [벤치마크 RFC 4절](../rfc/concurrency-benchmark.md)에 있고, 여기에는 그 값으로 무엇을 판단했는지만 적는다.

**재고 행 락 경합이 실재한다**

- 앱을 3배로 늘리자 조건부 UPDATE의 락 대기 누적이 5.2초에서 45.8초로 8.8배 늘었다
- 대기 횟수는 985회에서 999회로 거의 같다. 요청 수가 같으니 당연하고, **건당 대기 시간이 8.6배 길어진 것**이 악화의 실체다

**락과 무관한 요인도 실재한다**

- Redis는 재고 행을 수정하지 않아 락 대기가 정확히 0인데도 1.10초에서 1.99초로 1.8배 느려졌다
- 한 머신에서 앱 셋과 DB·Redis·부하 도구가 자원을 나눠 쓴 결과로 본다

**Redis를 대조군으로 두면 둘이 갈린다**

- 앱 3대에서 조건부와 Redis의 지연 차이(0.53초)를 락 경합이 추가로 만든 몫으로 읽는다
- 다만 그 값을 신뢰하지는 않는다. 단일 측정이라 같은 조건 두 실행도 갈렸고, 두 전략은 락 말고도 다르다(DB UPDATE 경로 전체 vs Redis 명령 하나). 방향은 락 대기 데이터가 뒷받침하지만 크기는 아니다
- 나머지 악화는 두 전략이 함께 겪었으므로 락 밖 요인이다

**순간을 찍는 관측으로는 보이지 않았다**

- 2초 간격으로 기록한 `Innodb_row_lock_current_waits`는 34번 모두 0이었다
- 누적값(`Innodb_row_lock_time`)을 보고서야 45.8초가 드러났다. 대기가 짧고 잦으면 순간 관측은 놓친다

**확실한 것**

- 초과 판매 0건은 앱 3대에서도 성립했다. 재고 10에 1,000명이 몰려도 성공은 정확히 10건이다
- 앱 3대에서 조건부는 SLA 2초를 넘겼고(2.52초) Redis는 1.99초로 겨우 들어왔다. 절대값은 로컬 한 머신에 딸린 값이지만, 조건부가 더 나빠지는 방향은 락 대기 데이터가 뒷받침한다
- 전환 수단은 준비돼 있다. `stock.deduct.strategy` 설정값으로 Redis, 그다음은 재고를 여러 행으로 분산하는 것

## 6. 락 순서와 실패 처리

- 주문과 재고를 함께 건드리는 모든 경로는 **주문 → 재고** 순서를 지킨다 (교착 방지)
- **코드에 쓴 호출 순서가 그대로 SQL 순서가 된다** — 통합 테스트 SQL 로그로 확인했다
  - 주문은 ID가 IDENTITY라 `save()` 시점에 INSERT가 나간다. DB가 채번하므로 커밋을 기다릴 수 없다
  - 재고 차감은 JPQL 벌크 UPDATE라 호출 시점에 바로 나간다. 영속성 컨텍스트의 쓰기 지연은 엔티티 변경 추적에만 적용되고 벌크 연산은 그 경로를 타지 않는다
  - 두 SQL 사이에 다른 문장이 끼지 않았다. 앞서 조회한 엔티티를 아무도 수정하지 않아 함께 내보낼 변경이 없었기 때문이다
- 그래서 이 순서는 Hibernate가 정리해 주는 것이 아니라 코드가 지켜야 한다. 다른 ID 전략을 쓰면 INSERT가 커밋 시점으로 밀려 순서가 뒤집힌다
- 만료 일괄 처리는 주문 1건 = 트랜잭션 1개
- 경합에 밀린 요청은 "다시 시도해 주세요"로 돌려준다
  - 서버가 몰래 재시도하지 않는다
  - 첫 시도가 사실 성공했는데 응답만 늦은 경우 중복 주문이 되기 때문

트레이드오프

| 대가 | 대응 |
|---|---|
| 폭주 때 일부 요청이 실패 응답을 받는다 | 재고가 사라진 것이 아니라 다시 주문하면 살 수 있다 |
| 재고가 남았는데 덜 팔릴 수 있다 | 초과 판매만 절대 막고, 덜 팔리는 것은 받아들인다 |
