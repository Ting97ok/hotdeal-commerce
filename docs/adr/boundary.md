# 모듈 경계 — 의사결정 기록

1인 프로젝트라 서비스를 쪼갤지 판단할 신호가 없다. 팀도, 배포 인프라도, 독립 확장을 요구하는 트래픽도 없다.
**모놀리식은 고른 것이 아니라 출발점이다.** 이 기록이 정한 것은 그 한 덩어리 안을 무엇으로 갈랐나다.

한 도메인 안에서 계층을 어떻게 쌓고 인터페이스를 어디에 두는지는 이 문서의 축이 아니다.

**결론**

- 경계는 카디널리티가 아니라 **변경 이유**로 갈랐다
- 재고를 독립 모듈로 뗐다. 경합하는 수량은 정보가 아니다
- 의존은 한 방향으로만 흐른다. 카탈로그와 재고는 주문을 모른다

---

## 1. 경계는 변경 이유로 가른다

"핫딜을 주문에 합쳐야 하나"를 엔티티 관계(핫딜 1 : N 주문)로 판단하려다 층위를 혼동한 적이 있다. **카디널리티는 경계를 정하지 않는다.** 한 경계 안에도 1:N 은 흔하다(주문 1 : N 주문라인).

가르는 기준은 **무엇이 이 코드를 고치게 만드나**다.

| 모듈 | 맡는 것 | 변경을 부르는 것 |
|---|---|---|
| `auth` | 로그인·토큰 재발급 | 인증 방식 |
| `user` | 회원 | 회원 정보 규칙 |
| `product` | 상품 카탈로그(이름·정가) | 상품 등록·정보 변경 |
| `stock` | 재고 — 상품 원본과 핫딜 몫 | **동시성·정합성** |
| `hotdeal` | 판매 행사 정의(특가·기간·수량) | **선착순 운영** |
| `order` | 구매 트랜잭션(누가·무엇을·언제) | 구매 흐름·상태 전이 |
| `payment` | 결제 시도·승인·해소 | 외부 PG 연동 |

- 굵게 표시한 둘이 이 저장소가 파고드는 곳이다. 나머지는 그 둘을 성립시키는 주변이다
- 밖에서 부를 수 있는 진입점을 가진 것은 `auth`·`hotdeal`·`order`·`payment` 넷뿐이다. `product`·`stock`·`user` 는 다른 도메인이 불러 쓴다
- **핫딜을 `order` 에 흡수하지 않았다** — 주문이 0건인 핫딜이 존재한다. 생명주기가 독립이고, 주문은 핫딜을 참조할 뿐 포함하지 않는다

## 2. 재고를 독립 모듈로 뗐다

- 재고는 상품·핫딜의 *정보* 가 아니라 *경합하는 수량* 이다. 그 차이가 테이블을 가른 이유이고([재고 동시성 ADR 1절](concurrency.md)) 모듈을 가른 이유도 같다
- 데이터의 원본 기준은 상품이지만 코드 모듈은 재고 관심사로 묶는다. **두 층위라 충돌하지 않는다** — "상품이 재고 원본을 보관한다"(데이터)와 "`stock` 모듈 소속"(코드)은 다른 말이다
- 덕분에 동시성 실험과 장부 검증식이 한 모듈에 모인다. 전략 세 구현을 설정으로 바꿔 끼우는 것도 이 응집 위에서 된다

재고는 쪼갤 후보에서도 뺀다. 주문 생성의 선점, 결제 승인의 확정 차감, 만료·해소의 복원 **세 흐름 모두와 원자성으로 묶여 있다.** 강한 일관성이 필요한 곳을 분산시키면 얻을 것이 없다.

## 3. 의존은 한 방향으로만 흐른다

경계가 무너지지 않는 것은 패키지를 몇 개로 쪼갰느냐가 아니라 **의존을 어디로 걸었느냐**로 정해진다.

```
order   → hotdeal · product · stock · user
payment → hotdeal · stock
hotdeal · product · stock → 없음
```

- 구매 쪽이 카탈로그를 참조하고, **역방향은 한 건도 없다.** 상품과 재고는 주문을 모른다
- 타 도메인의 Repository 를 직접 부르는 코드도 없다. 남의 도메인은 그쪽 Service 를 거쳐서만 닿는다
- 이 방향이 지켜지는 동안은 어디를 떼든 **잘라야 할 선이 한 곳에 모인다.** 참조가 양방향이면 그 선이 사라진다
- 자동 강제(ArchUnit 같은)는 없다. 지금은 코드 리뷰가 안전장치다

---

**제외** — 결제를 별도 서비스로 떼는 일은 하지 않았다. 이벤트 발행도 없다. 분리 설계는 실제로 뗄 때 쓴다.
