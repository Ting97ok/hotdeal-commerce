# 결제 — 의사결정 기록

결제를 어느 PG(카드사·은행과 가맹점 사이에서 결제를 대행하는 사업자)에 붙이고, 외부 승인 결과를 우리 데이터와 **어긋나지 않게 잇는 방법**을 정한 기록.
주문이 재고를 언제 잡고 언제 놓는지는 [주문 ADR](order.md)에 있다.

**결론**

- PG는 토스페이먼츠 테스트 모드다. 사업자 등록 없이 붙일 수 있는 것이 탈락 기준이었다
- 결제 시도 한 번이 한 행이다. 토스가 시도마다 다른 키를 발급하고, 그 키가 곧 우리 행이다
- 토스 호출은 DB 트랜잭션 밖에 둔다. 왕복 내내 커넥션을 잡으면 결제와 무관한 요청까지 막힌다
- 트랜잭션을 쪼개면 자동 롤백이 사라진다. 그 자리를 결과 네 갈래별 명시적 후처리가 대신한다
- 결과를 모르는 경우는 되돌리지 않고 남긴다. 되돌리면 돈은 나갔는데 주문은 취소된 상태가 된다

---

## 1. PG는 토스페이먼츠 테스트 모드다

- 후보는 토스페이먼츠·포트원·나이스페이·카카오페이·스트라이프였다
- 첫 기준은 **사업자 등록 없이 테스트할 수 있나**였고, 못 하면 그 자리에서 탈락이다. 개인 프로젝트라 협상 여지가 없다
- 요금은 PG 사이 차이가 거의 없어 변별 기준에서 뺐다
- 남은 변별은 문서 품질인데, 그중에서도 **에러 코드 체계·멱등키·결제 조회 API** 세 가지로 갈랐다
  - 성공 경로 문서는 어디나 있다. 이 셋이 없으면 실패 경로를 설계할 수 없다
  - 실제로 이 프로젝트의 결제 설계는 대부분 실패 경로다(5·6절)

트레이드오프

| 대가 | 대응 |
|---|---|
| 실거래가 없어 카드사 거절·지연이 실제로 어떤 분포로 오는지 모른다 | 분포에 기대는 판단을 두지 않았다. 분류는 응답 내용만 보고 하고([결제 결과 분류 RFC](../rfc/payment-result-classification.md)), 각 갈래는 어댑터 단위 테스트에서 응답을 직접 만들어 확인한다 |

## 2. 결제 시도 한 번이 한 행이다

- 주문과 결제는 1:N이고, 행 하나가 토스 거래 하나(`paymentKey`)에 대응한다
- 카드 한도가 넘어 다른 카드로 다시 시도하면 토스가 새 키를 발급한다. **두 키는 토스 입장에서 별개 객체 둘**이지 한 결제의 두 상태가 아니다
- 주문당 한 행 + 이력 테이블은 기각했다
  - 시도마다 메인 행을 덮어쓰면, 옛 키로 도착한 통보를 메인에서 못 찾아 이력 테이블을 뒤져야 한다
  - 기록용으로 만든 테이블이 운영 경로로 새고, 애초에 두 키가 다른 객체라 "한 칸 + 이력"이 모델 착오다
- 거래마다 고유 식별자를 주는 것은 토스만의 방식이 아니다. 포트원 `imp_uid`·나이스 TID·Stripe charge id가 모두 같다. "행 하나 = PG 거래 하나"는 PG를 바꿔도 그대로 간다
- `payments.pg_payment_key` 에 유니크를 건다
  - 같은 키로 두 행이 생기는 경로는 주문 상태 전이가 앞에서 막아 닿지 않는다(4절)
  - 그래도 뚫리면 500으로 드러낸다. 붙잡아 기존 행을 돌려주는 처리는 두지 않았다 — 방어를 뚫은 이상을 숨기게 된다
- 승인 성공이 주문당 한 건인 것은 Payment가 아니라 주문 전이(`PENDING`→`PAID` 한 번)가 보장한다
- 한 키의 상태 변천이나 토스 응답 원문을 쌓는 테이블은 두지 않았다. 지금 쓰는 것은 마지막 상태뿐이다

## 3. PG 의존은 세 층 경계에 가둔다

```
PaymentFacade → PaymentGatewayClient → TossPaymentClient → TossHttpClient
                (계약)                 (변환)              (전송)
```

| 층 | 맡는 일 | 규율 |
|---|---|---|
| 계약 `PaymentGatewayClient` | 승인·조회를 우리 언어로 선언 | 시그니처에 토스 타입이 나오지 않는다 |
| 어댑터 `TossPaymentClient` | 토스 응답·예외를 우리 결과 네 갈래로 접고 에러 코드를 분류 | 토스 지식은 여기까지만 |
| 전송 `TossHttpClient` | HTTP 호출·인증 헤더·멱등키 헤더 | 판단 로직 없음 |

**토스 어휘를 막는 것은 인터페이스가 아니라 결과 타입이다**

- 어댑터가 토스 응답과 예외를 네 갈래로 접어 돌려주므로 호출부가 받는 것은 그 넷뿐이다. 토스 에러 코드도 HTTP 예외도 위로 올라가지 않는다
- 반환 타입을 토스 응답으로 바꾸면 인터페이스가 있어도 분류 정책이 통째로 호출부에 올라온다
- 변환은 계층 사이 DTO 매핑과 다르다. 남의 어휘를 우리 것으로 바꾸는 국경 통관이고, 결과를 접고 에러를 분류하는 정책 판단을 포함한다
- 실제로 토스 구현을 이름으로 부르는 코드는 자기 자신과 그 테스트뿐이다. 결제 흐름은 계약만 본다

인터페이스를 어디에 두는지, 벤더 구현을 왜 도메인 밖에 두는지는 [애플리케이션 구조 ADR 3·4절](architecture.md)에 있다. 여기서는 그 규칙이 결제에 어떻게 적용됐는지만 적는다.

```
domain/payment/client/                  계약 — 밖으로 나가는 호출 계층의 입구
domain/payment/client/dto/              그 계약이 주고받는 결과 타입
infrastructure/paymentgateway/toss/     PG 역할의 토스 구현 — 어댑터·전송·요청 응답 타입·설정
```

- `TossConfirmResponse` 같은 타입은 결제 비즈니스가 아니라 토스 API 명세다. 토스가 필드를 바꿔 결제 도메인 파일이 바뀌면 변경 이유가 섞인 것이다
- 역할을 벤더보다 위에 둔 것은 둘째 PG 때문이다. 구현들이 `paymentgateway` 아래 나란히 서면 교체 후보가 한자리에 모인다
- 전송층은 선언형 HTTP 인터페이스이고, 주소·타임아웃·인증은 설정 클래스가 프록시 빈을 만들 때 넣는다. 시크릿은 환경변수로 주입받아 코드에 박지 않는다
- 둘째 PG를 동시에 받는 일(에러 정규화·PG 선택)은 하지 않았다. 둘째가 실제로 필요해질 때 어댑터 자리에 구현을 더한다

## 4. 토스 호출은 DB 트랜잭션 밖이다

경계가 셋이다.

```
TX1  조회·금액 검증 → 핫딜 취소 확인 → 주문 선점 → 상품 재고 차감 → 커밋
     토스 승인 호출 (트랜잭션 밖)
TX2  결과별 반영
```

- 외부 왕복을 트랜잭션 안에 두면 그동안 DB 커넥션을 잡고 있다. read 타임아웃이 60초라 최악의 경우 커넥션 하나가 60초 묶인다
  - 스레드는 수백 개라 여유가 있지만 커넥션은 수십 개라 먼저 마른다. 토스가 느려지면 결제와 무관한 요청까지 막힌다
  - 요청 스레드는 여전히 동기로 기다린다. 논블로킹으로 바꾼 것이 아니라 커넥션만 돌려준 것이다
- 선점이 토스 호출보다 앞이라는 순서는 그대로다

```sql
UPDATE orders SET status = 'PAID'
 WHERE id = :id AND status = 'PENDING' AND expires_at > :now
```

- 만료로 취소된 주문도, 이미 결제된 주문도 여기서 영향 행 0으로 걸러져 **토스를 부르지 않는다**. 돈이 나갈 일이 없다
  - 만료 시각이 지났는데 만료 처리가 아직 안 쓸어간 주문은 `expires_at > :now` 가 막는다
  - 영향 행이 0이면 만료됐는지 이미 결제됐는지 구분하지 않고 409 하나로 답한다. 확인하고 나서 다시 쓰면 그 사이에 또 끼어들 수 있다
- 타임아웃은 연결 2초, 응답 60초다. 연결은 빨리 실패해야 "닿지 않았다"가 확정되고, 응답 60초는 토스가 결제 처리 API에 권장하는 값이다

트레이드오프

| 대가 | 대응 |
|---|---|
| TX1이 먼저 커밋돼 토스가 거부해도 자동 롤백이 없다 | 결과 네 갈래마다 되돌리는 방법을 명시로 정했다(5절) |
| 외부 결제와 우리 DB를 한 번에 쓸 수 없어 그 사이가 끊기면 잔여가 남는다 | 동기로는 막을 수 없다. 남긴 것을 해소가 주기적으로 정리한다(6절) |

## 5. 결과 네 갈래마다 되돌리는 방법이 다르다

승인 결과를 sealed 타입 넷으로 가른다. 호출부는 `switch` 하나로 받고 `try-catch` 가 없다.

| 결과 | Payment | 주문 | 재고 | 응답 |
|---|---|---|---|---|
| 승인 | `DONE` 생성 | `PAID` 유지 | 차감 유지 | 200 |
| 거절 — 돈이 안 나간 것이 확정 | 만들지 않음 | `CANCELED`(`PAYMENT_FAILED`) | 핫딜·상품 둘 다 방출 | 402 |
| 통신오류 — 요청이 닿지 않음 | 만들지 않음 | `PENDING` 복귀 | 상품 재고만 복원 | 502 |
| 미확정 — 닿았는데 결과를 모름 | `IN_DOUBT` 생성 | `PAID` 유지 | 차감 유지 | 200 |

- 거절과 통신오류를 다르게 다루는 기준은 **주문을 살려 둘 이유가 있나**이다
  - 거절은 사용자의 결제 수단이 막힌 것이라 같은 주문으로 다시 눌러도 또 막힌다. 핫딜 재고를 즉시 놓아 다음 대기자에게 돌리고, 재시도는 새 주문으로 받는다
  - 통신오류는 우리 쪽이나 네트워크 문제라 사용자 잘못이 아니다. 주문을 살려 두고 바로 다시 누를 수 있게 한다
- 그래서 놓는 재고 범위도 다르다
  - 거절은 주문이 끝나므로 핫딜 몫까지 놓는다
  - 통신오류는 주문이 `PENDING` 으로 살아 있어 핫딜 몫을 계속 잡아 둔 채, 결제 확정 때 뺀 상품 재고만 되돌린다. 그래도 안 오면 만료가 마지막으로 정리한다
- 되돌리는 일도 전부 조건부 전이다(`WHERE status = 'PAID'`). 영향 행이 1일 때만 재고를 건드려 두 번 놓는 일이 없다
- 예상하지 못한 예외는 결과로 접지 않고 그대로 500으로 내보낸다. 전부 삼키면 우리 버그가 미확정으로 위장된다
- 어떤 토스 응답이 어느 갈래로 가는지, 그 경계를 어디에 그었는지는 [결제 결과 분류 RFC](../rfc/payment-result-classification.md)에 있다

트레이드오프

| 대가 | 대응 |
|---|---|
| 미확정이면 사용자에게 성공도 실패도 아닌 답을 준다 | 200에 상태를 실어 보내 "확인 중"으로 구분할 수 있게 한다. 그 값을 화면이 어떻게 보여줄지는 정하지 않았다 — 이 저장소에 프런트엔드가 없다 |

## 6. 결과를 모르는 것은 남기고 나중에 확정한다

- 미확정을 예외로 던지면 트랜잭션이 롤백돼 주문이 `PENDING` 으로 돌아간다. 그런데 돈은 나갔을 수 있다
  - 돈이 나갔는데 주문이 취소된 상태가 가장 나쁘고, 남겨 두는 쪽은 정리가 늦어질 뿐이다. 이 비대칭이 결제 설계 전체의 기준이다
- 남긴 것은 스케줄러가 1분마다 정리한다. 두 가지를 본다
  - **미확정 결제** — 만든 지 1분이 지난 것부터
  - **결제 행이 없는 `PAID` 주문**(고아) — 만료 시각이 5분 넘게 지난 것부터
- 해소는 만료 처리와 스레드를 나눠 쓴다(풀 2). 해소가 토스 응답을 오래 기다려도 만료가 멈추지 않는다
  - 한 회차에 보는 건수도 상한을 둔다. 밀린 물량이 한 번에 쏟아져도 회차 비용이 일정하다
- 고아는 TX1 커밋 뒤 토스 호출·TX2 사이에 프로세스가 죽으면 남는다. 미확정 행 기준으로도, `PENDING` 기준 만료로도 안 잡혀 따로 본다
  - 선점 조건에 `expires_at > :now` 가 있으므로 `PAID` 가 된 주문은 그 순간 만료 전이었다. 만료 시각이 5분 넘게 지났다면 결제 흐름은 끝났거나 죽었다는 뜻이다
- 확정하는 쪽은 우리가 아니라 토스다. 우리는 물어보고 반영한다
  - 승인됐으면 결제를 `DONE` 으로 올린다. 놓친 매출을 되찾는 것이다
  - 만료·중단·취소면 실패로 확정하고, 주문을 취소하며 재고를 놓는다
  - 토스에 결제 자체가 없으면(위조·오타 키) 돈이 나갈 수가 없어 실패로 확정한다
  - **인증만 끝나고 승인이 안 들어간 상태**는 실패가 아니라 우리가 마무리하지 못한 매출이다. 같은 키로 승인을 다시 부른다. 토스가 10분이면 스스로 만료시키므로 재시도 횟수를 따로 세지 않아도 무한히 돌지 않는다
- 고아를 되살릴 때 토스가 답한 금액이 주문 금액과 다르면 자동으로 확정하지 않고 로그만 남긴다. 사람이 봐야 하는 경우다
- 후속 처리(배송·알림·정산)의 방아쇠는 주문 `PAID` 가 아니라 결제 `DONE` 이다. 이것이 지켜지는 동안 고아를 자동 취소해도 뒤따르는 피해가 없다
- 여러 서버가 동시에 해소를 돌려도 결과가 같아 처리권을 나누지 않았다
  - 상태 전이가 전부 조건부라 반영은 한 번이고, 승인 재시도는 멱등키가 같아 토스가 같은 답을 준다
  - 겹치면 토스 조회가 중복되고, 고아를 동시에 복구하려 하면 결제 키 유니크에 걸려 한쪽이 예외 로그를 남긴다. 다음 회차엔 이미 결제 행이 있어 대상에서 빠진다
  - 넣는다면 정확성이 아니라 낭비를 줄이는 선택이다

## 7. 멱등키는 토스가 발급한 키를 그대로 쓴다

- 승인 요청 헤더에 `Idempotency-Key: {paymentKey}` 를 실어 보낸다. 서버가 따로 UUID를 발급하지도, 주문에 보관하지도 않는다
- 필요한 성질이 정확히 이것이다
  - 같은 결제를 다시 보내면(네트워크 재전송·해소의 재시도) 키가 같아 토스가 첫 결과를 그대로 준다
  - 카드를 바꿔 새로 결제하면 키가 달라 새 승인이 열린다
- 그래서 `payments` 에 멱등키 컬럼이 없다. 한때 두었지만 어느 경로에서도 값을 쓰지 않아 걷어냈다
- 겹은 둘이다. 안쪽은 주문당 `PAID` 전이 한 번, 바깥쪽은 토스 멱등키다
- 같은 키로 다시 들어온 요청에 저장된 결과를 돌려주는 방식은 만들었다가 물렸다
  - 이 API를 부르는 것은 결제창에서 돌아온 브라우저뿐이라, 409로 "이미 처리된 주문"이라 답하고 주문 내역으로 보내는 편이 계약이 단순하다
  - 되돌려주기를 두면 프런트엔드가 구분할 수 없는 200 경로가 하나 늘어난다
  - 서버끼리 부르거나 자동 재시도 계층이 생기면 다시 본다

## 8. 테스트 모드에서 확인하지 못하는 것

- 실거래가 없어 청약철회 같은 실서비스 법적 의무는 발생하지 않는다
- 부하 테스트는 결제 경로를 부르지 않는다. 폭주는 주문 생성에만 걸고, 외부 샌드박스에 부하를 보내지 않는다
- 승인 뒤 취소·환불·분쟁은 다루지 않았다. `PaymentStatus` 에 취소 값을 미리 만들어 두지도 않았다
  - 환불은 승인과 같은 어댑터를 방향만 바꿔 한 번 더 쓰는 일이다. `PaymentGatewayClient` 에 취소를 더하고 토스 취소 응답을 같은 결과 네 갈래로 접으면 된다
  - 새로 증명되는 것이 없어 넣지 않았다. 어려운 쪽은 부분 환불·환불의 멱등성·환불 실패 시 주문 상태인데, 그것을 열면 취소 API 와 정산 개념이 따라온다
- 결과 통보(웹훅)를 받지 않는다
  - 받으려면 공인 주소가 필요하고, 지금은 스케줄러가 물어보는 것으로 대신한다
  - 웹훅이 생겨도 해소를 대체하지 않는다. 미확정을 만드는 상황(부하·타임아웃)에서 통보도 같이 유실될 수 있어, 통보만 믿으면 놓친 건이 영영 안 잡힌다
