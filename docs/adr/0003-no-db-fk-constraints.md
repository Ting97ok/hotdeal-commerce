# ADR-0003. DB FK 제약 미사용 (칼럼 + 인덱스만)

- 상태: 확정 · 작성: 2026-06-10

## 컨텍스트

핫딜 구매는 한 핫딜에 쓰기가 폭주하는 경로다. InnoDB 에서 FK 제약이 있으면 자식 행 INSERT 마다 부모 행에 공유 잠금("처리 끝날 때까지 지우지 마" 표시)이 걸린다. 또한 이 프로젝트는 결제 후속 처리를 MSA 로 분리할 계획([ADR-0002](0002-monolith-first-partial-msa.md))이라, 경계를 넘는 FK 는 어차피 유지할 수 없다.

## 결정

**물리 DDL(Flyway 마이그레이션)에 FK 제약을 선언하지 않는다.** 참조는 FK 칼럼(`*_id`) + 보조 인덱스만 둔다. JPA 연관 매핑(@ManyToOne 등)은 유지하되, 연관에 `@ForeignKey(ConstraintMode.NO_CONSTRAINT)` 를 명시해 Hibernate 스키마 생성 경로에서도 FK 가 만들어지지 않게 한다 — 객체 모델과 DB 제약은 별개(상세 [entity.md](../../.claude/rules/entity.md)). ERD 다이어그램의 관계선(논리 참조)도 유지한다.

## 근거

1. **폭주 쓰기 경로의 부모 행 잠금 제거** — 주문 INSERT 가 핫딜/사용자 행에 거는 공유 잠금 비용과, 관리자 수정과의 상호 대기 소거.
2. **DDL·운영 유연성** — 테이블 변경, 대량 적재, 아카이빙이 제약 순서에 묶이지 않음.
3. **MSA 분리 대비** — 결제 경계 분리 시 경계 넘는 FK 는 불가능. 미리 같은 규율로 운영.
4. **대규모 실무 관행** — SK㈜ C&C 테크블로그가 "FK 없이 구축하는 관계형 DB"를 정리했고, Alibaba Java 개발 매뉴얼(p3c)은 "외래키·캐스케이드 금지(애플리케이션 계층에서 해결)"를 **강제 규칙**으로 명문화 — 출처: [리서치 10.4](../design/research-flash-sale.md).

## 트레이드오프 (잃는 것)

- 고아 데이터(부모 없는 자식 행)를 DB 가 막아주지 않는다.

## 보완 (잃은 것을 어떻게 메우나)

- **서비스 가드** — 쓰기 경로는 항상 부모 존재를 검증한 뒤 진행(구매 가드의 핫딜 조회 등).
- **정합 검증식 테스트** — 장부 일치식(정의: [주문 ADR 7절](order.md))이 참조 깨짐(고아 데이터)을 간접 탐지.
- 코딩 룰에 반영: [.claude/rules/entity.md](../../.claude/rules/entity.md).

## 전환 경로

참조 무결성이 DB 강제로 필요해지면 `ALTER TABLE ... ADD CONSTRAINT` 로 후처리 가능(추가 전 기존 데이터 정합 검증 필요). 결정을 뒤집는 비용이 낮은 편이다.
