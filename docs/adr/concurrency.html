재고 동시성 — 의사결정 기록

선착순 구매가 재고 한 행에 몰릴 때 재고를 어디에 두고, 무엇으로 차감할지 정한 기록. 측정 방법과 실측값은 동시성 벤치마크에 있다.

결론

  • 재고는 상품·핫딜 정보와 다른 테이블에 둔다 (ProductStock 원본 / HotDealStock 핫딜 몫)
  • 차감은 원자적 조건부 UPDATE 한 문장. 낙관적 락, Redis + Lua 와 같은 조건에서 측정해 선정했다
  • 남는 한계는 앱을 늘려도 처리량이 선형으로 늘지 않는다는 것이다

1. 재고는 상품·핫딜 정보와 다른 테이블에 둔다

  • 상품 재고 ProductStock(실물 / 예약), 핫딜 재고 HotDealStock(잔여) 두 테이블 — 전체 관계는 데이터 모델
  • 재고는 주문마다 수정되고 상품 정보는 등록 후 거의 바뀌지 않는다
    • 한 행에 두면 상품 정보를 고치는 작업이 구매 차감과 같은 행 락을 두고 서로 기다린다
    • 지금은 상품 수정 기능이 없지만, 생기면 그 경합이 구매 경로 안으로 들어온다
  • 차감 지점이 한 곳이라, 차감 방식만 교체하여 같은 부하를 다시 측정할 수 있었다

트레이드오프

대가대응
핫딜 등록이 3단계로 늘었다 (상품 재고 예약 → 핫딜 → 핫딜 재고)한 트랜잭션으로 묶어 중간에 실패하면 전부 되돌린다
재고를 따로 조회해야 한다구매가 몰리는 경로는 핫딜 재고 한 행만 봐서, 늘어난 조회가 부하 경로 밖이다

2. 핫딜 수량은 상품 재고에서 떼어 온다

  • ProductStock이 재고 원본이다
    • 창고에 실제 있는 수를 실물, 핫딜에 떼어 둔 수를 예약으로 나눠 갖는다
    • 판매 가능 수량은 컬럼으로 저장하지 않고 실물 − 예약으로 그때그때 계산한다
    • 저장하면 실물이나 예약이 바뀔 때마다 같이 고쳐야 하고, 어긋나면 그대로 버그가 된다
  • 구매가 몰리는 경로는 핫딜 재고 한 행만 수정한다. 상품 재고는 핫딜 등록과 결제 확정에서만 건드리므로 경합에서 비켜나 있다

트레이드오프

대가대응
상품 재고의 예약은 상품당 합계 하나라, 그 값만으로는 핫딜별 몫을 알 수 없다핫딜별 예약량은 hot_deals.total_quantity(등록 후 불변)이고, 판매·대기 수량은 주문이 핫딜을 참조하므로 분해된다. 합계와 개별값이 어긋나지 않는지는 재고 장부 검증식이 확인한다

3. 세 방식을 같은 조건에서 측정한다

  • 낙관적 락(@Version), 원자적 조건부 UPDATE, Redis + Lua
  • 비관적 락과 분산 락(Redisson)은 재지 않았다
    • 결과가 이론으로 예측돼 측정 이득이 낮다
    • 비관적 락은 락을 기다리는 동안 DB 커넥션을 쥔다. 처리량이 락 보유 시간에 묶인다
    • 분산 락은 락을 얻고 푸는 데 Redis를 두 번 더 왕복한다. Redis 직접 차감보다 느리다
  • 무엇을 재고 무엇을 이론으로 접을지 고르는 것 자체가 판단이다

4. 차감은 원자적 조건부 UPDATE 한 문장

UPDATE hot_deal_stock SET remaining_quantity = remaining_quantity - :qty
 WHERE hot_deal_id = :id AND remaining_quantity >= :qty
  • 확인(WHERE)과 차감(SET)이 한 문장이라 그 사이에 다른 요청이 끼어들 틈이 없다
    • 영향 받은 행이 없으면 품절이다
    • 충돌도 재시도도 없다
  • 읽어서 판단하고 쓰는 방식은 위험하다
    • InnoDB의 일반 SELECT는 스냅샷을 읽어(MVCC) 남이 방금 차감하고 커밋한 결과를 못 본다
    • UPDATE의 WHERE는 스냅샷이 아니라 최신 커밋 값으로 평가된다
  • 선정한 이유
    • 쿼리 한 문장이라 단순하다
    • 재고를 DB 한 곳에서만 관리한다
  • 낙관적 락은 고경합에서 1,000건 중 163건만 성공해 탈락
  • Redis + Lua는 미채택
    • 재고를 Redis에서 관리하게 된다
    • DB 동기화와 유실 복구가 따라온다

5. 앱과 인원을 늘리면 — 무엇이 재현되고 무엇이 안 되는가

앱 1대와 3대를 나란히 두고 인원을 100에서 3,000까지 올리며 각 지점을 6회씩 쳤고, 같은 격자를 세 번 돌렸다. 실측값은 벤치마크 RFC 4절에 있고, 여기에는 그 값으로 무엇을 판단했는지만 적는다.

세 실행에서 일관된 것 — 결정의 근거로 쓴다

  • 재고 행 락 경합이 실재하고, 앱을 늘리면 커진다
    • 조건부 UPDATE의 락 대기 누적이 앱 대수에 따라 열 배 넘게 늘어난다
    • 대기 횟수는 요청 수와 같으므로 악화의 실체는 건당 대기 시간이다
    • Redis는 재고 행을 수정하지 않아 정확히 0이다
  • 커넥션 풀이 병목이고, Redis는 그 대기를 절반 가까이 줄인다
    • 획득 대기 누적이 조건부 481초, Redis 258초다
    • 차감 UPDATE가 락을 기다리는 동안 커넥션을 놓지 않기 때문이다
    • 락 대기 누적과 같은 이야기를 커넥션 쪽에서 본 것이다
    • 순간값으로 판정하면 정반대로 읽힌다
      • 사용 중 커넥션은 조건부 30(상한)·Redis 10(3분의 1)이라 "Redis는 여유가 있다"로 보인다
      • 누적으로 재면 Redis도 258초를 기다린다
      • 락 경합에서 겪은 함정을 커넥션에서 되풀이할 뻔했다
  • 정확성은 인원에도 앱 대수에도 무관하다
    • 전 구간에서 초과 판매 0건, 품절 경합에서 성공은 정확히 재고 수량만큼이다
  • 순간을 찍는 관측으로는 락 경합이 보이지 않는다
    • Innodb_row_lock_current_waits는 전 스냅샷 0인데 누적 델타(Innodb_row_lock_time)는 수백 초다
    • 대기가 짧고 잦으면 순간 관측은 놓친다

결론을 내지 못한 것 — 결정의 근거로 쓰지 않는다

  • 두 전략의 지연 우열
    • 인원 2,000 이상에서 실행마다 뒤집힌다
    • 회차를 늘려도 좁혀지지 않는다. 부하 도구와 서버가 한 기기에 있어 편차의 원인이 측정 대상 밖에 있기 때문이다
  • 고부하 구간의 절대값
    • 그 구간부터 연결이 성립하지 않는 요청이 나온다
    • 유실분은 지연에 잡히지 않아 값이 낙관적으로 편향된다

앞선 판단 중 철회한 것

  • 이 절은 한동안 "조건부와 Redis의 지연 차이를 락 경합이 만든 몫으로 읽는다"고 적고 있었다
  • 두 전략의 지연 차이가 실행마다 부호까지 바뀌므로 그 차이를 어떤 원인에도 귀속시킬 수 없다
  • 락 경합이 실재한다는 판단은 유지된다. 근거가 두 전략의 지연 차이가 아니라 락 대기 누적과 커넥션 점유로 바뀌었을 뿐이다

저장장치와 격리 — 전환 판단에 직접 걸리는 둘

  • 디스크가 끼면 양쪽이 함께 나빠진다
    • tmpfs에서 도출한 SLA를 실제 저장장치에서는 조건부가 못 맞춘다
    • 락 대기가 세 배로 늘기 때문이다
    • Redis도 주문 INSERT 때문에 비슷한 배수로 느려진다
  • Redis는 조회 영향을 45% 줄이지만 격리하지는 못한다
    • 재고 부하와 무관한 조회를 같이 흘렸더니 조건부에서 크게 밀렸고 Redis에서 그 절반 가까이로 줄었다
    • 커넥션 획득 대기가 46% 준 것과 감소율이 맞아떨어져 인과가 분명하다
    • 그래도 무부하 대비 수십 배는 남는다. 주문 요청이 재고 차감을 Redis로 보내고도 사용자·상품·핫딜 조회와 주문 INSERT로 DB를 계속 치기 때문이다
    • 격리의 조건은 Redis를 쓰는 것이 아니라 요청 경로에서 DB를 걷어내는 것이고, 이 구현은 경합하는 한 행만 뺐다

그래서 전환 판단은

  • 얻는 것은 측정됐다
    • 커넥션 획득 대기가 46% 줄고, 그만큼 무관한 조회가 덜 밀린다(45%)
    • 순간값이 아니라 누적으로 잰 값이고, 회차마다 두 값이 함께 움직인다
  • 대가도 분명하다 — 재고의 단일 진실이 Redis로 옮겨간다
    • 현재 구현은 재고를 Redis에서만 차감한다
    • DB의 재고 행은 갱신되지 않고, Redis가 유실되면 재고가 그대로 사라진다
    • 벤치마크는 초과 판매 검증을 Redis에서 읽어 통과시키지만, 운영에서는 그 자체가 위험이다
  • 같은 이득을 더 싸게 얻을 길이 아직 안 열려 있다
    • Redis가 줄인 46%는 락 대기가 커넥션 점유를 늘리던 몫이다
    • 남은 258초는 풀 30개를 요청 1,000건이 나눠 쓴 몫이다
    • 풀 크기는 HikariCP 기본값 그대로 두고 쟀다
  • 지금 전환하지 않는다
    • 이득이 없어서가 아니라, 재고 원본을 옮기지 않고 같은 지점을 건드리는 수단을 아직 안 써봤기 때문이다
    • 커넥션 풀 튜닝이 먼저고, 그다음이 경합하는 행을 쪼개는 것(SKIP LOCKED)이다
    • 둘 다 재고의 단일 진실을 DB에 남긴다
  • 전환한다면 정합성 작업이 선행이다. DB 반영·유실 복구·만료 복원을 갖춘 뒤라야 이득과 대가를 같은 저울에 올릴 수 있다
  • 전환 수단 자체는 준비돼 있다. stock.deduct.strategy 설정값으로 Redis, 그다음은 재고를 여러 행으로 분산하는 것. 락 대기가 앱 대수에 따라 커진다는 관측은 후자를 가리킨다

6. 락 순서와 실패 처리

  • 주문과 재고를 함께 건드리는 모든 경로는 주문 → 재고 순서를 지킨다 (교착 방지)
  • 코드에 쓴 호출 순서가 그대로 SQL 순서가 된다 — 통합 테스트 SQL 로그로 확인했다
    • 주문은 ID가 IDENTITY라 save() 시점에 INSERT가 나간다. DB가 채번하므로 커밋을 기다릴 수 없다
    • 재고 차감은 JPQL 벌크 UPDATE라 호출 시점에 바로 나간다. 영속성 컨텍스트의 쓰기 지연은 엔티티 변경 추적에만 적용되고 벌크 연산은 그 경로를 타지 않는다
    • 두 SQL 사이에 다른 문장이 끼지 않았다. 앞서 조회한 엔티티를 아무도 수정하지 않아 함께 내보낼 변경이 없었기 때문이다
  • 그래서 이 순서는 Hibernate가 정리해 주는 것이 아니라 코드가 지켜야 한다. 다른 ID 전략을 쓰면 INSERT가 커밋 시점으로 밀려 순서가 뒤집힌다
  • 만료 일괄 처리는 주문 1건 = 트랜잭션 1개
  • 경합에 밀린 요청은 "다시 시도해 주세요"로 돌려준다
    • 서버가 몰래 재시도하지 않는다
    • 첫 시도가 사실 성공했는데 응답만 늦은 경우 중복 주문이 되기 때문
