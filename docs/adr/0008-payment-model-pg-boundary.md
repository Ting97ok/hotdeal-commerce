# ADR-0008. 결제 모델(1:N)과 PG 경계 — 어댑터

- 상태: 확정 · 작성: 2026-06-11
- 관련 규칙: [가설 9 슬라이스 3·10](../design/hotdeal-purchase-hypothesis.md) · [erd 3](../design/erd.md) · [ADR-0001 토스](0001-payment-gateway-toss.md)

## 컨텍스트

결제 시도가 여러 번일 수 있다(카드 한도 초과 후 다른 카드로 재시도). 이를 어떻게 기록하고, 토스라는 특정 PG 에 대한 의존을 어디까지 허용하나.

## 결정 1 — Order : Payment = 1 : N, 행 단위 = paymentKey 1개

**영수증 비유**: 시도 1(신한카드, 실패)에 토스가 영수증 번호 A(paymentKey)를, 시도 2(국민카드, 성공)에 B 를 발급한다. **A 와 B 는 토스 입장에서 별개의 결제 객체 2개**다 — 한 결제의 두 상태가 아니다. 그래서 "영수증 1장 = 1행".

| 대안 | 평가 |
|---|---|
| Payment 1행(주문당) + PaymentHistory 테이블 | 실무에 존재하는 패턴. 그러나 메인 행을 시도마다 덮어쓰면, 토스 통보(웹훅)가 **옛 paymentKey** 로 도착했을 때 메인에서 못 찾고 이력 테이블을 뒤져야 함 — "기록용" 테이블이 운영 경로에 들어와 역할이 섞임. 근본적으로 A·B 는 다른 객체라 "한 칸+이력"이 모델 착오 — 기각 |
| **1:N, paymentKey 단위 (채택)** | 덮어쓰기 자체가 없음. 통보 매칭이 운영 테이블에서 끝남. 실패 이력 = CS·분쟁·정산 증빙 |

- 같은 멱등키로 승인을 재시도하면 토스가 **같은 paymentKey** 를 반환 → 새 행이 아니라 기존 행 갱신(유니크 충돌 = 같은 시도의 멱등 재시도로 해석).
- 진짜 "이력"(한 paymentKey 의 상태 변천·웹훅 수신 원문 보관)은 슬라이스 3 에서 필요해지면 별도 추가 — 지금은 과설계.
- **승인 성공이 주문당 1건**인 것은 Payment 가 아니라 주문 상태 전이(PENDING→PAID 1회)가 보장.

## 결정 2 — PG 보편 구조라 벤더 의존이 아니다

"PG 거래마다 고유 식별자"는 토스 고유가 아니라 업계 보편: 토스 paymentKey · 포트원 imp_uid · 나이스 TID · Stripe charge id. 우리 모델의 약속은 "Payment 행 = **PG 거래 1건**"이고 이는 이식 가능하다. 정산·대사·CS 분쟁도 어차피 PG 의 거래 ID 기준 — 그 단위 기록은 의존이 아니라 결제 도메인의 본질.

## 결정 3 — 어댑터 구조 (PG 의존은 경계에서 차단)

진짜 의존이 생기는 지점에 **어댑터**(Adapter — 외부 시스템을 우리 계약에 끼워 맞추는 변환 구현체. DDD 의 부패 방지 계층(Anti-Corruption Layer)과 같은 역할)를 둔다:

```
PaymentFacade(트랜잭션 밖) → PaymentGatewayClient(계약 인터페이스) 
                              └ TossPaymentClient(어댑터 — 변환) → TossHttpClient(전송)
DB 상태 전이·복원은 PaymentService(@Transactional)
```

| 층 | 역할 | 규율 |
|---|---|---|
| `PaymentGatewayClient` (인터페이스) | **도메인 언어 계약** — 승인/취소/조회 | 시그니처에 토스 DTO 노출 금지 |
| `TossPaymentClient` (어댑터) | **변환** — 토스 상태 10여 개를 우리 결과(승인/재시도 가능 실패/재시도 무의미/상태 불명)로 접고, 에러코드를 우리 비즈니스 부류로 분류 | 토스 지식 전부 여기 격리 |
| `TossHttpClient` | **전송만** — HTTP 호출·인증/멱등키 헤더·타임아웃 | 판단 로직 0, 얇게 |

- 변환은 계층 간 DTO 매핑(우리끼리 모양 바꾸기)과 다르다 — **남의 어휘가 비즈니스 로직에 못 들어오게 국경에서 바꾸는 것**이고, 상태 접기·에러 분류라는 정책 결정을 포함한다.
- 인터페이스 채택의 즉시 효용: **테스트 대역**(가짜 구현으로 승인 성공/실패/타임아웃 시나리오 제어) 끼움 지점 + MSA 경계([ADR-0002](0002-monolith-first-partial-msa.md)) 선긋기. 비용은 인터페이스 파일 1개 — 사실상 0.
- **정직한 한계**: 구현이 토스 하나인 동안 계약의 PG 중립성은 검증 불가 — 이 구조는 "교체 보장"이 아니라 **"교체 지점 격리"** 다(수술 범위를 어댑터 1곳으로 모음).
- 범위 밖: 다중 PG 동시 수용(공통 에러 정규화·PG 선택 라우팅) — 두 번째 PG 가 실제로 필요해질 때.

## 결정 4 — 네이밍 컨벤션 (외부 연동 계층)

계약 인터페이스 `{역할}Client` / 어댑터 구현 `{벤더}{도메인}Client` / HTTP 전송 `{벤더}HttpClient`.
(예: `PaymentGatewayClient` / `TossPaymentClient` / `TossHttpClient`. "PG-" 접두 클래스명은 PostgreSQL 연상 충돌이 있어 풀네임 사용.)

## 함께 묶이는 방어 (슬라이스 3)

- 멱등 2겹: 내부 = 활성 유니크([ADR-0005](0005-one-per-user-active-unique.md)) / 외부 = 토스 멱등키.
- 이중 승인 방어: 토스의 주문번호 중복 승인 거부(1차) + PAID 전이 1회(2차) + 돈만 나간 승인은 즉시 토스 취소(보정).
- 금액 검증: 서버가 주문 시점 저장 금액으로.
- **실패 분류별 주문 처리(방향 — 슬라이스 3 확정)**: 재시도 가능 실패(한도 초과 등) = 제한시간 내 같은 주문 유지(1:N 의 존재 이유) / 재시도 무의미 = 즉시 취소+복원(`cancel_reason=PAYMENT_FAILED` 는 후자 전용).
