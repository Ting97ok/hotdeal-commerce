# 주문 — 의사결정 기록

선착순 주문이 **재고를 언제 잡고 언제 놓는지**, 한 사람이 얼마나 살 수 있는지 정한 기록.
재고를 어디에 두고 무엇으로 차감하는지는 [재고 동시성 ADR](concurrency.md)에 있다.

**결론**

- 재고는 주문을 만들 때 잡는다. 결제 성공을 기다리지 않는다
- 잡은 것을 놓는 일은 주문 상태 전이가 성공한 한 번에만 붙인다
- 한 사람이 같은 핫딜에 살아 있는 주문을 1건만 갖도록 DB 유니크가 막는다
- 절대 지키는 것은 둘이다. 재고보다 많이 팔지 않는 것, 성공이라 답했으면 주문이 반드시 있는 것

---

## 1. 재고는 주문을 만들 때 잡는다

- 주문 생성 트랜잭션에서 재고를 차감하고 주문을 `PENDING` 으로 만든다. 결제는 그 뒤다
- 결제 승인 뒤에 차감하면 선착순의 의미가 깨진다
  - 재고 10에 100명이 "살 수 있다"는 상태로 결제까지 들어와 90명이 결제 직후 실패한다
  - 결제에 들어올 인원을 재고에 맞추려면 결국 어딘가에서 미리 세어야 하고, 그러면 지금 구조와 같아진다
- 잡고 나서 확정하는 2단계가 선착순 실무의 표준이다. 인터파크 예매도 좌석을 잡아 두고 시간을 제한하며 미결제면 푼다 ([리서치 9.1·10.3](../design/research-flash-sale.md))

트레이드오프

| 대가 | 대응 |
|---|---|
| 잡아만 두고 결제하지 않는 주문이 재고를 묶는다 | 제한시간이 지나면 만료 처리가 자동으로 푼다(3절). 값은 `order.payment-timeout` 에 두었고 현재 10분이다 |

## 2. 잡는 기준은 주문 생성 API 성공이다

- 핫딜 화면이나 주문서에 들어가는 것은 아무것도 잡지 않는다. "구매하기"를 눌러 주문 생성이 성공한 순간이 잡은 시점이다
- 화면 진입에서 잡으면 구경만 하고 떠난 사용자가 재고를 묶는다
- 결제창을 여러 개 띄워 선점을 쌓는 것은 주문 생성을 또 불러야 해서, 활성 유니크(4절)가 막는다

## 3. 놓는 일은 상태 전이가 성공한 한 번에만 붙는다

- 주문 상태를 바꾸는 것은 모두 조건부 갱신 한 문장이다. 만료 취소도 결제 선점도 `PENDING` 을 조건으로 건다
- 재고를 되돌리는 일은 **영향 받은 행이 1일 때만** 같은 트랜잭션에 붙는다

```sql
-- 만료 취소
UPDATE orders SET status = 'CANCELED', cancel_reason = 'EXPIRED'
 WHERE id = :id AND status = 'PENDING'

-- 결제 선점
UPDATE orders SET status = 'PAID'
 WHERE id = :id AND status = 'PENDING' AND expires_at > :now
```

- 같은 주문을 두 곳에서 되돌리려는 경합은 반드시 생긴다. 여러 서버의 만료끼리, 그리고 만료와 결제 선점 사이에서
  - 둘 다 되돌리면 재고 수치가 실제 남은 물량보다 커지고, 늘어난 만큼 더 팔린다
  - 전이는 한 번만 성공하므로 되돌리기도 한 번이다. 별도의 락 없이 전이 자체가 관문이다
- 겹쳐도 진 쪽이 그 사실을 안다
  - InnoDB에서 UPDATE의 WHERE는 스냅샷이 아니라 최신 커밋 값으로 평가되고, 남이 잠근 행이면 기다린다. 먼저 커밋한 쪽이 이긴다
  - 진 쪽은 영향 받은 행이 없어 자기가 졌음을 안다. 만료 대상을 미리 조회해 골라도 낡을 수 있는 값이라, 관문은 주문별 조건부 UPDATE다
- 만료 처리는 주문 1건이 트랜잭션 1개다. 한 건이 실패해도 나머지가 진행되고, 실패한 건은 다음 번에 다시 본다
- 여러 서버가 동시에 만료를 돌려도 무해해서 분산 락(ShedLock)을 넣지 않았다
  - 이긴 서버만 되돌리고 나머지는 영향 행이 없어 건너뛴다. 넣는다면 정확성이 아니라 낭비를 줄이는 선택이다
- 만료 판정(`expiresAt < now`)은 각 인스턴스의 시계를 쓴다. 호스트 시각이 동기화(NTP)돼 있다는 전제다
  - 동기화된 오차는 수 ms 라 제한시간 10분 판정에 무해하다
  - DB `NOW()` 단일 기준으로 바꾸지 않는다. 앱에서 `now` 를 주입해야 테스트가 시각을 고정할 수 있다
- 이 보장은 재고 차감이 DB일 때 성립한다. Redis 전략은 재고 연산이 DB 트랜잭션과 함께 되돌아가지 않아 전환하려면 그것부터 풀어야 한다. 운영 기본값은 조건부 UPDATE다
- 결제는 성공했는데 주문이 취소되는 경우는 순서를 바꿔 없앴다. `PAID` 전이가 토스 승인 호출보다 앞에 있다 ([결제 ADR 4절](payment.md))
  - 승인에 성공한 주문은 이미 `PAID` 라서 만료 후보(`PENDING`)에 남지 않는다
  - 남는 틈은 승인 직후 우리 기록이 유실되는 것 하나고, 그때도 주문은 `PAID` 라 해소 스캔이 빠진 결제 기록을 채운다
  - 취소된 주문을 되살리는 규칙은 **코드에 없다.** 늦게 도착하는 성공 신호를 받게 되면 그때 필요해진다

트레이드오프

| 대가 | 대응 |
|---|---|
| 여러 서버가 같은 주문을 겹쳐 처리해 일이 낭비된다 | 전이가 한 번만 성공하므로 결과는 같다. 낭비가 부담이 되면 분산 락으로 줄인다 |

## 4. 계정당 살아 있는 주문 1건 — DB 유니크가 막는다

`orders` 에 저장 생성 컬럼(다른 컬럼 값으로 DB가 자동 계산해 저장하는 컬럼)을 두고 복합 유니크를 건다.

```sql
is_active TINYINT GENERATED ALWAYS AS (IF(status IN ('PENDING','PAID'), 1, NULL)) STORED,
UNIQUE KEY uk_orders_active (user_id, hot_deal_id, is_active)
```

- 유니크 제약은 NULL을 유일성 검사에서 제외한다. NULL은 "값이 없음"이라 서로 비교되지 않기 때문이다 (SQL 표준이라 PostgreSQL도 같다)
  - 그래서 취소된 주문은 몇 건이든 쌓이고 살아 있는 주문만 1건으로 묶여, 취소 뒤 재구매가 열린다
- 앱에서 "이미 샀나?"를 조회하고 INSERT 하는 방식만으로는 못 막는다. 확인과 쓰기 사이에 다른 요청이 끼어든다
- 그래서 두 겹으로 둔다. 앱 가드가 대부분을 사유와 함께 거절하고(`ALREADY_PURCHASED`), 통과한 나머지는 유니크가 최종으로 막는다(위반도 같은 코드로 돌려준다)
- 이 컬럼은 엔티티에 매핑하지 않는다. JPA가 생성 컬럼에 값을 쓰려 드는 함정을 피한다
- 유니크 하나가 중복 클릭·네트워크 재시도·결제창 다중 오픈을 함께 막아, 별도의 멱등 키 없이 내부 멱등이 해결된다
- `(user_id, hot_deal_id)` 완전 유니크는 취소 뒤 재구매를 막아 쓸 수 없었다. 활성 행을 넣고 지우는 보조 테이블도 실무에 흔하지만, 테이블과 동기화 코드가 늘어 택하지 않았다

트레이드오프

| 대가 | 대응 |
|---|---|
| MySQL에는 일부 행에만 거는 유니크 인덱스(부분 유니크 인덱스)가 없어 생성 컬럼으로 우회한다 | 집행이 마이그레이션 DDL 한 곳에 모여 있고 엔티티에 매핑하지 않아, PostgreSQL로 옮기면 부분 유니크로 바꾸는 것으로 끝난다. 자바 코드는 손대지 않는다 |
| "최대 N건"은 유니크로 표현할 수 없다 | 건수 상한이 필요해지면 메커니즘을 바꾼다(5절). 그 비용은 지금 유니크를 걸든 안 걸든 같다 |

## 5. 수량 상한은 주문당만 걸었다

- 한 주문에 담는 수량은 핫딜이 정한 `maxPerOrder` 까지다. 넘으면 `EXCEEDS_PURCHASE_LIMIT`
- "계정당 1건"과 `maxPerOrder` 는 다른 축이다. 앞은 살아 있는 주문 **건수**, 뒤는 한 주문의 **수량**이다
- 주문 금액은 특가 × 수량으로 주문 시점에 저장하고, 핫딜 재고도 같은 수량 단위로 차감한다
- **계정당 총량 상한은 두지 않았다**
  - 여러 번 나눠 사려면 첫 주문이 끝나야(만료되거나 결제되어야) 둘째 주문이 가능하다. 계정당 1건이 걸려 있는 동안은 누적 자체가 생기지 않는다
  - 도입한다면 `is_active` 를 `PENDING` 만으로 다시 정의하고 결제 완료 누적을 세야 한다. 유니크로는 표현할 수 없는 카운트라 메커니즘이 바뀐다

## 6. 절대 지키는 것 둘, 받아들이는 것 하나

| 실패 | 사용자 피해 | 판정 |
|---|---|---|
| **초과 판매** (재고보다 많이 팔림) | 산 줄 알았는데 못 받음 | **0건** |
| **거짓 성공** (성공이라 답했는데 주문이 없음) | 산 줄 알았는데 없음 | **0건** |
| **정직한 실패** (재고가 남았는데 실패 응답) | 다시 누르면 살 수 있음 | 허용 |

- 앞의 둘은 협상 대상이 아니고, 마지막은 불편할 뿐이라 받아들인다
  - 올리브영 사례의 "미발급 0.014%도 치명적"은 성공이라 답하고 주지 않은 쪽 이야기다 ([리서치 1](../design/research-flash-sale.md))
- 서버가 몰래 재시도하지 않는다
  - 덜 팔리는 것을 없애려고 안에서 다시 시도하면, 첫 시도가 사실 성공했는데 응답만 늦은 경우 주문이 둘 생긴다
  - 경합에 밀린 요청은 잔여가 부족하면 `SOLD_OUT`, 이미 산 핫딜이면 `ALREADY_PURCHASED` 로 그대로 돌려준다
- 부수 효과로 방식별 "성공 수"가 그대로 비교 지표가 된다. 낙관적 락이 1,000건 중 163건만 성공해 탈락한 것이 그 예다 ([재고 동시성 ADR 4절](concurrency.md))
- 거짓 성공이 없는지는 200 응답 수와 실제 주문 행 수를 맞대어 확인한다. 지금은 구매 동시성 테스트 한 곳에 있다

## 7. 방어는 겹치기가 아니라 분업이다

각 층은 다른 층이 못 하는 일을 맡는다.

| 층 | 막는 것 | 다른 층이 대신 못 하는 이유 |
|---|---|---|
| 앱 검증 (판매 기간·이미 산 주문) | 명백한 실패를 사유와 함께 거절 | DB 제약 위반은 왜 안 되는지 알려주지 않는다. 판매 기간은 DB 제약으로 표현 자체가 안 된다 |
| DB 유니크·조건부 UPDATE | 동시 경합 | 앱의 확인은 확인과 쓰기 사이 끼어듦에 무력하다. 최종으로 줄을 세우는 것은 DB만 할 수 있다 |
| CHECK 제약 | 검증을 건너뛴 미래의 경로 | 코드가 뚫려도 데이터가 망가지는 것은 막는다. UPDATE당 비교 한 번이라 비용이 사실상 없다 |
| 장부 검증식 | 설계 결함 | 테스트에서만 돌아 운영 비용이 0이다 |

- CHECK는 9개를 걸었다. 그중 잔여 수량 0 이상 제약이 차감 쿼리의 WHERE와 겹으로 음수 재고를 막는다
- **재고만은 미리 읽지 않는다**
  - 읽은 값은 낡을 수 있어 판단에 쓸 수 없고, 관문은 어차피 조건부 UPDATE다 ([재고 동시성 ADR 4절](concurrency.md))
  - 대가는 재고가 없어 실패할 요청도 주문 INSERT까지 갔다가 되돌아온다는 것이다. 실패가 대부분인 폭주에서 이 비용이 얼마인지는 재보지 않았다
- 취사 원칙은 "그 층이 막는 것이 실재하고 비용이 효용보다 작으면 켠다"이다. FK 제약은 비용이 효용보다 커서 뺐고([참조 무결성 ADR](integrity.md)), 되돌리기는 조건부 전이 하나가 가장 정확해서 겹치지 않았다(3절)

**장부 검증식**

```
총 수량 = 남은 재고 + 살아 있는 주문의 수량 합
주문당 승인된 결제 ≤ 1
PAID 주문 ↔ 승인된 결제 1:1
```

- 지금 도는 것은 첫 줄뿐이다. 구매 동시성 테스트 한 곳에서 "잔여 = 초기 재고 − 판매 수량"으로 확인하되 주문을 살아 있는 것만으로 거르지는 않고, 아래 두 줄은 시나리오별 단언으로만 있다
