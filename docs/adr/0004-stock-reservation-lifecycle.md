# ADR-0004. 재고 선점·복원 생명주기

- 상태: 확정 · 작성: 2026-06-11 · 갱신: 2026-07-03 (결정 4 충돌 처리 — 이행 우선 → 취소+보상, 실무 사례 반영)
- 관련 규칙: [가설 4·5](../design/hotdeal-purchase-hypothesis.md) · [erd 4](../design/erd.md)

## 결정 요약

- **무엇을**: 재고는 **주문 시 선점**(결제 후 차감 ❌), 복원은 조건부 상태 전이가 성공한 **정확히 한 번**만. 성공한 결제는 재고 재확보로 **되살림 우선**, 재확보 불가 충돌만 취소+환불+보상 통보.
- **왜**: 선착순 = "먼저 잡은 사람". 결제 후 차감은 그 의미가 깨져 재고 10에 100명이 결제까지 진입해 90명이 결제 직후 실패한다.
- **버린 대안**: 결제 승인 후 차감(선점 없어 경험 붕괴 + 결국 선점 구조로 회귀) / 무통보 강제 환불(시장 관행보다 과보호 + 물리 재고 부재 시 이행 불능)
- **범위 밖(Non-Goal)**: 승인 후 환불 자동화(빈도 낮음 — 수동), 만료 취소 전 토스 조회(**미구현 확정** — 선점 순서 재배치로 필요 소멸, 잔여는 [ADR-0008](0008-payment-model-pg-boundary.md) B2 해소)
- **트레이드오프**: 얻음 = 선착순 의미 보존 · 오버셀 0이 예외 없는 단일 불변식 ↔ 잃음 = 유령 선점(만료 복원이 처리) · dual-write 잔여(외부 결제↔우리 DB 비원자 — 비동기 해소 필요)
- **가역성**: **Type1** — 재고 차감 시점은 주문 상태기계·보상 흐름 전체를 결정하는 뼈대라, 나중에 바꾸면 슬라이스 전부가 흔들린다.

## 컨텍스트

선착순 구매에서 "재고를 언제 차감하느냐"가 주문 상태 전이·보상(되돌리기) 흐름 전체를 결정한다. 또한 결제라는 외부 호출이 끼므로, 차감의 반대 방향(복원)이 안전해야 한다 — 잘못 복원하면 재고 수치가 실제보다 커지고 그만큼 더 팔려 오버셀이 된다.

## 결정 1 — 주문 시 선점 (결제 승인 후 차감 ❌)

주문 생성 트랜잭션에서 재고를 차감하고 주문을 PENDING 으로 만든다. 결제는 그 뒤.

**대안 비교**
- **결제 승인 후 차감**: 선점이 없어 유령 선점 문제는 없지만 — 재고 10개에 100명이 "구매 가능" 상태로 결제까지 진입해 90명이 결제 직후 실패하는 경험 붕괴 + 결제 가능 인원을 재고 수에 맞추려면 결국 어딘가에서 선점·카운트를 해야 하는데, 그러면 '주문 시 선점'과 똑같은 구조가 된다. 기각.
- **주문 시 선점(채택)**: 예약형 2단계(선점 → 확정)가 선착순 실무 표준 — 임시 예약 후 결제 성공 시 확정, 미결제는 일정 시간 뒤 자동 해제(보통 5~15분). [리서치 9.1](../design/research-flash-sale.md). **공식 1차 확인**: 인터파크 FAQ 가 같은 구조(좌석 선점·시간 제한·미결제 시 해제)를 명시 — [리서치 10.3](../design/research-flash-sale.md). 대가인 "유령 선점"은 만료 복원(슬라이스 2)이 처리.

## 결정 2 — 선점 기준 = 주문 생성 API 성공 (화면 진입 ❌)

핫딜 화면·주문서 진입은 아무것도 선점하지 않는다. "구매하기" 클릭 → 주문 생성 API 성공 = 선점.

- 화면 진입 선점은 구경만 하고 떠난 사용자가 재고를 묶는 유령 선점을 양산.
- "결제창 여러 개 띄워 선점 쌓기"는 주문 생성을 또 호출해야 하므로 활성 유니크([ADR-0005](0005-one-per-user-active-unique.md))가 차단.

## 결정 3 — 복원은 정확히 한 번 (조건부 상태 전이)

복원(재고 +)은 `status='PENDING' → 'CANCELED'` **조건부 갱신이 성공(영향 행 1)한 그 트랜잭션에서만** 수행하고, 취소 사유(`cancel_reason`)를 기록한다.

- 만료 처리와 결제 실패 처리가 **같은 주문을 동시에 취소**하려는 경합은 반드시 생긴다. 둘 다 복원하면 재고 수치가 실제 남은 물량보다 +2 커지고, 그 늘어난 만큼 추가로 팔려 결국 재고보다 많이 팔리게 된다.
- 상태 전이는 한 번만 성공하므로(DB 가 직렬화) 복원도 한 번 — 별도 잠금 없이 전이 자체가 잠금 역할. 이 단층 설계가 가장 단순하고 정확해서 여기엔 방어를 겹치지 않았다([ADR-0006](0006-correctness-invariants-defense-layers.md) 의 취사 원칙).

### 동작 원리 — 승인과 취소가 같은 순간에 겹치면

전이는 "상태를 읽고 → 판단 → 갱신"이 아니라 **조건부 갱신 한 문장**이다:

```sql
-- 승인:      UPDATE orders SET status='PAID'     WHERE id=? AND status='PENDING'
-- 만료 취소: UPDATE orders SET status='CANCELED' WHERE id=? AND status='PENDING'
```

확인(WHERE)과 쓰기(SET)가 한 문장이라 사이에 끼어들 틈이 없다. 그리고 InnoDB 에서 **SELECT 는 트랜잭션 시작 시점의 스냅샷(사진)을 읽지만, UPDATE 는 항상 최신 커밋 상태를 기준으로 평가하며 남이 잠근 행이면 대기**한다:

```
승인 트랜잭션 A                        만료 취소 트랜잭션 B
UPDATE … SET PAID WHERE PENDING
 → 행 잠금 획득 + 1행 변경(미커밋)       UPDATE … SET CANCELED WHERE PENDING
                                       → 같은 행 잠금 대기 ⏸
COMMIT (PAID 확정)
                                       → 잠금 해제 → 조건을 최신 상태로 재평가
                                       → 이미 PAID → 영향 행 0 = 전이 실패
                                       → 복원 실행 안 함 ✅
```

- 만료 작업이 후보를 SELECT 로 골라 "PENDING 으로 보였다" 해도 그건 낡을 수 있는 사진일 뿐 — 관문은 주문별 조건부 UPDATE 다(영향 행 0이면 건너뜀).
- 역순(취소가 먼저 커밋)이면 승인 쪽 전이가 0행 — "돈은 나갔는데 주문은 취소됨"을 알게 된다. 이 경우는 강제 환불이 아니라 **결정 4(결제 성공이면 이행)** 로 처리한다. **어느 쪽이 이기든 진 쪽이 항상 그 사실을 안다.**

## 결정 4 — 결제가 성공했다면 반드시 이행한다 (강제 환불 ❌)

**언제 문제가 되나**: 토스 승인은 성공해 돈이 빠져나갔는데, 그 직후 서버 다운·응답 유실로 우리 DB 가 그 사실을 기록하지 못함 → 주문이 PENDING 인 채 만료될 수 있다. 이 회원은 선착순 안에 들어 주문을 잡았고 제한시간 안에 결제도 성공했다 — 취소된 이유는 **오직 우리 시스템이 결제를 제때 기록하지 못한 것**뿐이다.

원칙: **성공한 결제는 재고 재확보로 되살리는 것을 우선하고, 재확보가 불가능한 충돌만 통보·보상을 동반한 환불로 종결한다(무통보 환불 금지).** 결제 성공 신호(동기 응답 / 웹훅 / 만료 처리 중 토스 조회)가 도착했을 때 주문 상태별 처리:

| 주문 상태 | 처리 |
|---|---|
| PENDING | `PENDING→PAID` 전이(1회). 확정 |
| CANCELED(만료로 취소·재고 복원됨) | **재고 재확보 시도**(조건부 차감). ① 확보 성공 → `PAID` 로 되살림(만료 때 복원했던 단위를 도로 가져오는 것 = 순효과 0, 오버셀 없음). ② 확보 실패(그 사이 재판매됨) → 드문 진짜 충돌 → **취소 확정 + 자동 환불 + 보상 지급·고객 통보** (2026-07-03 갱신 — 실무 표준: [무신사 품절 취소 시 판매가 비례 적립금 보상](https://www.consumernews.co.kr/news/articleView.html?idxno=720925). 구 정책 "고객 이행, 초과 1단위 운영 흡수"는 시장 관행보다 과보호 + 물리 재고 부재 시 이행 불능이라 교체) |
| PAID | 멱등 무시(이미 처리됨) |

- 외부 시스템의 성공과 우리 DB 커밋은 **하나의 원자 작업으로 묶을 수 없다**(토스 호출은 트랜잭션 밖) — 분산 시스템의 고전 문제라 원천 차단은 불가능하고, 위 규칙으로 수습한다.
- **오버셀 0 과의 관계**: 정상 구매 경로의 오버셀 0 은 그대로 절대 불변이다. 경계에서 ⓐ 미결제 단위를 남들이 사게 복원 / ⓑ 결제 성공한 당첨자에게 물건 이행 / ⓒ 오버셀 0 — 셋 중 둘만 가능하다. 만료 취소 전 토스 조회가 이 상황을 드물게 만들고, 그래도 발생하는 극히 드문 충돌에선 **ⓐ+ⓒ 를 지키고 ⓑ 는 보상으로 대체**한다 — 취소+환불+보상 통보(2026-07-03 갱신). 오버셀 0 이 예외 없는 단일 불변식으로 단순해지는 부수 효과가 있다.
- **만료 취소 전 토스 조회**는 이 충돌을 줄이는 보조 수단으로 구상했으나 **구현하지 않았다**(2026-07-19 확정) — 결제 선점(`markPaid`)이 토스 승인 앞으로 재배치되면서([ADR-0008](0008-payment-model-pg-boundary.md) 슬라이스4·B1) 승인 성공한 주문은 이미 PAID 라 만료 후보(PENDING)에 남지 않는다. 잔여(승인 후 기록 유실)는 만료가 아니라 **B2 해소**(IN_DOUBT·PAID 고아 스캔 — [payment system 설계](../payment/api-design-system.md))가 담당하고, 위 표(CANCELED 행)의 되살림 규칙은 웹훅 등 늦은 성공 신호 도입 시를 위한 원칙으로 보존한다.

## 보류 해소 (슬라이스 2 — 2026-06-23)

아래 보류 항목은 슬라이스 2 설계에서 확정했다. 운영 상세·플로우는 설계 문서로 모은다 → [order System API 설계](../order/api-design-system.md).

- **만료시각 최종값**: `PT10M` 확정(`order.payment-timeout`, application.yml). 리서치 권장대역 5~15분 내.
- **판매 종료 ↔ 결제 허용**: 만료 판정은 `order.expiresAt`만 본다("판매 종료는 새 주문에만" — 진입 고객은 자기 결제창까지 보호). 판매종료·관리자 중단 ↔ 결제 차단은 슬라이스 3 결제 관문이 `expiresAt`를 요청 시점에 직접 확인.
- **만료 처리 방식**: DB 만료 스케줄러(`@Scheduled`). Redis 키 TTL은 만료 알림이 재시작 유실·전달 비보장이라 백업 만료 처리가 또 필요 → 제외([리서치 9.2절](../design/research-flash-sale.md)).
- **다중 서버 중복 실행**: 잠금 없이 허용 — 슬라이스2 동시 만료 처리는 둘 다 HotDealStock을 복원하므로 **HotDealStock `@Version`(낙관락)이 복원 1회를 보장**(두 번째 복원이 version 충돌→롤백, 동시성 테스트로 증명)해 중복 만료 처리가 무해하다. 결정 3의 조건부 전이(주문 상태 관문)는 **슬라이스3 만료↔결제**(주문엔 @Version 없음)에서 필요. 중복 만료 처리 비용은 부하 측정 후 필요 시 Redis ShedLock(최적화)으로 추가 — 스케일아웃 트레이드오프 인지.
