# 애플리케이션 구조 — 의사결정 기록

계층을 어떻게 나누고, 무엇을 강제하고, 규칙이 틀렸을 때 어떻게 바꾸는지를 정한 기록.

앞의 문서들이 이 시스템이 부딪힌 문제를 다룬다면, 이 문서는 **부딪히기 전에 갖고 들어온 기본값**이다.
유지보수는 팀에서 값이 나오고, 기본값을 정해두지 않으면 매번 다시 정하게 된다.
규칙 자체는 [CLAUDE.md](../../CLAUDE.md) 에 있고, 여기에는 **그렇게 정한 이유**를 적는다.

**결론**

- 계층은 넷이고 **예외를 두지 않는다.** 예외 하나가 다음 사람에게는 선례가 된다
- **트랜잭션을 여는 곳은 Facade 뿐이다.** 여는 방법은 필요가 정한다
- 인터페이스는 **외부 시스템 경계에만** 둔다. 구현이 하나뿐인 자리에는 두지 않는다
- **벤더 지식은 도메인 밖에 둔다.** 자리는 변경 이유로 가른다
- 규칙이 틀렸다고 판단되면 바꾼다. **바꾸는 범위는 일정이 정한다**

---

## 1. 계층은 넷이고 Facade 에 예외를 두지 않는다

```
Controller → Facade → Service → Repository
```

- 조합할 것이 없어 **위임 한 줄로 끝나는 Facade 도 만든다.** 로그아웃은 토큰 저장소를 부르는 것이 전부인데 Facade 를 거친다
- "조합이 없으면 Controller 가 Service 를 직접 부른다"는 예외를 두지 않는다
  - 그러면 **매번 "조합이 있나"를 판단해야 하고, 그 판단은 사람마다 갈린다**
  - 오늘 위임 한 줄이어도 내일 조합이 붙는다. 그때 Controller 를 고쳐야 하고, 고치는 사이 경계가 흐려진다

**예외는 위반보다 위험하다.** 규칙을 어긴 코드는 리뷰가 잡지만, 예외로 허용된 코드는 남아서 **다음 사람이 규칙을 다시 읽는 근거**가 된다.

- 실제로 팀원이 이렇게 말한 적이 있다 — **"어디는 Service 를 받아 쓰길래 써도 되는 줄 알았다."** 규칙을 어긴 것이 아니라 코드에서 규칙을 재구성한 것이다
- 문서를 아무리 정확히 써도 막히지 않는다. 사람은 문서보다 옆 코드를 먼저 본다

**얻는 것은 성능이 아니라 믿음이다.** **어느 도메인을 맡든 사이드 이펙트가 엉뚱한 도메인에서 터지지 않는다고 믿을 수 있다.**

- 도메인 사이 의존이 Facade 한 곳으로만 흐르니 **숨은 호출 경로가 없다.** 내가 고친 것이 어디까지 가는지 코드에서 찾을 수 있다
- Service 가 여기저기서 불리면 호출처를 전부 뒤져야 하고, 뒤지다 빠뜨린 것이 다른 도메인에서 터진다
- 영향이 없다는 뜻이 아니라 **영향 범위를 찾을 수 있다**는 뜻이다. 그래야 코드를 빨리 고친다

### 없는 계층은 예외가 아니다

계층에는 성격이 둘이다.

| 성격 | 계층 | 언제 존재하나 |
|---|---|---|
| **도메인 고유** — 그 도메인을 벗어나지 않는다 | entity · service · repository | 도메인이 있으면 항상 |
| **진입점** | controller · facade | 외부 진입점이 있을 때만 |

- 회원·상품·재고에 Facade 가 없는 것은 **예외가 아니라 결과**다. 자체 API 가 없으니 진입점 계층을 만들 이유가 없고, 그 도메인 로직이 필요한 쪽은 규칙대로 Facade → Service 로 들어온다
- 회원 API 가 생기면 Facade 도 생긴다. 규칙이 바뀌는 것이 아니다

**그래서 정확한 형태는 "예외를 두지 않는다"가 아니라 "판단을 요구하는 예외를 두지 않는다"이다.**

- "진입점이 있나"는 사실이라 판단이 필요 없다. 없는 것을 안 만들 뿐이다
- "조합이 있나"는 오늘의 상태라 내일 뒤집힌다

트레이드오프

| 대가 | 대응 |
|---|---|
| 하는 일이 없는 계층이 생긴다. 파일이 늘고 호출 스택이 깊어진다 | 저울의 반대편은 읽는 사람의 오해와 그것을 잡는 리뷰 부담이다. 후자가 훨씬 크다고 봤다 |
| 규칙을 기계로 강제할 수 없다 | 리뷰가 최종 수단이고 100%는 없다는 것을 전제로 둔다 |

## 2. 트랜잭션을 여는 곳은 Facade 뿐이다

- 한 덩어리로 묶이면 `@Transactional`, **중간에 외부 호출이 끼어 쪼개야 하면 `TransactionTemplate`** 을 쓴다. 템플릿은 Facade 에서만 쓴다
- Service 의 `@Transactional` 은 **경계가 아니라 합류**다. Service 를 Facade 없이 부르는 경로를 만들지 않는다
- `readOnly` 를 포함한 트랜잭션 속성은 **경계를 연 쪽의 선언만 유효**하다. 합류하는 쪽의 선언은 무시된다
- **DB 를 쓰지 않는 흐름은 트랜잭션을 열지 않는다.** 토큰 저장소만 건드리는 로그아웃이 그렇다

**어노테이션만으로는 부족해서 템플릿이 필요했다.** 프레임워크 제약이다.

- 프록시 기반이라 같은 클래스 안의 호출에는 걸리지 않는다
- 메서드 단위라 **"이 메서드의 앞 절반"을 표현할 방법이 없다.** 그런데 외부 호출을 트랜잭션 밖으로 빼려면 정확히 그것이 필요하다

기각한 대안이 둘이다.

- **트랜잭션을 묶기 위한 Service 나 Facade 를 하나 더 만든다** — 읽는 사람이 "이건 왜 있는 클래스지"를 판단할 수 없다. 이름으로 드러나지 않는다
- **전용 계층을 새로 만든다** — 일반적으로 없는 계층이라 **새 사람이 올 때마다 설명해야 한다.** 그 비용이 얻는 것보다 크다

기존 규칙을 깨지 않고 작은 규칙 하나를 더하는 쪽을 골랐다.

트레이드오프

| 대가 | 대응 |
|---|---|
| 람다로 감싸므로 어노테이션보다 읽기 나쁘고, 트랜잭션 여부가 시그니처에 안 드러난다 | 쪼개야 하는 곳에만 쓴다. 대부분의 Facade 메서드는 어노테이션 그대로다 |
| 경계가 Facade 에 있다는 것을 알아야 Service 의 어노테이션을 합류로 읽을 수 있다 | 규칙을 문서에 명시한다. 이것만으로 안 되면 리뷰가 잡는다 |

## 3. 인터페이스는 외부 시스템 경계에만 둔다

- Service·Facade 는 전부 구체 클래스다. 구현이 하나인데 인터페이스를 씌우면 파일이 늘고 따라갈 곳이 한 겹 깊어진다
- 재고 차감은 인터페이스를 뒀다. **구현이 실제로 둘이고 설정으로 갈아끼운다**
- 결제 게이트웨이는 구현이 하나다. 인터페이스를 두되 **그것이 무엇을 벌어주는지는 정확히 적어 둔다**

**인터페이스가 버는 것은 셋이고, 어휘 격리는 그중에 없다.**

- **호출부 안정성** — 구현을 갈아도 호출부를 안 고친다
- **의존 방향** — 도메인이 인프라를 모른다. 인터페이스를 지우면 호출부의 본문은 그대로지만 import 가 벤더 구현을 가리켜, 도메인이 인프라를 알게 된다
- **구현 공존** — 인터페이스가 없으면 두 구현이 같이 못 산다. 설정으로 고르는 수단 자체가 막힌다

**경계에서 벤더 어휘를 막는 것은 반환 타입이다.**

- 외부 응답과 예외를 우리 결과 타입으로 접어 돌려주면, 호출부가 받는 것은 그 결과뿐이다
- 반대로 반환 타입을 벤더 응답으로 바꾸면 **인터페이스가 있어도** 벤더 어휘가 위로 샌다. 인터페이스는 누가 부르는지를 가리지 무엇이 넘어오는지를 가리지 않는다

**정직한 한계**: 구현이 하나인 동안 그 계약이 벤더 중립인지는 확인할 수 없다. 이 구조가 주는 것은 교체 보장이 아니라 **교체할 자리를 한 곳에 모은 것**이다.

## 4. 벤더 지식은 도메인 밖에 둔다

- 벤더의 요청·응답 타입은 우리 비즈니스가 아니라 **그 회사의 API 명세**다. 벤더가 필드를 바꿔 도메인 파일이 바뀌면 변경 이유가 섞인 것이라, 벤더 구현은 도메인 밖에 둔다
- 역할을 벤더보다 위에 둔다. 같은 역할의 구현들이 한자리에 모여야 **교체 후보가 보이고**, 벤더 이름만으로는 무슨 연동인지 드러나지 않는다
- **enum 을 종류로 모으면 짝이 갈린다.** 레코드와 그 필드 타입이 다른 폴더로 나뉘어, 한 개념이라는 것이 안 보인다
- **요청 DTO 를 command 로 다시 매핑하지 않는다.** 인바운드 입구가 하나라 대부분 필드가 같은 복사본이 되고, 검증 선언이 두 곳으로 갈린다. 입구가 둘 이상 되면 그때 도입한다
- 영속은 JPA 를 기본으로 한다. 특정 경로에서 벗어나는 판단은 **그 경로의 문서가 근거와 함께 소유한다**

## 5. 규칙은 바뀐다 — 세 갈래로 갈린다

| 갈래 | 그대로 두면 | 판단 | 코드 변경 |
|---|---|---|---|
| **틀린 판단** | 부채가 계속 쌓인다. 새 코드마다 잘못이 복제된다 | **바꾼다** | 크다 |
| **규칙 공백** | 다음 사람이 또 각자 판단한다 | **발견 즉시 메운다.** 저울질할 대상이 없다 | 거의 없다 |
| **더 나은 방법** | 손해가 고정이다. 지금 것도 동작한다 | **저울질한다.** 감당할 수 있는지부터 본다 | 크다 |

- 무지해서 잘못 정한 것이라면 **과감히 바꾼다.** 부채를 너무 두려워하면 레거시에 남는다
- 반대로 유행을 좇아 매번 바꾸면 **한 저장소 안에 여러 세대의 코드가 공존한다.** 그래서 도입 전에 내가, 또는 팀이 그 리팩터링을 감당할 수 있는지를 먼저 본다

**바꾼 범위는 일정이 정한다.** 이것은 엔지니어링 판단이 아니라 비즈니스 판단이다.

- 개발자의 0순위는 비즈니스가 원하는 시점에 제품을 내는 것이다
- 여유가 있으면 옛 코드까지 고친다. **촉박하면 새 코드부터 적용하고 남은 부채를 백로그에 명확히 남긴다**

**컨벤션 지적의 근거는 사람이 아니라 문서다.**

- 이 저장소에서 그 문서는 [CLAUDE.md](../../CLAUDE.md) 다. **사람과 AI 가 같은 문서를 본다** — 컨벤션을 두 벌로 두면 둘이 갈린다
- 문서에 없는 것을 개인 판단으로 지적하면, **받는 쪽은 문서와 지적 중 무엇을 따를지 알 수 없다**
- 그래서 문서를 항상 최신으로 둔다. **바뀐 시점은 본문에 적지 않는다** — git 이 이미 갖고 있고, 손으로 적은 날짜는 안 고쳐지면 틀린다
- **코드가 문서와 다르면 코드가 낡은 것이다.** 옛 방식으로 쓰인 코드를 따로 표시하지 않는다. 표시하는 순간 그것도 관리 대상이 된다
  - 1절의 오해가 여기서 닫힌다 — **코드는 규칙의 증거가 아니다**
- 규칙을 바꿀 권한이 어디 있는지는 조직이 정한다

## 6. 확인하지 못한 것

- **검증 범위가 좁다.** 소규모 팀 경험에서 나온 판단이라, 인원이 늘 때 "문서가 유일한 근거"를 유지하는 비용이 어디서 꺾이는지는 확인하지 못했다
- **예외가 선례가 된 사례는 한 건을 직접 겪었다.** 나머지는 그 한 건에서 밀어낸 추론이고, 모든 규칙에 관찰이 있는 것은 아니다
- 이 규칙들이 **다음 프로젝트에서 처음부터 적용됐을 때** 어떻게 되는지는 아직 모른다. 트랜잭션 경계처럼 이번에 사후로 정리된 것이 섞여 있다
