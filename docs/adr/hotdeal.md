# 핫딜 — 의사결정 기록

핫딜은 이 서비스가 기간을 정해 여는 판매 행사다. 가격과 수량을 정해 열고, 지금은 한 핫딜이 상품 하나를 판다.
기간 없이 상시로 값을 내리는 것은 핫딜이 아니라 상품 가격의 문제다.

**돈이 아니라 신뢰와 트래픽을 사는 장사다.** 미끼 상품이라 팔수록 손해일 수 있고, 그래서 수량 한정이 생명이다.
행사가 남기는 것은 매출이 아니라 "여기 핫딜은 진짜다"라는 신뢰다. 초과 판매 0건이 협상 대상이 아닌 이유가 여기 있다.

"지금 살 수 있는가"를 무엇으로 판단하고 운영자에게 무엇을 열어 줄지 정한 기록이다.
재고를 어디에 두고 무엇으로 차감하는지는 [재고 동시성 ADR](concurrency.md), 언제 잡고 언제 놓는지는 [주문 ADR](order.md)에 있다.

**결론**

- 진행·매진을 상태값으로 저장하지 않는다. 판매 기간과 재고를 그때 읽어 판단한다
- 그래서 스케줄러가 없다. 시작 시각이 지나면 열리고, 재고가 없으면 닫힌다
- 한 핫딜은 상품 하나를 판다. 여러 상품을 묶지 않는다
- 등록한 핫딜은 고치지 않는다. 바꾸려면 취소 후 새로 열고, 물량을 더하려면 새 회차를 연다
- 취소된 핫딜은 토스를 부르기 전에 막는다. 막는 자리는 신규 주문과 결제 승인 둘이다

---

## 1. 진행·매진은 저장하지 않고 그때 읽어 판단한다

- `status` 는 `ACTIVE` 와 `CANCELED` 둘뿐이다. 예정에서 진행으로, 진행에서 종료로 넘어가는 전이 상태값을 두지 않는다
- 판단은 쿼리가 한다. 주문이 상품으로 활성 핫딜을 찾을 때 이 조건을 본다

```sql
WHERE product_id = :productId AND status = 'ACTIVE'
  AND start_at <= :now AND :now < end_at
```

- 저장된 단계값을 읽지 않는다. 시각 비교가 곧 "지금 열려 있나"이다
- 매진은 이 조건에 없다. 재고 차감이 영향 행 0으로 답하는 것이 매진이다
- 상태값을 두면 그 값을 갱신하는 순간과 실제가 어긋난다
  - 임계 경로가 표시를 믿는 순간 그 어긋남이 초과 판매가 된다
  - 정확성은 재고 차감의 원자성이 보장한다. 상태값은 현실과 어긋날 수 있는 표시일 뿐이다
- 단계를 전이시키는 생명주기는 `Order`(`PENDING`에서 `PAID` 또는 `CANCELED`로)가 이미 담당한다
- 정시 오픈이 "시작 시각 도달"이라 스케줄러 인프라가 통째로 불필요해진다
  - 실무 모델도 같다. 쿠팡 골드박스 매일 7시, 카카오 정시 오픈([실무 사례 3절](../design/research-flash-sale.md))
- 만료 스케줄러는 있지만 그것은 **주문** 만료다([주문 ADR 3절](order.md)). 핫딜 상태를 바꾸는 스케줄러는 없다

트레이드오프

| 대가 | 대응 |
|---|---|
| 매진 여부로 거르려면 핫딜과 재고를 함께 읽어야 한다 | 표시가 틀려도 최악은 "살 수 있어 보였는데 눌러 보니 실패"다. 상태 컬럼을 두면 같은 어긋남이 초과 판매가 된다 |
| 그만큼 읽기가 무거워진다 | 캐시와 인덱스로 푸는 종류다. 정합성으로 갚지 않는다 |

## 2. 한 핫딜은 상품 하나를 판다

- 여러 상품을 한 핫딜에 묶지 않는다. 상품과 핫딜이 1:N인 것은 한 상품의 여러 회차를 뜻한다
- 이유는 증명하려는 것이 경합 재고 한 행이기 때문이다
  - "상품 하나 = 경합 재고 한 행"이 이 저장소의 측정 단위다([재고 동시성 ADR 1절](concurrency.md))
  - 여러 상품을 묶으면 재고 단위가 갈려 동시성 초점이 흐려진다
- 한 핫딜이 여러 상품을 담게 되면 이 테이블이 둘로 갈린다
  - `hot_deals` 가 행사 자신(이름·기간)을 맡고, `hot_deal_products` 가 상품별 특가와 수량을 맡는다
  - 지금 한 행이 미래의 (핫딜 1 + 핫딜 상품 1)이다
- 전환 비용은 국소적이다
  - 운영 중이면 한 번에 이름을 바꾸지 않고 새 구조를 먼저 세운 뒤 옛 구조를 걷는 단계 마이그레이션으로 한다
  - DB FK 제약이 없어([참조 무결성 ADR](integrity.md)) 변경이 `hot_deals` 주변에 머문다. 타 도메인이나 API 계약으로 번지지 않는다

## 3. 같은 상품의 판매 기간이 겹치면 등록을 거부한다

- 겹치면 같은 상품이 같은 시각에 두 가격으로 팔린다
- MySQL에 기간 배타 제약이 없어 등록 API의 검증으로 막는다

```sql
-- 겹침 판정
h.start_at < :endAt AND :startAt < h.end_at
```

- 기존 시작이 신규 끝보다 앞이고 신규 시작이 기존 끝보다 앞이면 겹친다
- 둘 다 strict 비교라 앞 핫딜의 끝과 뒤 핫딜의 시작이 맞물리는 경우는 겹침이 아니다
- 동시 등록 두 건이 검증을 같이 통과하는 경합은 다루지 않았다
  - 이 저장소가 증명하는 동시성은 사용자 구매 경합이고, 관리자 조작끼리의 경합은 그 축이 아니다
  - 같은 등록 안에서도 재고 예약 경합은 구매와 같은 자원을 건드려 검증했다([재고 동시성 ADR 4절](concurrency.md))
  - 필요해지면 등록을 직렬화한다(상품 행 락)
- 핫딜이 단일 가격(`dealPrice`)이라 한 상품 다단 할인은 담기지 않는다
  - "선착순 30개 50% + 70개 30%"를 두 핫딜로 열면 위 겹침 금지에 막히고, 한 핫딜 안의 가격 티어로 두려 해도 담을 컬럼이 없다
  - 필요해지면 가격 티어를 별도 행으로 더하거나 겹침 규칙을 완화한다

## 4. 등록한 핫딜은 고치지 않는다

- 총 한정 수량은 등록 후 불변이다. 엔티티에 수정 메서드 자체가 없다
- 변경은 취소 후 재등록, 추가 물량은 새 회차 등록이다
- **정직한 인정**: 운영자가 물량을 다시 채우는 재입고 증량도 실무에 실재한다(올리브영 재입고 기획전 — [실무 사례 4절](../design/research-flash-sale.md)). 금지의 근거는 "업계 표준이라서"가 아니다
- 실제 이유는 스코프 선택이다
  - "품절 후 다시 살 수 있게 되는" 요구는 두 경로로 이미 재현된다. 취소·만료 복원([주문 ADR 3절](order.md))과 회차 재오픈(카카오 100개씩 3차례 — [실무 사례 3절](../design/research-flash-sale.md))이다
  - 증량을 열면 관리 API·검증·테스트가 한 벌 더 늘어난다
  - 가격 오류 대응도 수정이 아니라 긴급 차단이 통례다

**증량을 연다면 두 숫자를 한 트랜잭션에서 올린다**

- 검산식이 하나 있다. `총 수량 = 남은 재고 + 살아 있는 주문의 수량 합`([주문 ADR 7절](order.md))
- 100개 중 30개가 팔린 핫딜을 150개로 늘리면 총 수량과 남은 재고를 같이 올려야 한다. 총 수량만 먼저 올리면 그 순간 검산이 어긋난다
- 한 트랜잭션에 넣으면 중간 상태가 밖에서 보이지 않아 검산이 항상 맞는다. "등록 후 불변"은 그때 해제한다

## 5. 취소된 핫딜을 어디서 막나

막는 자리는 둘이고, 둘 다 통합 테스트로 명세돼 있다.

| 막는 자리 | 무엇이 막나 | 사용자가 받는 것 |
|---|---|---|
| 신규 주문 | 활성 핫딜 조회의 `status = 'ACTIVE'` 조건 | 구매 가능한 활성 핫딜 없음 (404) |
| 결제 승인 | 주문 선점 트랜잭션 안의 취소 확인 | 취소된 핫딜은 결제 불가 (409) |

- 결제 승인 검사는 **토스 호출 앞**이다. 돈이 움직이기 전에 거부한다
  - 취소의 대표 목적이 가격 오류 긴급 차단인데, 새 구매만 막으면 이미 결제창을 연 사람들이 취소 뒤에도 계속 확정되는 구멍이 남는다
- 취소 뒤의 방침
  - 이미 결제 완료된 주문은 유효하다. 환불 자동화는 범위 밖이라 필요하면 토스 대시보드에서 수동으로 한다
  - 미결제 주문은 만료로 자연 취소된다. 일괄 강제 취소를 만들지 않아 재고 복원 경로가 하나로 유지된다

**상태를 뒤집는 API 는 만들지 않았다.** 관리자 1인 운영이라 운영자가 DB 로 한다. 여기서 정할 것은 어디서 막느냐이고 그 답이 위 표다.

- 테스트도 같은 방식으로 취소한다. 핫딜 행의 상태를 직접 뒤집고 두 경로가 막히는지 본다. API 가 없어도 가드는 명세된다

---

**제외** — 이 저장소의 관심사는 고경합 주문·결제다. 공개 조회 API와 관리자 취소 API는 그 관심사 밖이라 만들지 않았다.
