# ADR-0006. 정확성 불변식과 방어 계층 분업

- 상태: 확정 · 작성: 2026-06-11
- 관련 규칙: [가설 4](../design/hotdeal-purchase-hypothesis.md) · [erd 4](../design/erd.md)

## 컨텍스트

선착순 시스템의 "정확성"을 무엇으로 정의하고, 어느 층이 무엇을 책임지나. "이중·삼중 방어는 복잡도·성능 낭비 아닌가"라는 도전에 대한 답을 포함한다.

## 결정 1 — 절대 불변식: 오버셀 0 + 거짓 성공 0. 덜 팔림은 허용

실패를 세 종류로 갈라야 한다:

| 실패 유형 | 사용자 피해 | 판정 |
|---|---|---|
| **오버셀** (재고보다 많이 팔림) | 산 줄 알았는데 못 받음 | **0건 절대** |
| **거짓 성공** (성공 응답인데 실제 주문 없음) | 산 줄 알았는데 없음 | **0건 절대** |
| **정직한 실패** (재고 남았는데 "실패, 다시 시도" 응답) | 다시 누르면 살 수 있음 — 불편할 뿐 | **허용** |

- 올리브영 사례의 "미발급 0.014%도 치명적"은 **거짓 성공**(성공 응답 후 미지급) 이야기다 — 정직한 실패가 아니다([리서치 1](../design/research-flash-sale.md)). 정직한 실패는 재고가 사라지지 않아 비즈니스 손실이 제한적.
- **서버 몰래 재시도 금지**: 덜 팔림을 없애려고 서버가 내부 재시도하면, 첫 시도가 사실 성공했는데 응답만 늦은 경우 **중복 주문**을 만든다 — 배보다 배꼽. 경합 실패는 `PURCHASE_CONFLICT`("다시 시도")로 정직하게 반환.
- 부수 효과: 방식별 "성공 수"가 합법적 벤치마크 지표가 된다(낙관락은 충돌로 10 미만, 비관락/Redis 는 10 도달 — [ADR-0009](0009-stock-concurrency-design.md)).

## 결정 2 — 방어 계층 분업 (이중·삼중이 아니라 분업)

각 층은 **다른 층이 못 하는 일**을 맡는다:

| 층 | 막는 적 | 다른 층이 대신 못 하는 이유 |
|---|---|---|
| 애플리케이션 검증 (입력 검증 + 서비스의 기간·재고·중복 사전 확인) | 명백한 실패의 싸고 사유 있는 거절 | DB 제약 위반은 "왜 안 되는지"를 모름(에러 구분 불가). 판매 기간은 DB 제약으로 표현 자체가 불가 |
| DB 원자성·유니크 | 동시성 경합 | 앱 확인은 "확인↔쓰기 사이 끼어듦"에 원리적으로 무력 — 최종 직렬화는 DB 만 가능 |
| CHECK 제약 | 미래의 버그 (검증 없는 차감 경로 등) | 코드가 뚫려도 데이터 오염만은 차단. UPDATE 당 비교 1회 = 비용 ~0 |
| 정합 검증식 | 설계 결함 | 테스트 전용 — 런타임 비용 0 |

**"최종 방어선(DB) 하나로 충분하지 않나"에 대한 답** — 성공 경로만 보면 맞지만, 플래시세일의 트래픽 프로파일은 반대다(재고 10 / 요청 10만 = 실패가 99.99%):

- DB 만으로: 실패 요청 전부가 트랜잭션 → INSERT → 차감 실패 → **롤백**(되돌리기 + 인덱스 원복 + 예외 비용 + JPA 영속성 컨텍스트 무효화). 쓰기 경로가 실패 폭주를 정통으로 맞음.
- 가드가 있으면: 실패 대부분이 가벼운 읽기에서 `OUT_OF_STOCK` 으로 잘림. 게다가 가드는 **어차피 읽어야 할 데이터**(특가·기간) 위의 if 문이라 성공 경로 추가 비용 ~0.
- → 사전 가드는 방어 중복이 아니라 **실패 폭주 환경의 성능 최적화** (실무의 빠른 거절·대기열·선차단이 전부 같은 원리).

**취사 원칙**: "그 층이 막는 적이 실재하고 비용 < 효용이면 켠다" — FK 는 비용>효용이라 제거([ADR-0003](0003-no-db-fk-constraints.md)), 복원은 단층(조건부 전이 1회 — [ADR-0004](0004-stock-reservation-lifecycle.md))이 가장 정확해서 단층.

## 결정 3 — 정합 검증식 (장부 일치)

모든 동시성 테스트의 마지막 단언:

```
totalQuantity = remainingQuantity + Σ(활성 주문 quantity)
주문당 승인 결제 ≤ 1
PAID 주문 ↔ 승인 결제 1:1   (승인 0건인 PAID = 거짓 성공의 결제판까지 탐지)
```

차감 유실·이중 복원·이중 승인을 한 그물로 잡고, 운영 중 정합 감사 쿼리로 재사용 가능하다.
