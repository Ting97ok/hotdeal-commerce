# 의사결정 기록 (ADR) — 색인

> ADR(Architecture Decision Record) = 설계 갈림길에서 **무엇을, 왜** 선택했는지 남기는 문서.
> 주제 하나가 한 파일이고 번호도 계급도 없다.
> **결정이 바뀌면 새 문서로 대체하지 않고 그 문서를 직접 고친다.** 변경 이력은 git 이 갖는다.
> 그 "왜"가 길어 파일을 따로 열 만할 때만 [RFC](../rfc/) 로 뗀다. 링크는 ADR → RFC 한 방향이다.
> 수록 기준은 **"6개월 뒤 새 멤버가 'X 왜 썼어요?' 물을 결정"** 이다.

## 주제 일곱 편

| 주제 | 답하는 질문 | 무엇을 왜 택했나 (한 줄) |
|---|---|---|
| [인증](auth.md) | 누구인지를 매 요청 어떻게 확인하나 | Redis 를 안 쓰는 것이 아니라 **인증 핫패스에서 뺐다** — 매 요청 검증은 로컬 서명으로 끝나고 Redis 는 재발급 때만 간다. 대가인 "만료 전 무효화 불가"는 **Access 30분 + Refresh 회전 + tokenVersion** 으로 갚고, 동시 재발급 경합은 Redis **`GETDEL` 한 명령**이 막는다 |
| [애플리케이션 구조](architecture.md) | 계층을 어떻게 나누고 무엇을 강제하나 | 계층은 **넷이고 예외를 두지 않는다**(예외 하나가 다음 사람에게 선례가 된다), 트랜잭션을 여는 곳은 **Facade 뿐**, 인터페이스는 **외부 시스템 경계에만**, 벤더 지식은 도메인 밖. 규칙이 틀리면 바꾸되 **바꾸는 범위는 일정이 정한다** |
| [참조 무결성](integrity.md) | 참조를 무엇이 지키나 | FK 를 걸지 않는다 — **조회 성능은 인덱스가 주는 것**이고 FK 는 안 읽는 인덱스까지 강제한다. FK 가 주는 것은 실수 방지 하나인데 대가가 **데이터를 원하는 대로 정리 못 하는 것**이다. 코드 경로는 서비스 가드가, 사람이 DB 를 직접 만지는 경로는 **권한**이 막는다 |
| [주문](order.md) | 재고를 언제 잡고 언제 놓나 | 재고는 **주문 만들 때 선점**(결제 후 차감은 선착순 의미가 깨져 기각), 놓는 일은 **조건부 상태 전이가 성공한 한 번**에만. 계정당 살아 있는 주문 1건은 **DB 활성 유니크**가 막고, 절대 지키는 것은 **초과 판매 0건 + 거짓 성공 0건** |
| [핫딜](hotdeal.md) | 지금 살 수 있는지를 무엇으로 판단하나 | 진행·매진을 **상태값으로 저장하지 않고** 판매 기간과 재고를 그때 읽어 판단한다 — 그래서 스케줄러가 없다. 한 핫딜은 **상품 하나**를 팔고, 등록한 핫딜은 고치지 않는다(변경은 취소 후 재등록, 증량은 새 회차). 취소는 **막는 가드 둘**로만 두었다 |
| [결제](payment.md) | 외부 승인을 우리 데이터와 어떻게 잇나 | PG는 **토스 테스트 모드**(사업자 없이 붙는 것이 탈락 기준), 결제는 **시도(paymentKey)마다 1행**, 토스 호출은 **DB 트랜잭션 밖**이라 자동 롤백 대신 **결과 네 갈래별 명시적 후처리**. 결과를 모르면 되돌리지 않고 남겨 해소가 확정 — 분류 근거는 [결과 분류](../rfc/payment-result-classification.md) |
| [재고 동시성](concurrency.md) | 재고를 어디 두고 무엇으로 차감하나 | 재고는 **전용 테이블**(`ProductStock` 원본 · `HotDealStock` 핫딜 몫), 차감은 3방식 실측으로 고른 **원자적 조건부 UPDATE** — 측정은 [벤치마크](../rfc/concurrency-benchmark.md) |

## 파일 없는 한 줄 결정

파일을 열 만큼 길지 않은 결정은 여기서 끝낸다.

| 결정 | 내용 |
|---|---|
| 구매 흐름·상품 재고 | Product 가 재고 원본을 보관(`ProductStock` 실물·예약·가용)하고 핫딜은 거기서 예약한다. 구매 API 는 **상품 주소**(`POST /api/orders {productId}` — 서버가 활성 핫딜을 찾는다), 주문 모델은 **상품 참조 + 적용 핫딜 기록**이다 — [재고 동시성 ADR 2절](concurrency.md) |
| **주문 식별자** | 공개 카탈로그(상품·핫딜)는 순번 id 를 노출하고, 민감 리소스(주문)는 불투명 `order_no`(UUID, UNIQUE)를 쓴다 — 권한 검증 실수의 안전망 + 주문량(사업 지표) 은닉 + 토스 주문번호 겸용. PK 는 순번을 유지한다(UUID 를 PK 로 쓰면 InnoDB 삽입 성능이 떨어진다). BaseEntity 공통 UUID 는 5개 테이블에 낭비라 두지 않았다 |
| **금액 타입** | 전 금액 컬럼 `DECIMAL(12,0)` / JPA `BigDecimal` — 금액은 정확 십진수가 원칙이고 부동소수점을 쓰지 않는다. BIGINT 대비 소수 확장(할인율·수수료)이 자릿수 변경으로 끝나고 스키마에 "돈" 의미가 드러난다. KRW 전용이면 BIGINT 도 정당하지만 의미와 확장성으로 DECIMAL 을 골랐다 |
| **배포 전제** | 서버 여러 대 — LB 뒤에서 MySQL·Redis 를 공유한다. JVM 락은 자기 프로세스 안에서만 직렬화하므로 무효다. **커넥션 총량 = 인스턴스 수 × 풀 크기** — 앱 3대 × HikariCP 기본 10 을 실측하니 MySQL `Threads_connected` 31 이었다(`max_connections` 151 안). 인스턴스를 크게 늘리면 앱보다 DB 커넥션이 먼저 마른다 |
| 범위 밖 묶음 | 대기열·어뷰징 방어 / 승인 후 환불 / 주문 내역 조회·이어서 결제(만료 후 재구매로 갈음) / 다중 PG 일반화 / **멀티상품 핫딜**(한 핫딜 = 상품 하나 — 확장 경로는 [핫딜 ADR 2절](hotdeal.md)) |
| 슬라이스 순서 | 0 등록 → 1 구매 → 2 만료 복원 → 3 결제 승인 — 어느 시점에 멈춰도 시스템이 자기 완결이다 |
