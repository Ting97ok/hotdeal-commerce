# ADR-0013. 부하 테스트 도구 — k6

- 상태: 확정 · 작성: 2026-06-27
- 관련 규칙: [재고 동시성 ADR](concurrency.md) · [가설 8·9](../design/hotdeal-purchase-hypothesis.md) · [ADR-0001 토스](0001-payment-gateway-toss.md)

## 결정 요약

- **무엇을**: 동시성 벤치마크([재고 동시성 ADR](concurrency.md))의 부하 측정 도구로 **k6**(Grafana) 채택.
- **왜**: 측정의 본질이 "락 방식을 **동일 조건으로 반복** 측정해 비교"라, ① 정밀·재현 가능한 부하 제어와 ② 서버 메트릭(커넥션 풀·교착·충돌률)을 부하 곡선과 한 화면에 겹치는 통합 시각화가 일반 부하 테스트보다 우선이다. k6 + Prometheus + Grafana 가 한 생태계라 둘 다 자연스럽다.
- **버린 대안**: Gatling(부하 제어는 동급이나 서버 메트릭이 자체 리포트와 분리), JMeter(스레드 모델이라 도착률 정밀도 낮고 XML 이라 버전관리·재현 불리)
- **트레이드오프**: 얻음 = 정확한 도착률 제어 · Grafana 통합 대시보드 · JS 진입 낮음 · 단일 바이너리(설치·CI 간편) ↔ 잃음 = JVM 스택과 다른 언어(JS) — 측정 코드만의 분리라 비용 작음
- **가역성**: **Type2**(되돌리기 쉬움) — 도구라 교체 가능, 비용은 시나리오 재작성뿐

## 설계노트

> 결정에 이른 근거·기준·대안 비교. **결정 자체는 위 요약이 정본**이고, 아래는 "왜 그렇게 결정했나"를 보존한다.

### 컨텍스트

[재고 동시성 ADR](concurrency.md)의 동시성 벤치마크는 락 방식(낙관락 · 조건부 UPDATE · Redis)을 **같은 워크로드로 반복** 측정해 비교한다. 그래서 도구 선택 기준이 일반 부하 테스트(처리량 한계 찾기)와 다르다 — 비교 실험이라 **재현성**과 **서버 내부 지표 관측**이 먼저다.

핵심 제약: 재고 동시성 ADR이 보려는 지표(낙관락 충돌률, 비관락의 `hikaricp` 커넥션 풀 포화·교착 횟수)는 **클라이언트가 아니라 앱 서버**에서 나온다. 부하 도구의 클라이언트 지표(처리량·지연)만으로는 부족하고, 앱 메트릭(Micrometer)과 결합해 같은 시간축에서 봐야 "초당 요청 수가 이만큼일 때 풀이 마르고 교착이 터진다"가 드러난다.

### 선택 기준 (우선순위)

| 순위 | 기준 | 이유 |
|:---:|---|---|
| ① | 정밀·재현 가능한 부하 제어 | 3방식을 동일 조건으로 — 도착률(arrival rate, 단위시간당 요청 도착 수)이 흔들리면 비교가 오염됨 |
| ② | 서버 메트릭 통합 시각화 | 핵심 지표가 서버측(풀 포화·교착·충돌률)이라 부하 곡선과 한 화면에 겹쳐 봐야 함 |
| ③ | 세팅·학습 비용 | 1인·4주 일정 |
| ④ | 코드 기반(버전관리·재현) | 시나리오를 git 으로 관리 |

### 후보 비교

| 도구 | ① 부하 제어 | ② 메트릭 통합 | ③ 학습 | ④ 코드 |
|---|---|---|---|---|
| **k6** | 정확한 도착률 모델 | Prometheus+Grafana 한 생태계 | JS — 낮음 | ✅ JS |
| Gatling | 정밀 | 자체 HTML 리포트(서버 메트릭 별도) | Scala DSL — 중간 | ✅ Scala |
| JMeter | 스레드 모델(덜 정밀) | 플러그인 의존 | GUI/XML — 구식 | △ XML |

②가 결정적이다. Gatling 은 ①④ 동급에 JVM 친숙이라 방어 가능하나 서버 메트릭이 리포트와 분리돼 ②에서 손해를 본다. JMeter 는 ① 정밀도·④ 버전관리에서 탈락.

### 결정 — k6

- **측정 스택**: k6(부하 생성) + Micrometer→Prometheus(앱 메트릭 수집) + Grafana(통합 대시보드). k6 결과 메트릭도 Prometheus 로 내보내 한 대시보드에서 부하와 서버 지표를 겹쳐 본다.
- **부하 모델**: 가상 사용자(VU, virtual user — 부하 도구가 흉내 내는 가상 사용자) 1,000명이 각 1건씩 총 1,000건을 소화하는 구성(k6 `shared-iterations`). 계정당 1주문 제한이 있어 사용자 수가 곧 주문 수이고, 3방식이 같은 인원·같은 건수를 받으므로 비교 조건이 동일하다.
- **워크로드·측정 지표 상세**: [벤치마크 설계 문서](../rfc/concurrency-benchmark.md)에서 정의([재고 동시성 ADR](concurrency.md) 측정 지표와 연계).

### 범위 — 부하 대상이 아닌 것

- 토스 결제 승인 구간은 부하 대상이 아니다 — 외부 샌드박스에 부하를 보내면 호출량 제한·차단 위험([ADR-0001](0001-payment-gateway-toss.md) "테스트 모드의 운영 한계"). 부하는 **구매·재고 경합 경로**(주문 생성)에 한정하고, 결제 승인은 테스트 대역으로 대체한다.
