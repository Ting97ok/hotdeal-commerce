# ADR-0010. 동시성 운영 전략 선정 — 원자적 조건부 UPDATE

- 상태: 확정 (로컬 벤치마크 — 저경합·고경합 2구간, 고경합은 격리 자동 스택 재측정) · 작성: 2026-06-29
- 관련 규칙: [ADR-0009 재고 동시성](0009-stock-concurrency-design.md) · [ADR-0013 k6](0013-load-test-tool-k6.md) · [벤치마크 설계](../design/concurrency-benchmark.md)

## 결정 요약

- **무엇을**: 핫딜 재고 차감 운영 전략으로 **원자적 조건부 UPDATE** 채택.
- **왜**: 정확성(오버셀 0)은 모든 구간·전략 동률. **저경합(동시 100·재고 10)** 조건부 최저(p95 266ms < Redis 344 < 낙관락 382). **고경합(동시 1000·재고 2000, 격리 측정)** 조건부 1.37s ≈ Redis 1.48s(동률, 조건부 근소 우위) — 호스트 측정의 "Redis 역전"은 SQL 로깅 오염이었다(아래). 단순(쿼리 1문)·정합 자동인 조건부가 고경합서도 Redis 에 밀리지 않는다. Redis 의 진짜 역전은 단일 행 천장을 넘는 더 높은 경합 구간.
- **버린 대안**: 낙관락 — 재시도 없는 구현이라 고경합서 버전 충돌로 대량 거절(동시 1000서 성공 163/1000), 정확하나 비실용. Redis — 저경합 오버헤드 + 고경합서도 조건부와 동률(우위 아님) + DB 정합 비용 → 기본 제외, 단일 행 천장 초과 시 승격.
- **트레이드오프**: 얻음 = 단순(쿼리 1문)·정확·정합 자동 ↔ 잃음 = 단일 행 쓰기 한계 — 넘으면 Redis/버킷 분산.
- **가역성**: **Type2** — 전략은 `@ConditionalOnProperty(stock.deduct.strategy)` 로 교체 가능.

## 설계노트

### 측정 환경

- 워크로드: 선착순 폭주 — VU별 고유 계정(1인 1주문)으로 `POST /api/orders` 경합 ([k6/order-flash-sale.js](../../k6/order-flash-sale.js)). k6 `setupTimeout` 300s + 주문 지연 전용 `order_duration` 으로 setup(bcrypt 로그인) 지연을 분리.
- **두 구간**: ① 저경합(동시 100·재고 10 — 대부분 빠른 거절) ② 고경합(동시 1000·재고 2000 — 거의 전원이 실제 차감 UPDATE 수행, 단일 행 경합 노출).
- **측정 환경 2종**: (A) 호스트 수동 — 앱 호스트 기동 + SQL DEBUG 로그 on + 공유 MySQL. (B) **격리 자동** — 일회용 컨테이너(MySQL·Redis tmpfs) + 앱 컨테이너(SQL 로그 WARN), [run.sh](../../k6/benchmark/run.sh) 한 번으로 3전략 순회 후 폐기. **(B)가 오염이 적어 신뢰도가 높다** — 고경합은 (B)로 재측정했다.

### 결과

**① 저경합 — 동시 100·재고 10** (환경 A, 거절 위주라 오염 영향 작음)

| 전략 | 성공/재고 | 오버셀 | p95 | avg |
|---|---|:---:|---|---|
| 낙관락(@Version) | 10 / 10 | 0 | 382ms | 148ms |
| **원자적 조건부 UPDATE** | 10 / 10 | 0 | **266ms** | **99ms** |
| Redis+Lua | 10 / 10 | 0 | 344ms | 125ms |

**② 고경합 — 동시 1000·재고 2000** (환경 B 격리, `order_duration`)

| 전략 | 성공/1000 | 오버셀 | p95 | avg |
|---|---|:---:|---|---|
| 낙관락(@Version) | 163 | 0 | 1.44s | 1.03s |
| **원자적 조건부 UPDATE** | 1000 | 0 | **1.37s** | **925ms** |
| Redis+Lua | 1000 | 0 | 1.48s | 1.09s |

- **정확성**: 거짓 성공 0 · 5xx 0%. 초과 판매 0 은 **신청자 > 재고인 저경합(100·재고 10)에서 실측** 확인([ADR-0006](0006-correctness-invariants-defense-layers.md) 절대 불변식). 고경합(재고 2000 > 1000명)은 초과 판매가 구조적으로 불가능 — 표의 0 은 검증이 아니라 당연한 값이다(아래 한계).
- **측정 환경이 결론을 바꿨다**: 호스트 A 에선 조건부 2.25s·Redis 1.44s 로 **Redis 역전**처럼 보였으나, 격리 B(SQL 로그 off + 깨끗한 DB)에선 조건부가 **2.25s→1.37s 로 개선**돼 Redis(1.48s)와 동률이 됐다. 조건부는 차감이 DB UPDATE 라 SQL 로깅·공유 DB 부하에 민감하고 Redis 는 메모리라 둔감 — 오염을 걷어내니 격차가 사라졌다. 앞서 본 "교차점"은 상당 부분 **측정 오염**이었다.
- **낙관락**: 재시도 없는 버전 충돌이 대량 거절(성공 163/1000) — 재고가 남아도 못 판다. 정확성은 지키나 처리량이 비실용(환경 무관 일관).

### 예상 대비 (ADR-0009 "예상 X, 측정 Y, 이유 Z")

- ADR-0009 예상: Redis 처리량 최고. **이 규모(동시 1000)까진 미검증** — 호스트 측정에선 Redis 우위로 보였으나 격리 재측정에서 조건부와 동률로 수렴(오염 제거). Redis 우위는 단일 행 천장을 넘는 더 높은 경합에서 드러날 것 — 이 규모론 미도달.
- 낙관락 예상(고경합 약점)은 적중 — 다만 "재시도 폭증으로 처리량 최저"가 아니라 재시도 없는 구현이라 "충돌 즉시 거절로 성공률 최저"(163/1000)로 나타났다.

### 운영 결정

- **조건부 UPDATE 채택(기본)** — 단순(쿼리 1문)·정합 자동(DB 가 단일 진실)·정확. 격리 측정에서 고경합서도 Redis 와 동률이라, Redis 의 DB 정합 보정 비용·복잡도를 떠안을 이유가 없다. `ProductStock` 운영 방식([ADR-0011 결정4](0011-product-inventory-reservation.md))과 일치해 재고 도메인이 한 방식으로 통일된다.
- **Redis 승격 조건**: 조건부와 동률이 깨지는 지점 — 핫딜 폭주가 단일 행 UPDATE 천장을 넘겨 조건부 지연이 SLA 를 깨면 Redis(+Lua) 전환 또는 재고 버킷 분산([ADR-0009 결정1](0009-stock-concurrency-design.md)). 그 구간은 본 측정(동시 1000)보다 높아 미도달 — 다중 노드 부하로 재측정해 찾는다. 전환 시 Redis→DB 정합을 함께 구현한다.
- 낙관락 배제 — 재시도 없는 구현은 고경합서 성공률 16%(163/1000). 재시도를 붙여도 충돌 폭증 비용이 조건부보다 불리.

### 정직한 한계

- **측정 환경이 결과를 바꾼다(이번 핵심 교훈)**: 호스트(SQL 로그 on·공유 DB)에선 조건부 2.25s 였던 게 격리(로그 off·tmpfs DB)에선 1.37s 로, "Redis 역전"이 사라졌다. DB 의존 전략일수록 환경 오염에 민감 — 그래서 [격리 자동 스택](../../k6/benchmark/run.sh)으로 재현·고정한다.
- **로컬 1머신**이라 절대 천장은 환경 종속(production QPS 천장 아님). 신뢰하는 건 같은 격리 환경의 **상대 비교**(조건부 ≈ Redis ≫ 낙관락)지 절대 수치가 아니다. 부하 생성기·앱·DB 분리 다중 노드 측정은 후속.
- **고경합은 처리량(속도) 측정이지 초과 판매 검증이 아니다** — 신청자(1000) < 재고(2000)라 마지막 재고를 두고 다투지 않는다. 초과 판매 방지(정확성)는 신청자 > 재고인 저경합·통합 테스트가 담당하고, **고경합 품절 경합(재고 < 인원, 예: 1000명·재고 10)은 후속**이다.
- **동시 1000 은 부하로는 타당하나(순간 동시성 기준 큰 부하) 그 숫자 선택은 임의** — 목표 동접 모델이 없다. 인원 곡선(100~2000 스윕)으로 맥락을 주는 건 후속([run.sh](../../k6/benchmark/run.sh) `ACCOUNTS` 변수).
- 각 전략 1회 측정 — 1.37 vs 1.48 차는 노이즈 범위일 수 있어 "동률"로 본다. 다회 평균은 후속.
- Redis 지연은 DB 정합 보정 비용 **미포함**([벤치마크 설계](../design/concurrency-benchmark.md)) — 실제 운영 전환 시 더해진다.
