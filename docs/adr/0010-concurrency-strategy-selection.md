# ADR-0010. 동시성 운영 전략 선정 — 원자적 조건부 UPDATE

- 상태: 확정 · 작성 2026-06-29 · 보완 07-03(SLA·사례)·07-24(다중 인스턴스·용어 '천장'→'한 줄 병목')
- 관련: [ADR-0009 재고 동시성](0009-stock-concurrency-design.md) · [ADR-0013 k6](0013-load-test-tool-k6.md) · [벤치마크 설계·측정 상세](../design/concurrency-benchmark.md)

## 결정 요약

- **무엇을**: 핫딜 재고 차감 = **원자적 조건부 UPDATE**(현재 코드 기본값). redis 는 정합 완성 후 채택 검토(→ [다음 작업](#운영-결정)).
- **왜**: 오버셀 0 은 전 전략 동률. 조건부가 단순(쿼리 1문)·정합 자동으로 저·고경합 최저~동률. 낙관락은 고경합서 성공 163/1000 탈락. **다중 인스턴스(1 vs 3)서 인스턴스를 늘릴수록 redis 가 conditional 을 앞서는 격차**를 관찰(i1 동률 → i3 벌어짐)했으나 로컬 한계로 절대 우위는 미확증.
- **트레이드오프**: 얻음 = 단순·정확·정합 자동 ↔ 잃음 = 단일 행 **한 줄 병목**(넘으면 redis·재고 버킷 분산).
- **가역성**: Type2 — `@ConditionalOnProperty(stock.deduct.strategy)` 로 교체.

## 핵심 결과 ① 스케일아웃은 재고 병목을 못 푼다 — 다중 인스턴스

nginx LB 뒤 앱 **1 vs 3**(conditional·redis)을 격리 스택([run-multi.sh](../../k6/benchmark/run-multi.sh))으로 측정. 부하는 nginx 로 통일해 인스턴스 수만 변수로 뒀다(VU 1000).

![인스턴스 1→3: i1 동률, i3서 conditional 급증·redis 와 격차](../design/images/benchmark-multi-instance.svg)

| 전략 | i1 p95 (동률·순위 요동) | i3 p95 | 행 잠금 대기(누적) |
|---|---|---|---|
| 조건부 UPDATE | 1.1~1.9s | **~4.4s** | 7.5s → **71.6s** |
| Redis+Lua | 1.4~1.5s | **~2.6s** | **0** (행 미접근) |

- **i1 은 동률(측정마다 순위 요동), i3 서 redis 가 격차를 벌린다.** 앱을 늘려 단일 행 압력을 3배로 주니 DB 에 매인 conditional 은 급증(~4.4s), 메모리 차감인 redis 는 완만(~2.6s).
- **이건 "한 줄 병목"이지 자원 포화가 아니다.** 측정 중 DB `Threads_running` 은 **2뿐**(커넥션 31 물렸으나 대부분 락 대기) — 자원이 남는데 외줄로 서서 느린 구조.
- **오버셀 0**(i3 정확히 10)·**커넥션 = N×풀**(HikariCP 합산 30 = DB `Threads_connected` 31)은 인스턴스 수와 무관하게 성립 — 로컬에서도 깨끗한 실측.

**정직한 한계 (이 측정의 값)**: i3 격차의 원인(단일 행 직렬화 vs 로컬 1머신 CPU 경합)은 앱 3개가 한 CPU 를 다퉈 **미분리** · MySQL 이 tmpfs 라 실제 운영의 저장 병목이 없음 · 단일 측정이라 절대값은 노이즈. **신뢰는 방향(i3 격차·행 잠금 폭증)이지 절대 수치가 아니다 — 확증은 부하기·앱·DB 물리 분리 후속.** "격차를 봤지만 이걸로 운영을 성급히 바꾸지 않는다"가 이 측정의 결론.

## 핵심 결과 ② 측정 오염이 결론을 바꿨다 — 단일 인스턴스

![측정 환경이 결론을 바꿨다 — 호스트 Redis 우위가 격리서 소멸](../design/images/benchmark-measurement-pollution.svg)

호스트(SQL 로그 on·공유 DB)선 조건부 2.25s·redis 1.44s 로 **redis 가 앞서는 것처럼** 보였으나, 격리(로그 off·tmpfs)선 조건부가 **1.37s 로 급락**해 동률이 됐다. 조건부는 차감이 DB UPDATE 라 로깅·부하에 민감하고 redis 는 메모리라 둔감 — 오염을 걷으니 격차가 사라졌다. **"측정 환경이 결론을 바꾼다"가 이 프로젝트의 핵심 교훈.**

| 구간 (환경 B 격리) | 조건부 | redis | 낙관락 |
|---|---|---|---|
| 저경합 100·재고10 (p95) | **266ms** | 344ms | 382ms |
| 고경합 1000·재고2000 (p95) | **1.37s** | 1.48s | 1.44s · **성공 163 탈락** |
| 품절 1000·재고10 (정확성) | 정확히 10 | 정확히 10 | 정확히 10 |

전 구간 **오버셀 0 · 거짓 성공 0 · 5xx 0%**. 낙관락은 재시도 없는 버전 충돌로 성공 163/1000 — 정확하나 비실용(탈락). ([ADR-0006 절대 불변식](0006-correctness-invariants-defense-layers.md))

## 한 줄 병목이란

`hot_deal_stock` 단일 행은 한 번에 하나씩만 고쳐(오버셀 방지) 요청이 한 줄로 선다. **자원이 꽉 차서(CPU 100%)가 아니라 외줄 구조라** 대기하는 게 한 줄 병목(직렬화 병목)이다. 그래서 **서버를 늘려도 안 풀리고**(문이 하나), **redis(메모리로 빠른 차감)·재고 버킷 분산(문 여러 개)**으로만 푼다.

## 운영 결정

- **조건부 UPDATE 채택(기본).** 단순(쿼리 1문)·정합 자동(DB 가 단일 진실)·정확. 코드 기본값도 조건부([ADR-0011 결정4](0011-product-inventory-reservation.md) `ProductStock` 과 통일). 낙관락 구현·`version` 컬럼은 측정 후 코드에서 제거(결과는 위 표 보존, 재현은 git).
- **redis 승격 조건 = SLA 위반 시.** redis 이점은 속도(메모리)뿐 아니라 **격리** — 재고 부하가 같은 DB 의 주문·정산으로 번지지 않는다([여기어때](https://techblog.gccompany.co.kr/redis-kafka%EB%A5%BC-%ED%99%9C%EC%9A%A9%ED%95%9C-%EC%84%A0%EC%B0%A9%EC%88%9C-%EC%BF%A0%ED%8F%B0-%EC%9D%B4%EB%B2%A4%ED%8A%B8-%EA%B0%9C%EB%B0%9C%EA%B8%B0-feat-%EB%84%A4%EA%B3%A0%EC%99%95-ec6682e39731)가 Write DB 장애 전파를 든 이유). 대가는 정합·유실 관리 부담. **"대형사가 쓰니까"는 근거가 아니다** — [Shopify(2026)](https://shopify.engineering/scaling-inventory-reservations)는 오히려 redis 를 걷어내고 MySQL `SKIP LOCKED`+재고 1단위 1행으로 고처리량을 냈다. 본질은 'DB 냐 redis 냐'가 아니라 **'단일 행이냐 분산이냐'**. 전환은 오직 SLA 위반.
- **다음 작업 (별도 브랜치)**: 이 격차 관찰을 계기로 redis 를 **정합(DB 싱크·유실 복구)까지 완성**해 채택을 검토한다. 현 redis 는 재고를 Redis 에만 두는 벤치마크용 반쪽이라 정합 완성이 전제. 근거는 "절대 우위"가 아니라 **격차 관찰 + 스케일아웃 대비 + 구현 완성도**이며, 실제 전환·기본값 변경은 구현 완료 후 본 ADR 갱신(코드-문서 일치).

## SLA · 정직한 한계

- **SLA**(주문 `POST /api/orders`): 폭주 **p95 ≤ 2s** / 평시 **≤ 500ms**. 실측 분포에 여유를 붙여 올림([Google SRE Workbook](https://sre.google/workbook/slo-document/) 절차 — 저경합 266ms→500ms, 고경합 1.37s→2s). 사용자경험 상관은 미검증(운영 데이터로 조정 전제). 오버셀 0·거짓 성공 0 은 SLA 가 아니라 절대 불변식.
- **부하 모델**: 동시 1000 VU = 오픈 순간 구매 버튼 동시 클릭 스파이크(실측 역산 ~700 RPS). 일반 CCU 환산 ≈ 2만~6만(Little's Law).
- **로컬 1머신**이라 절대 수치는 신뢰하지 않고 **상대 비교**만 본다. 물리 분리 측정·다회 평균·redis 정합 비용 반영은 후속.
