## 1. 목표와 정체성

### 증명하려는 역량
1. **대량 트래픽 처리** — 쓰기 동시성(핫딜 재고 경합) + **읽기 부하(고트래픽 조회)**
2. **트랜잭션 정합성** — 주문–결제, 실패 시 보상
3. **MSA 환경 플로우 이해** — 이벤트 기반 통신, Saga 보상, 멱등성

### 정체성: "핵심 흐름 + 다역량 각각 깊게"
넓은 기능을 얕게 펼치지 않는다. **두 흐름(① 핫딜 구매=쓰기, ② 고트래픽 조회=읽기)을 프로덕션 수준으로 깊게** 판다.

### 스코프 아웃 (의도적 제외)
- 넓은 커머스 기능(장바구니·리뷰·배송·쿠폰 등)
- 풀 MSA 인프라(게이트웨이·서비스 디스커버리·독립 배포)
- 실 결제 (토스페이먼츠 테스트 모드만)

## 3. 기능 분류 (MoSCoW)

| 분류 | 기능 |
|---|---|
| **Must** | 회원 로그인(JWT) · 상품 조회(기본·시드) · 핫딜 등록/조회 · **핫딜 구매 + 재고 차감 동시성** · **토스 결제 + 주문–결제 트랜잭션 정합성** · 결제 실패/취소 → 재고 복원(보상) · 멱등성 |
| **Should** | ⭐**핫딜 동시성 제어 벤치마크** · ⭐**핫딜 k6 부하 테스트 → 개선** · ⭐**고트래픽 조회 최적화(캐싱·인덱싱·페이징) + 부하 테스트** · 관측(메트릭/로그/알람) · **v2: 결제 후속 Kafka+Saga 전환** |
| **Could** | 대기열 시스템 · PG 추상화 · 주문 내역 조회 · read replica · Grafana · 합성 대량 데이터 확장 테스트 |

⭐ = 포트폴리오 하이라이트.

## 4. 기술 의사결정 요약

| 결정 | 내용 | 근거 |
|---|---|---|
| **도메인** | 커머스 핫딜 | 동시성·트랜잭션이 도메인 본질에서 자연 발생 (주차장 대안: 읽기 중심이라 동시성 인위적 + 합법 데이터 확보 불가) |
| **결제 PG** | 토스페이먼츠 (테스트 모드) | 사업자 없이 테스트 무료 + 에러코드/멱등키 문서 최상 ([결제 ADR 1절](adr/payment.md)) |
| **아키텍처** | 모놀리식 완성 → 결제 후속 한 경계만 MSA 전환 | 강한 일관성(주문/재고)과 최종 일관성(결제 후속)을 경계로 분리 — 전환 설계는 착수 시 |

### 핵심 설계 이슈 (핫딜 결제 깊이의 본체) — 전부 결정 완료
1. **재고 차감 시점** → 주문 시 선점 + 만료 자동 복원 ([주문 ADR 1절](adr/order.md))
2. **외부 결제 호출 ↔ DB 트랜잭션 분리** → 토스 호출은 트랜잭션 밖, 어댑터 구조 ([결제 ADR 3·4절](adr/payment.md))
3. **결제 실패·취소 → 재고 복원** → 조건부 상태 전이가 성공한 1회에만 복원 ([주문 ADR 3절](adr/order.md))
4. **멱등성 2레이어** → 내부 = 활성 유니크([주문 ADR 4절](adr/order.md)) / 외부 = 토스 멱등키
5. **금액 위변조 방지** → 주문 시점 금액 저장 + 서버 검증 (웹훅 서명 검증은 폐기 — 해소는 결제 조회 재확인 방식, [결제 ADR 6절](adr/payment.md))
6. **결과 확정** → 동기 승인 + **해소 스케줄러**(IN_DOUBT·PAID 고아를 토스 재조회로 확정 — Phase B2 구현 완료). 웹훅은 후속 최적화(B3+, 해소 대체 아님)

## 5. 진행 순서 (슬라이스)

- **A. 셋업 + 기반**: ✅ 셋업(Spring Boot 3.5.13/Java 21/MySQL 8.4+Flyway/Redis/Docker) · ✅ 회원 로그인(JWT·RTR·tokenVersion) · ✅ 상품·재고 엔티티·시드 (상품 조회 API 는 고트래픽 조회 D 에서)
- **B+C. 핫딜 본편 (쓰기 · 1차 주연)**: ⓪ 등록 → ① 구매(재고 선점+PENDING, 낙관적 락) → ② 만료 복원 → ③ 토스 결제 승인 → 재고 동시성 3방식(낙관적 락/Redis/원자적 조건부 UPDATE) 벤치마크 + k6 — 비관적 락·분산 락은 이론으로 배제 → 운영 전략 확정 — **확정 슬라이스·스키마는 [기술 가설 9](design/hotdeal-purchase-hypothesis.md)·[ERD](design/erd.md) 기준**
  - **현황(2026-07-06)**: ⓪ 등록 ✅ · ① 구매 ✅ · ② 만료 복원 ✅(스케줄러, 건별 트랜잭션+LIMIT) · ③ 결제 승인 ✅ · 동시성 벤치마크 ✅(3방식 측정, **조건부 UPDATE 채택** [재고 동시성 ADR](adr/concurrency.md)) · **토스 실연동 ✅(Phase B1)** · **IN_DOUBT·PAID 고아 해소 스케줄러 ✅(Phase B2)**. 공개 조회와 관리자 취소 API 는 이 저장소의 관심사 밖이라 만들지 않았다([핫딜 ADR](adr/hotdeal.md)).
- **D. 고트래픽 상품 조회 (읽기 · 2차)**: 목록 조회(페이징/필터) · 인덱스 설계 + 쿼리 최적화(실행계획) · Redis 캐싱 + 무효화 · k6
- **E. v2 결제 후속 MSA 전환**: 경계 분리 · Kafka 프로듀서/컨슈머(멱등) · Saga 보상 · DLT · Before/After 다이어그램
- **F. 관측/마무리**: 메트릭(Micrometer)/로그/알람 · README · ADR

> 진행은 vertical TDD(RED→GREEN→Docs), 슬라이스 단위로 추적한다. 순서는 "본편(쓰기 동시성 → 결제 정합성) → 고트래픽 조회 → 결제 후속 MSA 전환"이며, **고정 기한이 아니라 완수 순서로 관리**한다(강의 종료 후에도 이어서 완성).
