# 진행 상황 노출 + 커밋 체크포인트

> 이 규칙은 `globs` 없이 **항상 로드**된다. CLAUDE.md `## 작업 진행 순서`·`## 하네스` 와 함께 본다.

## 자동 커밋 절대 금지

- **커밋/푸시는 사용자가 직접 수행한다**(글로벌 룰). 작업 단위마다 멈춰 추천 커밋 메시지(한 줄 명령)를 제시한 후 사용자 커밋을 대기.
- 추천 커밋 명령은 **한 줄 bash** 로 제시(따옴표 안 줄바꿈 금지 — Claude Code 터미널 실행 버튼이 노출되려면 single-line 이어야 함):
  ```bash
  git add {파일} && git commit -m "[접두사] {summary}" -m "- {세부1}" -m "- {세부2}"
  ```
- 접두사: `[Feat]` / `[Fix]` / `[HotFix]` / `[Docs]` / `[Test]` / `[Refactor]`.

## 진행 상황 노출 (vertical TDD 작업)

vertical TDD 작업 시 사용자가 "지금 어느 슬라이스 / 어느 사이클 / 어느 단계인지" 한눈에 보이도록 진행 매트릭스를 매 체크포인트에 노출 + TodoWrite 로 단계별 상태 추적.

```
📊 전체 진행 (슬라이스 N개 중 K번째)
| # | 슬라이스 | API | 상태 |
|---|---|---|---|
| 1 | {이름} | {Method Path} | 🚧 진행 중 |
| 2 | {이름} | {Method Path} | ⏳ 대기 |

📊 현재 슬라이스 사이클
| 사이클 | 행위 | 상태 |
|---|---|---|
| 1 | {행위} | ✅ |
| 2 | {행위} | 🚧 GREEN 완료, Docs 대기 |
```

- 슬라이스 단위는 설계 문서(`docs/{도메인}/`)에 이미 정의되어 미리 표시 OK.
- **사이클 단위는 anticipation 금지** — 미래 사이클 행을 미리 추가하지 않는다. 한 사이클 종료 후 다음 행위를 결정한 시점에 추가.

## 도메인 신규 개발 — vertical-slice TDD

mattpocock `tdd` 스킬의 vertical-slice TDD 를 따른다. 테스트와 구현이 한 슬라이스(=대개 한 API)당 한 사이클로 함께 자란다. "전체 구현 → 후행 테스트"(horizontal slicing) 는 안티패턴으로 금지.

| # | 시점 | 접두사 |
|---|---|---|
| 1 | API 설계 문서 완성(`/api-design`) | `[Docs]` |
| 2 | 엔티티 + 마이그레이션 SQL(`V{n}__*.sql`) | `[Feat]` |
| 3-N | API별 vertical TDD 사이클 | 단계별 분리 |

**Vertical TDD 사이클 한 번** = RED → GREEN → (REFACTOR) → Docs, **각 단계 별도 커밋**:
```
RED:      실패 테스트 1개 (한국어 @DisplayName)        → [Test] {슬라이스} {행위} 실패 테스트
GREEN:    그 테스트를 통과시키는 최소 구현               → [Feat] {슬라이스} {행위} 구현
REFACTOR: 중복 추출 (테스트 GREEN 유지, 없으면 생략)     → [Refactor] {슬라이스} {대상} 추출
Docs:     설계 문서 테스트 리스트 표 한 줄 추가          → [Docs] {슬라이스} 테스트 리스트 #N 반영
```

- Repository/QueryDSL 메서드·`ExceptionCode` enum 신규 추가도 슬라이스 GREEN 에서 함께(미리 짜놓지 않음 — 각 메서드/enum 존재가 테스트로 정당화).
- Entity 매핑 변경 시 Flyway 마이그레이션 SQL(`src/main/resources/db/migration/V{n}__*.sql`, MySQL 방언) 의무 동반.
- 우회 금지: `em.flush()`/`em.clear()` 로 PC 강제 sync, mock 과잉, production 과 다른 path 로 테스트만 통과시키지 않는다. GREEN 안 되면 root cause 진단(`diagnose` 스킬).

## 슬라이스 종료 확인 (anticipation 금지)

- 슬라이스의 모든 사이클이 끝났다고 판단되면 **한 번 멈춰** 설계의 critical 행위가 모두 작성됐는지 + 추가 검증 케이스(경계/격리)가 있는지 확인하고 사용자와 결정.
- 설계 문서의 테스트 리스트 표는 **빈 표(헤더만)로 시작**, placeholder 행 금지 — 사이클마다 한 줄씩 누적. 미래 시나리오는 본문 설계 노트에만 적는다.
- 미리 "총 N 사이클" 같은 분배 금지. 한 사이클 끝날 때마다 다음 critical 행위를 그 자리에서 결정.

## 체크포인트 적용 범위

- **적용(체크포인트 발동)**: 도메인 신규 개발·기존 수정, API 설계 문서, 마이그레이션 SQL.
- **제외(끝낸 뒤 1회 커밋)**: 메타 설정/스킬/룰 변경(`.claude/**`, `CLAUDE.md`) — 체크포인트(슬라이스/사이클) 발동 없이 작업 끝낸 뒤 1회 커밋. 이 repo 는 `.claude/` 도 git 추적 대상이므로 커밋한다.

## 체크포인트 발동 시 절대 규칙

체크포인트 발동 = **즉시 멈춤**. 다음 단계 Read/Bash/Grep 탐색·작업 분해 금지. 작업 내역 + 추천 커밋 메시지를 제시하고 "커밋했어"/"다음 진행해" 응답까지 대기.

## 단계 전환 시 커밋 상태 직접 확인 (필수)

다음 작업 단계(슬라이스/사이클/문서)에 착수하기 **직전, `git status --short` + `git log --oneline -N` 으로 커밋 상태를 직접 확인**한다:
- 직전 단계 산출물이 모두 커밋됐는지 (미커밋 `M`/`??` 가 없는지).
- 추천 커밋에서 빠진 파일(문서·설정 등)이 워킹트리에 떠 있지 않은지.
- 사용자가 "커밋했다"고 해도 추측하지 말고 `git log` 로 실제 반영을 확인.
- 미커밋/누락 발견 시 **다음 작업 착수 전에 먼저 커밋을 제시**해 정리한다 (떠다니는 변경이 다음 커밋에 섞이는 것 방지).

## 세션 분할 제안 (컨텍스트 위생)

세션 진행 중 새 세션으로 넘어가는 편이 나은 신호가 보이면 **강제로 넘기지 말고 먼저 제안**한다. 신호:
- 작업 단위(도메인/슬라이스/주차)가 완결되고 다음이 별개 단위일 때.
- 컨텍스트가 길어져(특히 compact 발생 후) 성능 저하·재compact 위험이 있을 때.
- 다음 작업이 현재 대화 맥락에 거의 의존하지 않고 문서·코드·git 으로 복원 가능할 때.

제안 시: 새 세션이 나은 **이유** + **인계 프롬프트**(현재 상태·다음 작업·참고 문서)를 함께 제시하고, 유지/분할은 사용자가 결정한다.
