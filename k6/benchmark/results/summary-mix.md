# 벤치마크 요약 — mix

`run-multi.sh` 가 생성한다. 손으로 고치지 않는다 — 재실행하면 덮인다.

- 스토리지 **tmpfs** · 재고 = VU×2 (전원 차감) · 회차 **6회**
- 값은 **중앙값 (최소~최대)**. 회차별 원값은 [`results/mix/raw.tsv`](./mix/raw.tsv) 한 줄씩
- 회차별 k6 출력 원문은 저장소에 두지 않는다. 수치가 전부 raw.tsv 에 있고, 원문은 재실행하면 다시 나온다
- 주문 p95 는 `order_duration` — 주문 요청만 잰다. 처리율은 `order_success` 의 초당 건수

## 배경 조회 지연 — 재고 부하가 번지는가

`GET /api/auth/me` (users PK 단건). 같은 도착률·같은 지속 시간으로 두 번 돌려, 주문 폭주가 겹칠 때만 달라지는지 본다.

| 전략 | 앱 | VU | 동시 부하 | 조회 p95 |
|---|:--:|--:|---|---|
| conditional | 3 | 1000 | 없음 | 16ms (11ms~40ms) |
| conditional | 3 | 1000 | 주문 폭주 | 1.37초 (1.04초~3.00초) |
| redis | 3 | 1000 | 없음 | 13ms (9ms~20ms) |
| redis | 3 | 1000 | 주문 폭주 | 835ms (612ms~1.68초) |

## 주문 지연 (참고)

> 이 모드의 **처리율은 읽지 않는다.** 배경 조회의 지속 시간이 k6 총 실행 시간에 들어가
> 분모가 되므로 주문 처리율이 실제보다 훨씬 낮게 나온다. 처리율은 sweep 요약에서 본다.
> `base` 행은 주문을 쏘지 않는 기준선이라 성공이 0 이다.

| 전략 | 앱 | VU | 주문 p95 | 처리율 | 성공 | 전송 실패 | 오버셀 | 행잠금 대기 | 커넥션 획득 대기 |
|---|:--:|--:|---|---|---|---|---|---|---|
| conditional | 3 | 1000 | 0ms (-~-) | 0.0/s | 0/1000 | 0 | 0 | 0.0회 / 0ms | 12ms |
| conditional | 3 | 1000 | 1.82초 (1.48초~3.61초) | 125/s | 1000/1000 | 0 | 0 | 996회 / 44.16초 | 383.46초 |
| redis | 3 | 1000 | 0ms (-~-) | 0.0/s | 0/1000 | 0 | 0 | 0.0회 / 0ms | 4ms |
| redis | 3 | 1000 | 1.37초 (1.10초~2.33초) | 125/s | 1000/1000 | 0 | 0 | 0.0회 / 0ms | 225.05초 |

**전송 실패**는 200·409 가 아닌 응답이다 — 연결이 끊기거나 5xx 일 때만 오른다.
성공 건수가 인원에 못 미치는 것이 경합 때문인지 요청이 서버에 닿지도 못한 것인지를 가른다.
성공·실패는 중앙값으로 접지 않고 회차 간 최소~최대로 적는다.

**커넥션 획득 대기**는 `hikaricp_connections_acquire_seconds` 의 부하 전후 누적 델타(앱 합산)다.
풀이 병목이면 여기가 오르고, 자리가 남으면 0 에 가깝다. 순간값(active)은 짧고 잦은 대기를 놓치므로 누적으로 잰다.
